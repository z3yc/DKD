# L0-05 · AI 协作三件套：AGENTS.md / CLAUDE.md / REVIEW.md

> 2026 年的现实：**大部分代码第一次是被 AI 读到的，不是被人读到的。**
> 这三份文档的写法，直接决定 AI 生成代码的质量上限。本文件是整套体系中**投入产出比最高**的部分。

## 1. 三份文档的分工（不要合并成一份）

| 文档 | 读者 | 回答的问题 | 篇幅上限 |
|---|---|---|---|
| **AGENTS.md** | AI（写代码前读） | 这个项目是什么、有什么硬约束、动代码前必须知道什么 | 无上限，但要**可检索**（分节、有目录） |
| **CLAUDE.md** | AI（每次对话加载） | 精简版：技术栈 + 模块 + 路由；**指向 AGENTS.md** | **≤60 行** |
| **REVIEW.md** | AI（评审时读）+ 人 | 我负责的这块代码里，**什么最重要**；**失败长什么样** | 每子系统一份，≤80 行 |

**为什么必须分开**：`CLAUDE.md`/`AGENTS.md` 会在每次对话被完整加载，越长越容易被截断、越容易稀释关键约束；而 `AGENTS.md` 是"按需查阅"的。把所有东西塞进 `CLAUDE.md` 是新手最常见的错误，结果是模型两边都没记住。

## 2. AGENTS.md 的必备章节（缺一不可）

```
1. 项目概览 + 子系统表（技术栈 / 位置 / 职责 / 端口）
2. 核心架构约束（**不可违背**的硬规则，带"为什么"）
3. 代码风格与命名约定（按语言分节）
4. 目录结构与模块边界
5. 注释与文档同步义务
6. 测试要求（覆盖率门槛、哪些必须打桩）
7. 已知的环境边界（**实测值，不许凭印象写**：DB/中间件版本与能力限制）
8. 常用验证命令（复制即可跑）
9. 术语表（见 02-naming.md）
10. 变更记录
```

**第 2 节和第 7 节是灵魂。** 它们的写法有讲究：

- **第 2 节（硬约束）**：每条必须写"违反会怎样"。
  ```
  ❌ "写操作要经 Java 服务"
  ✅ "所有写操作必须经 Java 服务的事务与校验链；绕过会跳过防重/状态/区域校验，
      直接产生重复工单 —— 2026-10 曾因此产生 N 张重复单"
  ```
  AI 对"禁止"的理解是模糊的，对"会导致什么后果"的理解是具体的。

- **第 7 节（环境边界）**：必须是**实测值**，并注明核实日期。
  ```
  ❌ "Redis 版本较旧"
  ✅ "Redis 3.2.100（2026-09-21 实测）：无模块系统（无 RedisJSON/RediSearch）、
      内核 <5.0（无 Streams）、appendonly no。→ 不得用作 LangGraph checkpointer，
      不得用作 Stream 队列。"
  ```
  凭印象写的版本信息，会让 AI 产出基于错误前提的代码，且极难在评审中发现。

## 3. REVIEW.md 的写法（多数团队缺的就是这份）

`REVIEW.md` 由**代码 owner** 写，告诉评审者（人或 AI）在这块代码里什么最重要。五个必备块：

```markdown
# REVIEW.md · <子系统名>

## 1. 这里什么最重要（按重要性排序）
1. 数据一致性：任何写入必须经 <Xxx>Service 的校验链
2. 幂等：同一请求重复提交不得产生重复记录
3. 可观测：每个决策必须留痕

## 2. 失败长什么样
- 文档失败 = **它在撒谎**（写得不完整不如不写）
- 配置失败 = **它转错路由**（错配比漏配更危险，漏配会报错，错配不会）
- 数据失败 = **它静默产生错误结果**（最危险，必须有对账）

## 3. nit 上限
- 最多提 3 条 nit；超过说明该改的是 lint 规则，不是这次的 PR

## 4. 跳过这些路径
- `target/`、`dist/`、`*.generated.*`、第三方 vendor

## 5. 证据要求
- 每个发现必须给出 **文件:行**，凭名字猜测的一律无效
- 摘要以**计数**开头："3 个问题：1 个重要，2 个 nit"
- **没问题就明确说"nothing to fix"**，不要为了显得有用而硬凑
```

> **"失败长什么样"是最难写也最有用的部分。** 它把抽象的"质量"翻译成这个系统里的具体失效模式。写不出来，说明你还没真正理解这块代码的风险。

## 4. 让 AI 遵守这些文档的三个技巧

1. **写在它必读的位置**：`AGENTS.md`/`CLAUDE.md` 放仓库根；`REVIEW.md` 放各子系统根。
2. **用负面示例**：只写"禁止 X"效果有限，写"❌ 这样写 → 会导致 Y"效果好得多。
3. **把反复出现的评审意见回灌**：如果 AI 连续三次犯同一类错，说明文档里没写清楚 —— 修文档，不要第三次手动改代码。这是一个正反馈回路：文档越好，人工修补越少。

## 5. 模板文件

见 `SPEC/templates/`：
- `AGENTS.md.template` —— 完整骨架，带填写指引
- `CLAUDE.md.template` —— 精简版
- `REVIEW.md.template` —— 评审关注点

使用：复制到项目根，替换 `__XXX__` 占位符，**删掉所有没填的章节**（留空章节比没有更糟 —— 空章节会被当成"此处无约束"）。
