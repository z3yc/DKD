# L0-02 · 标识符语义命名与术语表

> 上一篇（01）解决"文件叫什么、目录怎么放"；本篇解决"变量/函数/类叫什么"。
> 核心观点：**命名的难点不是格式（大小写），而是语义一致性** —— 同一个概念在系统里必须只有一个名字。

## 1. 命名的三层语义

| 层 | 要回答的问题 | 失败后果 |
|---|---|---|
| **领域层** | 它在这个业务里叫什么 | 代码与需求对不上，产品与开发鸡同鸭讲 |
| **角色层** | 它在架构里是什么角色（Controller/Service/DTO） | 职责漂移，业务逻辑渗进不该去的层 |
| **类型层** | 它是什么类型、什么单位、什么时区 | 隐式 bug（金额单位、时间戳时区） |

**先定领域名，再套角色后缀，最后标类型。** 顺序不能反。

## 2. 领域术语表（GLOSSARY）机制 —— 这是本篇最重要的东西

在每个项目的 `AGENTS.md` 里维护一张术语表，**它是命名的唯一权威**。任何新增标识符的名字必须能在术语表或业务词汇里找到依据。

```markdown
## 术语表（新增标识符前先查这里）
| 术语 | 代码名 | 禁止使用的别名 | 说明 |
|---|---|---|---|
| 售货机 | vm | machine, device, box | 一台物理设备 |
| 货道 | channel | slot, lane | 设备内的单个货位 |
| 点位 | node | point, place, location | 设备投放场所 |
| 补货工单 | task | order(❌ 与订单冲突), job | 运维人员执行的补货任务 |
| 订单 | order | - | 用户购买产生的交易记录 |
```

**为什么值得花这半小时**：AI 编码助手读一次术语表，后面几百次命名就都对了；不写这张表，它会按照训练数据里的常见用法自由发挥（`device` / `slot` / `job` 混着来），然后你在评审里一条条改 —— 这正是"AI 生成代码"最容易产生返工的地方。

## 3. 动词选择表（函数名）

| 动词 | 用于 | 反例 |
|---|---|---|
| `get_` / `select` | 单条查询，可能返回空 | ~~`query`~~（语义模糊） |
| `list_` | 集合查询，**必须带筛选参数** | `listTasks()` 无参全量 → 应强制分页参数 |
| `count_` | 计数 | ~~`getCount`~~ |
| `create_` / `insert` | 新增，失败抛异常 | ~~`add`~~（add 常用于集合追加） |
| `update_` | 更新，不存在则报错 | |
| `upsert_` | 存在即更新，不存在即插入 | |
| `delete_` / `deleteByIds` | 删除（优先软删） | ~~`remove`~~ 与集合操作混淆 |
| `validate_` | 校验，失败抛异常，**不改状态** | |
| `check_` | 返回布尔，**不抛异常** | 与 validate 必须严格区分 |
| `build_` / `to_` | 构造 / 转换 | ~~`make`~~ |
| `ensure_` | 保证某状态成立（幂等） | `ensure_index()` |
| `handle_` / `on_` | 事件处理 | |

**铁律**：`check_` 与 `validate_` 不得混用。调用方需要 if 判断时用 `check_`，需要中断流程时用 `validate_`。混用会导致调用方重复处理错误分支或漏处理。

## 4. 类型与单位标注（消除隐式 bug）

| 场景 | 规则 | 示例 |
|---|---|---|
| 金额 | **单位写进名字** | `price_cents` / `amount_yuan` / `BigDecimal amount` |
| 时长 | 单位写进名字 | `timeout_ms` / `duration_seconds` |
| 时间 | 明确是时间点还是时长；跨系统统一 UTC 或统一本地时间并注明 | `expire_at`（时间点）/ `ttl_seconds`（时长） |
| 比例 | 明确是 0~1 还是 0~100 | `discount_rate`（0~1）/ `discount_percent`（0~100） |
| 集合 | 用复数 | `task_ids` / `items` |
| 布尔 | 正向语义优先，避免否定式 | `enabled` / ~~`disabled`~~；`skip_validation` 例外保留 |

> 反模式真实代价：某项目 `amount` 在 DB 里是分、在接口里是元，两边都叫 `amount`，上线后对账差 100 倍。命名层解决不了的问题会一路漏到线上。

## 5. 跨系统字段对齐

跨服务/跨语言边界（HTTP、MQ、DB）传输时，字段名必须**完全一致**，不得做语言风格的驼峰/下划线转换而不记录：

- 边界协议统一用 `snake_case`（JSON / DB 列名）；
- Java 内部可以 `camelCase`，但**序列化出口必须转 `snake_case`**，且转换由统一配置完成，不允许手写 `@JsonProperty` 逐个标注；
- 新增边界字段必须同步更新接口文档与 DDL 归档。

## 6. 反模式清单（评审时直接对照）

| 反模式 | 问题 | 修法 |
|---|---|---|
| `data` / `info` / `result` / `temp` / `obj` | 无信息量 | 换成领域名 |
| `flag` / `status` 无枚举约束 | 魔法值遍地 | 定义枚举，code + name |
| `handleData()` | 职责不清 | 拆成动词 + 宾语 |
| 同名不同义（`order` 既指订单又指排序） | 跨模块误读 | 术语表登记，禁止别名 |
| 缩写未登记 | 新人/Agent 看不懂 | 进术语表，否则写全称 |
| `Manager` / `Helper` / `Util` 大杂烩 | 无边界的类 | 按职责拆；`Util` 只允许放**无状态纯函数** |
| 布尔 `isXxx` 字段 | 序列化/框架陷阱 | 去掉 `is` 前缀 |
