# L0-00 · 体系总览与分层原则

## 1. 设计目标（按优先级）

1. **可单独取用** —— 想要任意一个模块时，能只拿那一个，不需要搬整个体系。
2. **可裁剪** —— 删掉不用的部分不会破坏剩下的部分。
3. **跨项目一致** —— 不同项目里同类问题的解法是同一套，换项目不需要重新决策。
4. **轻量** —— 规范是文档不是框架；核心模块加起来不超过 **500 行**；不引入重量级依赖。
5. **对 AI 编码友好** —— 规范能被 LLM 直接读取并遵守（这是 2026 年的硬需求）。

> 反目标（明确不做）：不做框架、不做代码生成器、不替代语言生态的成熟方案（如不自己写 ORM）。

## 2. 四层模型与依赖方向

```
┌─────────────────────────────────────────────────────┐
│ L3 TEMPLATES  可运行骨架    python-fastapi / java / vue│
├─────────────────────────────────────────────────────┤
│ L2 CORE       可迁移实现    config logging errors ... │
├─────────────────────────────────────────────────────┤
│ L1 CONTRACTS  跨语言契约    错误码 响应包装 日志字段   │
├─────────────────────────────────────────────────────┤
│ L0 SPEC       纯文档规范    目录 命名 风格 注释 Git   │
└─────────────────────────────────────────────────────┘
        依赖方向：上 → 下（单向，禁止反向）
```

**为什么契约层（L1）要独立存在**：跨语言项目里最常见的失败是"同样的概念在四个子系统里叫四个名字" —— 错误码 Java 用 `5001`、Python 用字符串 `"internal"`、前端只认 HTTP 状态码。L1 的价值是让**同一件事在所有语言里长得一样**，且它是纯文档，不绑定任何技术栈。

## 3. 依赖检查清单（新增任何东西前先过一遍）

- [ ] 它属于哪一层？说不清层级的，不收。
- [ ] 它依赖的下层是否已存在？依赖**同层或上层**的，重构后再收。
- [ ] 它能被单独取走吗？需要"配套复制 3 个文件才能用"的，说明耦合过度，拆开。
- [ ] 引入的第三方依赖是否必要？能靠标准库解决的，不引。
- [ ] 加了之后，体系总行数增加多少？超过 100 行的新增模块需要说明理由。

## 4. 与项目已有规范的关系

dev-kit 是**默认基线**，项目自己的 `AGENTS.md` 是**项目级覆盖**。二者冲突时：

```
项目 AGENTS.md  >  dev-kit SPEC  >  个人习惯
```

理由：项目已有约定（如 DKD 的 Java 8 边界、Redis 版本约束）是踩过坑换来的，通用规范必须让路。dev-kit 的 SPEC 在被项目采纳时，应显式写进项目 `AGENTS.md` 的"引用清单"，并在差异处注明覆盖。

## 5. 版本与兼容性

- dev-kit 自身用 `VERSION` 文件（语义化版本）；
- **破坏性变更**（改契约字段、改目录约定）必须升主版本，并在 CHANGELOG 写明迁移步骤；
- 已落地项目**不强制跟随升级**，只在下次开新项目时用新版 —— 这是"复制而非引用"策略的代价，也是它稳定的原因。
