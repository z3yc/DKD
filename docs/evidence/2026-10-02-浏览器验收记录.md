## 三、新发现问题

### F-1 🟡（P2，功能失效，根因=环境配置漂移）Java 兜底单轮 AI 链路 401

**现象**：`设备管理 /vm/vm → 行内「AI诊断」` 弹窗直接显示：

```
AI 接口请求失败 (Status 401): {"error":{"message":"Authentication Fails, Your api key: ****48a8 is invalid ..."}}
```

截图：`docs/evidence/2026-10-02-browser-legacy-ai-401.png`

**根因（已取证到字节级）**：

| 来源 | Key 尾号 | 实测对 `api.deepseek.com/models` |
| --- | --- | --- |
| `.env`（Python 侧读取） | `feb2` | **HTTP 200（有效）** |
| Windows **用户级**环境变量 `DKD_DEEPSEEK_API_KEY`（Java 侧读取，`application.yml:151`） | `48a8` | **HTTP 401（无效）** |

- Java 进程 `PID 11128` 启动于 `2026-10-01 12:51:35`；`.env` 的 mtime 为 `2026-10-01 15:38:40`（**晚于** Java 启动）——但 Java 本来就不读 `.env`（README 已写明）。
- ⇒ 这正是 `AGENTS.md §9.3` 记录的坑：**"启动服务前先核对 `env` 与 `.env` 是否一致"**，残留旧值会覆盖 `.env`，报错却指向"鉴权失败"。

**影响（不止一个按钮）**：
1. `/manage/ai/diagnose`（旧单轮链路）在本机**完全不可用**；
2. **M1 验收项「`agent.enabled=false` 一键降级，主业务零影响」在本机不成立**——降级目标本身就是 401。排期 0-15 记录该项为"✅ 通过"，实际只验到了"开关能关"，**没验"关掉之后兜底真的能用"**（本轮把后半句补上了，结论是不成立）。

**修复**（非代码问题，需人工）：
```powershell
# 1) 用 .env 的有效值覆盖用户级环境变量
setx DKD_DEEPSEEK_API_KEY "<.env 中的值>"
# 2) 重启 Java 进程（环境变量变更需新进程生效）
# 3) 复验：
curl -s -o /dev/null -w "%{http_code}\n" https://api.deepseek.com/models -H "Authorization: Bearer $env:DKD_DEEPSEEK_API_KEY"   # 期望 200
```
> 建议同时把"启动前核对 env 与 .env"补进 `dkd-agent/README.md` 与 `deploy/` 手册的启动检查单。

### F-2 🟢（P3，前端一致性）`el-tag type="primary"` 非法 → 每次渲染产生 Vue 警告

- Element Plus **2.4.3** 的 `ElTag.type` 校验只接受 `["success","info","warning","danger",""]`，而以下 4 处会返回 `'primary'`：
  - `dkd-vue/src/views/manage/restock/index.vue:386` `priorityTagType()` → `2: 'primary'`
  - `dkd-vue/src/views/manage/restock/index.vue:406` `statusTagType()` → `[1-建议]: 'primary'`
  - `dkd-vue/src/views/manage/agentAudit/index.vue:312` `sceneTagType()` → `4: 'primary'`
- 实测（补货工作台每次进入）：`[Vue warn]: Invalid prop: validation failed for prop "type"... got value "primary"` + `custom validator check failed`，每条渲染触发一次。
- **视觉未坏**：`.el-tag--primary` 的 CSS 规则实际存在（实测 computed `background-color: rgb(235,245,255)`、`color: rgb(64,158,255)`），所以是"控制台噪声 + 校验失效"，不是显示异常。
- **为什么既有脚本没抓到**：`docs/scripts/restock-workbench-browser-check.cjs:85` 是 `if (m.type() === 'error')`——**只看 error，不看 warning**。
- 项目内已有正确写法可对照：`dkd-vue/src/views/system/dict/data.vue:95`（`scope.row.listClass == 'primary' ? '' : scope.row.listClass`）。
- 建议：把 4 处返回值按上述约定收敛为 `''`，并把验收脚本的 console 断言扩到 `warning`（否则同类问题会再次从"0 错误"里溜过去）。

### F-3 🟢（P3，错误呈现/信息暴露）上游原始错误 JSON 直接渲染给终端用户

- 兜底链路把 `Authentication Fails, Your api key: ****48a8 is invalid (request_id: …)` **原样**塞进业务弹窗。
- 两个问题：① 运营看到的是英文技术栈报错，无法据此行动；② 虽已掩码，仍向界面暴露了凭据指纹与上游请求 ID（`AGENTS §6.1` 已明令"日志中禁止输出完整 LLM 请求体"，此处是更宽的界面暴露）。
- 建议（属遗留链路，`AGENTS §3.5` 要求保留不删）：只向界面给可读文案（如"AI 服务鉴权失败，请联系管理员核对 API Key"），真因写日志。

### F-4 🟢（P3，文案与内容不符）审计页提示条把会话问答也算作"写操作"

- `dkd-vue/src/views/manage/agentAudit/index.vue:74` 提示条写：「本页展示智能体对业务数据的每一次**写操作**决策（含成功 / 幂等 / 被拒绝 / 失败四条路径）」。
- 实际列表里占比最大的是 `chat.respond`（每轮对话一条，属**读/会话**留痕，用于 token 计量与 trace），真正的写操作是 `restock.resume` / `restock.skip` / `restock_confirm` / `restock_adjust` / `restock_analyze`。
- 影响：审计人员按"写操作"理解会误判范围（也会让"写操作 100% 留痕"这句验收结论失去意义——因为分母里混了非写操作）。
- 建议：提示条改为"会话与写操作的完整决策留痕"，或加一列/一个筛选项显式区分 `chat.*` 与业务写动作。
