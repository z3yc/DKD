## 0. 一页看懂

### 0.1 这是什么生意

**B 端智能售货机运营平台**（帝可得）：把传统投币售货机改造成"扫码支付 + 远程运营"的设备，卖给/服务有点位资源的运营方。平台方赚钱的方式不是卖货，而是**让有限的设备和点位少缺货、少坏机、少跑空趟**——所以系统重心在"运营效率"而不是"交易本身"。

业务模式：**自营 / 加盟 / 点位主分成**三种（`dkd-parent/README.md:14`[档]）。这解释了 `tb_partner`（合作商 + 分成比例 + 独立账号）和 `tb_vending_machine.partner_id` 的存在。

一句话概括四类使用者：

| 谁 | 用什么端 | 关心什么 |
| --- | --- | --- |
| 平台/运营主管 | 管理后台（Vue） | 设备台账、点位、商品、补货计划、工单、报表 |
| 运营/补货员 | 管理后台 + 运维移动端 | 今天哪台机器缺什么、补多少、单子派给谁 |
| 维修/运维工程师 | 运维移动端（dkd-app） | 我的待办工单、接单、到场、完成 |
| 合作商（有点位没运营能力） | 后台/合作商侧 | 我的点位分成、设备与销售数据 |
| （C 端消费者） | 售货机屏幕/小程序 | 扫码支付拿货——**不在本仓库** |

### 0.2 全景图（四个端 + 外部系统 + 一条旁路）

### 0.3 六条必须先知道的结论

1. **本仓只覆盖"运营 + 运维"，不覆盖"交易"**：下单/支付/出货/设备接入（EMQ）都不在仓库里；`tb_order` 被当作外部写入的事实表消费[码]。
2. **库存有两套物理来源，且只有一套被写**：后台预警/建议读 `tb_inventory.current_stock`，运维端补货完成却只写 `tb_channel.current_capacity` → **补货动作消不掉预警**[码]。这是全项目第一号数据口径风险。
3. **工单是核心业务对象，建单校验链是核心规则**：后台建单与智能体建单共用同一条 8 步校验链（设备存在→设备状态×类型→在途防重→员工存在→区域一致→落库→明细→唯一键兜底）[码]。
4. **权限是"URL 级 + 菜单级"，没有行列级**：业务域 0 处 `@DataScope`，有 `manage:*:list` 就能看全国数据[码]。
5. **智能体是旁路增值层，不是第二套后端**：读走只读账号+白名单，写一律回调 Java，写操作强制人工确认并留痕；`agent.enabled=false` 时主业务不受影响[码/档]。
6. **"运营分析 Copilot"目前是空能力**：Phase 3 的 NL2SQL/分析模板已被主动砍掉，`scene=4` 只会在提示词里说"查不了，去报表页"[码]。

## 1. 业务背景与系统边界

### 1.1 业务对象与生命周期

平台运营的核心资产链是 **区域 → 点位 → 售货机 → 货道 → 商品**，围绕它跑四类业务：**投放（把机器装上）、销售（C 端买）、补货（把货补满）、维修（把坏机修好）**，最后用报表和工单数据反哺选点与排班。

### 1.2 系统边界（哪些在本仓 / 哪些不在）

| 能力 | 归属 | 事实 | 影响 |
| --- | --- | --- | --- |
| 设备台账/货道/商品/点位/员工/合作商/策略 | 本仓 `dkd-manage` | 档案 CRUD + 少量业务规则[码] | —— |
| 订单查询/取消/退款 | 本仓 | 只有查询与弱状态流转，**没有创建/支付/出货**[码] | 订单数据质量不可控，只能"读" |
| 下单、支付、出货、设备在线状态 | **仓外**（售货机端服务，MQTT/EMQ） | `VendingMachine.clientId` 注释"做 emq 认证用"[码]；代码里无 MQTT/支付客户端 | 库存扣减、异常订单检测只能基于结果表 |
| 工单执行（接单/完成） | 本仓 `dkd-app`（独立端口 9070） | 与后台**共用 `dkd` 库**、**不共用账号体系**[码] | 两套 JWT、两套主体（见 §5） |
| 补货建议（规则版） | 本仓 `dkd-manage` | 静态公式：补到 85%、下限 2×min[码] | 与智能体版并存，口径不同 |
| 补货建议（智能体版） | 本仓 `dkd-agent` | 7/14/30 天分位基线 + LLM 系数校准 + 人工确认[码] | 两套建议并存是当前过渡态 |
| 故障诊断 | 本仓 `dkd-agent` + 后端降级链路 | 诊断→证据→派单提案→人工确认→建维修单[码] | 无故障知识库（维修单无现象/原因字段） |
| 报表/AI 解读 | 本仓 | 日报/周报聚合 + LLM 分析落 `tb_report`[码] | 报表任务默认**暂停**且异常被吞（§8） |
| 短信验证码、OSS 上传 | 本仓接入外部服务 | dkd-app 短信、后台 `/common/upload`→OSS[码] | 缺凭据时 fail-closed |

### 1.3 基础设施现实约束（会直接影响业务方案）

| 项 | 现实 | 对业务的含义 |
| --- | --- | --- |
| 数据库 | **单主库、无从库**（`slave.enabled=false`） | 任何分析类查询必须限时间窗+分批+超时，否则与交易抢资源 |
| Redis | **3.2.100**（2016 移植版，无模块/无 Streams/仅 RDB） | 不能做 LangGraph 会话存储，也不能做队列；智能体会话走 SQLite/PostgreSQL |
| 业务表 DDL | **未入库**（`dkd-parent/sql/` 只有系统表/quartz/报表） | 表结构只能从 Mapper + `docs/ddl/` 实测归档反推，已出现代码与库结构疑似不一致（§8.2） |
| 环境 | Windows 开发机、4 个 Python、本机 MySQL/Redis/PG | 运行时坑多，见 AGENTS §1 约束 5 与排期 §十 |

## 2. 业务模型：组织、资产、交易、作业

### 2.1 主链路（业务口径）

```
区域 Region ── 1:N ── 点位 Node ── 1:N ── 售货机 VendingMachine ── 1:N ── 货道 Channel ── N:1 ── 商品 Sku
   │                    │                        │                          │
   │                    └─ 合作商 Partner        ├─ 设备型号 VmType（行×列→建机时生成几个货道）
   │                                             └─ 策略 Policy（折扣，当前无消费方）
   │
   ├─ 员工 Emp（区域+角色：1001 管理 / 1002 运营 / 1003 维修）
   ├─ 库存 Inventory（按 vm+sku+channel 的库存档案，**后台预警读它**）
   ├─ 工单 Task（投放/补货/维修/撤机，一单一类型）+ 补货明细 TaskDetails
   ├─ 订单 Order（外部写入的全快照表：设备/货道/商品/点位/区域名都冗余落库）
   └─ 报表 Report（日报/周报 + AI 分析）
```

### 2.2 ER 关系（文字化，关键点）

```
tb_region 1─N tb_node(region_id)          tb_partner 1─N tb_node(partner_id)
tb_node   1─N tb_vending_machine(node_id) tb_vm_type 1─N tb_vending_machine(vm_type_id)
tb_vending_machine 1─N tb_channel(vm_id，另有冗余 inner_code)
tb_sku 1─N tb_channel(sku_id；NULL=空货道)      tb_sku_class 1─N tb_sku(class_id，自关联树)
tb_vending_machine 1─N tb_inventory(vm_id)      tb_channel 1─N tb_inventory(channel_id)
tb_emp N─1 tb_region / tb_role                  tb_task N─1 tb_vending_machine(inner_code 字符串关联)
tb_task 1─N tb_task_details(task_id)             tb_task N─1 tb_emp(user_id=执行人)
tb_order / tb_report / tb_job / tb_policy：基本独立，order 是全快照表
agent_run 1─N agent_step 1─N agent_tool_call；agent_decision_log 以 request_id 关联业务动作
```

模型特征（都是有业务后果的）：

1. **无数据库外键**：关系全靠应用层维护，删除无级联保护 → 删区域/点位/设备会留下孤儿数据[码]。
2. **大量冗余/快照列**：`tb_channel.inner_code`、`tb_emp.region_name`、`tb_order` 全字段快照、`tb_task_details` 的商品快照。改名只同步一处（区域改名同步 `tb_emp`，**不同步订单快照**）[码]。
3. **库存双源**：`tb_inventory`（后台口径）与 `tb_channel.current_capacity`（运维端补货口径）并存，实测档案显示 `sku_id` 与容量 **3/3 全不一致**[档]。
4. **明细不建 FK**：`tb_task_details.channel_code` 是字符串，不校验是否属于该设备 → 填错/不存在的货道在完成时被**静默跳过**，工单仍"完成"[码]。

### 2.3 数据规模（开发库实测档案，2026-09-21）[档]

| 表 | 行数 | 备注 |
| --- | --- | --- |
| `tb_vending_machine` | 15 | 全部运行中 |
| `tb_node` / `tb_region` | 6 / 4 | 点位/区域 |
| `tb_channel` | 272 | 货道档案 |
| `tb_inventory` | **3** | 对比 272 个货道，库存档案严重缺失 |
| `tb_order` | 29 | 时间集中在 **2023-09**（对"近 30 天"演示是空结果） |
| `tb_task` / `tb_task_details` | 22 / 13 | 工单在 2025-11；明细缺失 |
| `tb_emp` | 17 | 派单候选人来源 |

> 这组数字是后续一切"验收/回测"卡住的根因：**没有足够真实数据就验不了"建议量 ±20%"和"10 台真机闭环"**（FIX-6）。

## 3. 六条端到端流程（现状标注）

> 图例：✅ 闭环可验证　⚠️ 半闭环（有断点/口径不一致）　❌ 本仓无实现

### 3.1 投放上架 ✅（但中间隔 3 个手工步骤）

```
建区域 → 建点位 → 建设备(POST /manage/vm)
   → 后端按型号 vm_row×vm_col 批量生成货道（current_capacity=NULL）
   → ① 给货道绑商品（PUT /manage/channel/config）
   → ② 初始化库存（POST /manage/inventory/init，**前端无入口**）
   → ③ 建投放工单（POST /manage/task，type=1）
   → 运维端 accept → complete：工单完成 + vm_status=1（可售卖）
```

规则：投放工单只允许"非运行中"设备（防重复投放）；完成时自动把设备置为运行中[码]。
风险：① 没有编排/幂等，任一步失败留下"半配置设备"；② 库存初始化接口存在但**没有页面入口**，只能手工调接口或直接改库[码]；③ 后台 `PUT /manage/vm` 能任意改设备状态，绕过工单副作用[码]。

### 3.2 销售与库存扣减 ❌（链路在仓外，且本仓无扣减落点）

- 订单由售货机/支付侧写入 `tb_order`（状态 0 待支付 / 1 支付完成 / 2 出货成功 / 3 出货失败 / 4 已取消）。
- 本仓 `OrderServiceImpl` 只有列表/详情/取消/退款；**库存增减工具 `updateInventoryQuantity` 全仓无调用方**（死代码），补货也不写 `tb_inventory_log`[码]。
- 后果：`tb_inventory` 只在"后台手工初始化/编辑"时变化，与真实销售脱节 → 预警与建议的输入长期失真。

### 3.3 库存预警 → 补货 → 工单 → 回写 ⚠️（最重要、也最断裂的一条）

```
【现状：规则版】
tb_inventory 低库存/缺货 → GET /manage/inventory/{low|outofstock|alerts}
   → GET /manage/inventory/restock（静态建议：补到 max*85%，下限 2*min，上限 max）
   → 人工在「运营工单」建补货单（选设备→选运营员→逐货道填数量）POST /manage/task
   → 运维端接单/到场/完成 → supply()：
        tb_channel.current_capacity += task_details.expect_capacity
        tb_vending_machine.last_supply_time = now
   ✗ 不写 tb_inventory、不写 tb_inventory_log、不校验 max_capacity
   ✗ 于是"补货"永远消不掉"库存预警"
```

**断点本质**：写的是 `tb_channel`，读的是 `tb_inventory`。两条数据流没有交汇，且实测两侧档案 3/3 不一致[档]。补货 Agent 读库存时也面临"读哪侧"的决策（FIX-5 待业务拍板）。

**智能体版（旁路）**：

```
每日 06:00 quartz(job 102) → POST /agents/restock/analyze
   → 取货道库存 + 近 7/14/30 天逐日销量 → 统计基线（加权分位）
   → LLM 校准系数（失败自动降级为纯统计）→ 落 agent_restock_plan（状态=1 建议）
   → 按设备区域选运营员（role 1002、当日负载最低；无候选=待指派）
   → 运营早上在「智能补货工作台」逐条：确认建单 / 调整 / 跳过 / 恢复 / 暂停
   → 确认时回调 POST /agent/callback/task → 复用 Java 建单校验链 → 回写 taskCode
```

### 3.4 维修闭环 ⚠️（诊断派单已通，作业回执缺失）

```
设备异常/用户报障 →（新）管理端「运行时间线」页发起故障诊断
   → Agent：取证（订单异常/库存异常/历史维修单）→ 证据回溯 → 诊断结论（无病因）
   → 派单提案（区域匹配维修员、按证据强度定优先级）
   → 人工「确认建单」→ 回调 Java 建维修单（type=3，允许"停机"设备）
   → 运维端接单 → 到场维修 → 完成（**只改工单状态，无任何现场回执**）
```

缺口：维修单**没有"现象/原因/处置/配件/照片"结构化字段**（`tb_task` 只有 `desc`，实测内容多为 `111` 等占位）[档]，运维端也没有上传接口 → 故障知识库无法冷启动（已降级为规则检索）；维修工单完成没有设备侧副作用（不像投放/撤机会改状态）[码]。

### 3.5 撤机 ✅

建撤机工单（type=4，仅运行中设备）→ 运维完成 → `vm_status=3`。后台也能直接改状态（旁路）[码]。

### 3.6 智能体旁路（增值层）✅/⚠️

| 入口 | 场景 | 现状 |
| --- | --- | --- |
| 智能补货工作台 | 建议→确认→建单 | ✅ 主体可用（M2 数据验收卡在真实数据） |
| 运行时间线页 | 故障诊断→派单提案→确认/驳回 | ✅ M3 已交付（M4 审核官未做） |
| AI 助手抽屉 | 补货问答 / 诊断问答 / 运营分析 / 通用 | ⚠️ 前两者可用；后两者无工具（"诚实但无能"） |

### 3.7 闭环健康度

| 流程 | 状态 | 主要缺口 |
| --- | --- | --- |
| 投放上架 | ⚠️ | 库存初始化无入口、状态可被后台旁路改 |
| 销售扣减库存 | ❌ 本仓无 | 交易在仓外；扣减工具断线 |
| 补货 | ⚠️ 半闭环 | **双库存源不通**；建议量口径待拍板 |
| 维修 | ⚠️ 半闭环 | 无现场回执/无知识沉淀；完成无设备副作用 |
| 撤机 | ✅ | 后台可旁路改状态 |
| 报表 | ⚠️ | 任务默认暂停 + 异常被吞 + 口径偏（§4.5） |
| 智能体 | ✅ 主体 | 数据与知识两处外部依赖未满足 |

## 4. 业务域详解

### 4.1 十八个域一页表

| 域 | 表 | 业务定位 | 成熟度 / 备注 |
| --- | --- | --- | --- |
| 区域 | `tb_region` | 最上层组织维度，被点位/设备/员工冗余引用 | 档案 CRUD；删除无引用检查 |
| 点位 | `tb_node` | 设备落地场地（门店/楼宇），承载商圈类型 | CRUD+Excel 导入（无事务，可能半批成功）+ AI 选址 |
| 合作商 | `tb_partner` | 点位主/加盟方，分成比例 + 独立账号 | CRUD+重置密码；列表 SQL 会带出密码哈希 |
| 员工/角色 | `tb_emp` / `tb_role` | 工单执行人（区域+角色+启停用），是派单候选来源 | CRUD；角色库无维护页面 |
| 设备型号 | `tb_vm_type` | 行×列×单货道容量，决定建设备时生成多少货道 | CRUD |
| 售货机 | `tb_vending_machine` | 设备台账；`vm_status` 是建单校验核心输入 | 档案 CRUD；**无状态机**（可任意改） |
| 货道 | `tb_channel` | 货道档案 + 绑定商品 + `current_capacity`（**运维端补货写这里**） | 配置接口全量提交 |
| 商品/分类 | `tb_sku` / `tb_sku_class` | 商品档案（价格单位**分**）/ 一级分类 | 前端按元录入、提交 `*100` |
| 策略 | `tb_policy` | 折扣策略（`discount` 80=8 折） | **无任何业务代码消费**（空转） |
| 订单 | `tb_order` | 全快照交易记录 | 查询/导出/取消/退款；创建在仓外 |
| 库存 | `tb_inventory` | 按货道的库存档案（current/min/max） | 预警/建议的唯一数据源；与货道侧不一致 |
| 库存流水 | `tb_inventory_log` | 库存增减流水 | 半成品：Mapper 列名与实测表结构不符、唯一写入口无调用方[码/档] |
| 工单 | `tb_task` | 四类作业单，**建单校验链是全项目最强规则** | 强校验；状态可被后台 `PUT` 绕过 |
| 工单明细 | `tb_task_details` | 补货明细（货道+数量+商品快照） | `expect_capacity`=补货数量（注释有陷阱） |
| 工单类型 | `tb_task_type` | 类型字典 | 与常量表口径可能不一致（未连库） |
| 自动补货配置 | `tb_job` | 仅一个"警戒值百分比" | **无消费方**（空转） |
| 报表 | `tb_report` | 日报/周报 + AI 分析 | 聚合口径有偏；任务默认暂停 |
| 智能体审计 | `agent_run`/`agent_step`/`agent_tool_call`/`agent_decision_log` | 过程与决策留痕 | 只读（Java 侧无写入） |

### 4.2 核心规则①：建单校验链（8 步，唯一入口）

入口有两个、实现只有一份：后台 `POST /manage/task` 与智能体 `POST /agent/callback/task` 都走 `TaskServiceImpl.insertTaskDtoInternal`（`@Transactional`）[码]。

| # | 校验/动作 | 规则 | 失败文案（原文） |
| --- | --- | --- | --- |
| 1 | 设备存在 | 按 `inner_code` 查 `tb_vending_machine` | 售货机不存在 |
| 2 | 设备状态 × 工单类型 | 投放：非运行中；**维修：运行中或停机**；补货/撤机：必须运行中 | 设备正在运行中，请勿重复投放 / 设备未投放或已撤机，无法创建维修工单 / 设备不在运行中，请勿重复补货 / 设备不在运行中，请勿重复撤机 |
| 3 | 在途工单防重 | 同设备 + 同类型 + 状态 ∈ {1 待接单, 2 进行中}（`limit 1`） | 设备有未完成工单，请勿重复创建工单 |
| 4 | 员工存在 | 按 `user_id` 查 `tb_emp` | 员工不存在 |
| 5 | 区域一致 | `emp.region_id == vm.region_id`（强制区域隔离的唯一落点） | 员工区域与设备区域不一致，请勿创建工单 |
| 6 | 组装落库 | 状态=1、执行人姓名、区域/地址取自设备、生成 `task_code` | —— |
| 7 | 补货明细 | 仅类型 2 且明细非空时批量插 `tb_task_details`（同事务） | —— |
| 8 | 唯一键兜底 | `DuplicateKeyException`/完整性异常 → 业务文案，整体回滚 | 设备有未完成工单或工单号冲突，请刷新重试 |

**已知缺口**（都会造成"事实不对"）：类型未做枚举白名单（传 5 静默建单）；不校验员工角色/启停用（补货可能派给维修员或已停用员工）；不校验 `channel_code` 归属与 `expect_capacity` 上限；防重的数据库唯一索引**尚未执行**，并发窗口仍在（实测已有 4 张同设备同类型活跃工单）[码/档]。

### 4.3 核心规则②：工单状态机与两条执行路径

```
1 待接单 ──accept──► 2 进行中 ──complete──► 4 完成
   │                     │
   └──── cancel ─────────┴──► 3 取消（拒绝与取消共用状态 3，只靠 desc 区分）
```

- **app 侧副作用**：投放完成→设备运行中；撤机完成→设备已撤机；补货完成→货道库存累加；**维修完成无副作用**[码]。
- **后台旁路**：`PUT /manage/task` 可直接改状态（甚至跳过接单改成完成），`PUT /manage/vm` 可直接改设备状态 → 状态机不是强约束[码]。
- **取消规则**：后台不能取消已取消/已完成；app 只能由本人取消未完成单。

### 4.4 核心规则③：库存预警与补货量（两套口径）

**规则版（Java）**[码]：

| 判断 | 规则 | 级别/优先级 |
| --- | --- | --- |
| 缺货 | service：`quantity == 0`；SQL：`current_stock < min_stock`（两处口径不等价） | 预警级别 3（严重），补货优先级 4 |
| 低库存 | service：`quantity <= min_stock`（`<=50%`→严重、`<=80%`→紧急、其余→普通）；SQL 却用 `=` | 优先级 3/2/1，预计撑 1/2/3 天 |
| 补货量 | 目标 `max*0.85`，下限 `min*2`，上限 `max`；现库存 ≥ `max*0.9` 不建议 | —— |

**智能体版（Python）**：7/14/30 天销量分位（权重 0.5/0.3/0.2）→ 基线建议量与"预计撑到哪天"→ LLM 只输出**校准系数**（不改数量）→ 逐货道 clamp 到 `[0, 货道容量-现库存]` → 人工可调整（直接改量 / 换窗口 / 换服务水平）→ 确认后建单[码]。

两套并存的问题：**建议量口径不一致**（固定 85% vs 销量预测），短期靠"规则版并行双跑"对比（1-14），长期由数据决定是否下线规则版入口。

### 4.5 核心规则④：报表口径

- 只统计 `order.status = 2（出货成功）`，半开区间 `[begin, end)`，`reportDate` = 窗口起点[码]。
- 日报看昨天、周报看前 7 天；`tb_report` 有 `(report_type, report_date)` 唯一键。
- 口径缺陷：`low_stock_devices` 统计的是库存**行数**不是设备数；`fault_devices` 把未投放/停机/已撤机都算"故障"；同名重复生成触发 1062 被双层 catch 吞掉（接口和 Quartz 都显示成功）[码]。
- 定时任务默认状态：日报/周报初始化 `status='1'=暂停`（装完永不执行，需人工启用）；智能补货任务 102 为 `status=0` 正常、每日 06:00[码/档]。

### 4.6 空转 / 半成品功能清单（别被菜单骗了）

| 能力 | 现状 |
| --- | --- |
| `tb_policy.discount` 折扣策略 | 有页面、可挂设备，**无任何计算消费方**（价格结算在仓外） |
| `tb_job.alert_value` 补货警戒值 | 只有一个字段，无消费方 |
| `tb_inventory.is_alert` | 有列，代码未映射，无人维护 |

## 5. 角色、权限与数据隔离

### 5.1 两套账号体系（同一个库，互不相通）

| 维度 | 管理后台 | 运维移动端 |
| --- | --- | --- |
| 登录主体 | `sys_user`（用户名+密码） | `tb_emp`（手机号 + 短信验证码） |
| 令牌 | JWT HS512，身份存 Redis，30 分钟滑动续期 | JWT HS256，claims 直接带 userId，12 小时、无服务端吊销 |
| 权限模型 | URL 级 `@PreAuthorize` + 菜单 `perms` | **无权限模型**（登录即可用全部 9 个接口） |
| 数据范围 | `@DataScope` 仅系统域生效 | 仅"接单/完成/取消"校验归属人 |
| 关键事实 | `tb_emp` 与 `sys_user` **没有可关联字段**（`tb_emp.user_name` 是中文姓名） | 同一事实 |

> 直接后果：想按"区域"给智能体注入身份头（`X-Agent-Region`）时拿不到映射，网关只能传空（`DefaultAgentRegionResolver` 已 fail-soft 并写明启用条件）。

### 5.2 角色与职责

| 角色 | 编码 | 端 | 能做什么 |
| --- | --- | --- | --- |
| 超级管理员 | `sys_role admin` | 后台 | 全部（含系统管理） |
| 普通角色 | `sys_role common` | 后台 | 除个别系统菜单外几乎全部（授权过宽，审计已记） |
| 管理人员 | `tb_role 1001` | 后台/运维端 | 管理视角 |
| 运营人员 | `tb_role 1002` | 后台/运维端 | 补货、建单、处理补货工单；**补货 Agent 派单只找这个角色** |
| 维修人员 | `tb_role 1003` | 运维端 | 维修工单（登录时 `loginType=1`，返回 `isRepair=true`） |
| 合作商 | `loginType=2` | 合作商侧 | 点位分成与数据（本仓仅 `tb_partner` 档案与账号） |

> `tb_role` 的真实数据不在仓库（业务表 DDL 未入库），1001/1002/1003 是从代码常量反推的[码/档]。

### 5.3 权限点（按域）

- 后台：`manage:region|node|partner|emp|role|vm|vmType|channel|sku|skuClass|policy|order|inventory|inventoryLog|task|taskDetails|taskType|taskJob|report|agentAudit:*`，143 处 `@PreAuthorize`[码]。
- 智能体网关：**按路径形状判权**——补货读写 `manage:task:list` / `manage:task:add`；诊断起跑 `manage:vm:query`、派单确认 `manage:task:add`；白名单外 404（fail-closed）[码]。
- **权限点漂移**：补货菜单 SQL 造的是 `manage:restock:*`，网关判的是 `manage:task:*` → 按菜单授权不等于获得网关访问权[码/档]。
- `/manage/ai/**`（降级 AI 链路）**无权限注解**：任何登录用户都能触发外部 LLM 调用（成本+数据风险）[码]。

### 5.4 数据隔离现状：0

- 业务域 0 处 `@DataScope`、Mapper 里 0 处 `${params.dataScope}`；列表查询对区域是"传了才过滤"[码]。
- 唯一区域约束在**建单时**（员工区域 == 设备区域），只管"派给谁"，不管"谁能看"。
- 运维端 `search` 的 `userId` 由前端传，不传即全量；`/user-service/user/{id}` 任意登录者可查任意员工（含手机号）[码]。

### 5.5 前后端权限"对不上"的细节（体验层 403 的来源）

| 位置 | 前端按钮要求 | 后端实际要求 | 结果 |
| --- | --- | --- | --- |
| 设备 → "货道" | `manage:vm:edit` | `manage:channel:list` / `manage:channel:edit` | 只授 vm:edit 的角色点开即 403 |
| 补货工作台 | **页面与按钮零 `v-hasPermi`** | 网关判 `manage:task:*`（9002~9006 按钮权限虽已入库但未使用） | 按钮级授权形同虚设，全靠网关兜底 |
| 区域/点位/策略详情 | `manage:node:list` / `manage:vm:list` | 各自 `:query` | 权限点错配 |
| 设备 → "AI 诊断" | 无门控 | `/manage/ai/diagnose` **无 `@PreAuthorize`** | 任何登录用户可触发 LLM 调用 |
| 补货菜单 vs 网关 | 菜单 SQL 建 `manage:restock:*` | 网关判 `manage:task:list/add` | 按菜单授权 ≠ 获得网关访问权 |

## 6. 前端：页面地图与关键旅程

### 6.1 页面矩阵（18 个页面，含智能体 3 页）

| 分类 | 页面 | 关键操作 | 备注 |
| --- | --- | --- | --- |

| 设备资产 | 设备、设备型号、设备状态监控、货道（弹窗） | 建设备自动生成货道、绑商品、挂策略 | 设备状态页只读；列表 `JSON.parse` 无兜底 |
| 商品 | 商品、商品类型 | 价格元/分换算、图片 | 分类无层级 UI |
| 策略 | 策略管理 | 折扣档案、看已绑设备 | 无消费方 |
| 交易 | 订单管理 | 查询、详情（退款/取消**必崩**） | 只读为主 |
| 库存 | 库存预警 | 低库存/缺货/规则版补货建议（只读弹窗） | **硬编码路由**，所有登录用户可见 |
| 作业 | 运维工单、运营工单 | 建单、详情、取消、重开 | 工单配置路径错 |
| 报表 | AI 报表分析 | 生成日报/周报、看 AI 分析、排行 | 硬编码路由；长任务 60s |
| 智能体 | 补货工作台(9001)、决策审计(9007)、运行时间线(9010) | 确认/调整/跳过/暂停；审计回放；发起诊断/确认派单 | 三页都经 Java 网关，前端不直连 Python |
| 全局 | AI 助手侧边栏 | 四场景对话、SSE 流式、降级横幅、停止生成 | 无权限点（登录即可用） |

### 6.2 关键旅程（操作 → 系统行为）

**A. 日常补货（当前主流路径）**
工作台看当日建议（统计卡：待处理/紧急/建议总量）→ 展开"依据"（每货道的现库存/容量/建议量/预计撑几天/优先级/理由）→ 异常项"调整"（改量或换窗口/服务水平，原因必填）→ "确认建单"（串行，失败提示"状态未变更，可重试"）→ 工单进入运维端 → 工程师接单→完成→货道库存累加。

**B. 故障处置**
设备管理/时间线页发起诊断 → 看证据条数、未知项、置信度（强调"不是概率"）→ 派单提案（接单人/优先级/选人依据）→ 确认建单（需 `manage:task:add`）或驳回（原因必填）→ 运维端维修 → 完成（无回执）。

**C. 审计追溯**
决策审计页按场景/结果/requestId 过滤 → 详情回放（输入上下文/LLM 输出，回复正文还原换行但不改写）→ "链路"看同一 requestId 下的完整时序（状态机放行→回调建单→回写状态）。

### 6.3 前端侧的坑（会直接影响业务可用性）

- **点下去就坏**：订单详情"退款/取消"调用未定义函数（后端 `PUT /manage/order/{refund|cancel}/{id}` 其实就绪）；"工单配置"跳 `/manage/job` 而后端是 `/manage/taskJob`；点位导入模板前端 GET、后端 POST → 405。
- **有接口没入口**：库存初始化、库存流水、库存预警明细、角色库维护、AI 运营建议、点位选址建议。
- **硬编码路由**：库存页与报表页写进 `constantRoutes` 又被拼进侧边栏 → 任何登录角色都能看到，绕过 `sys_menu` 授权（违反 AGENTS §2.2，安全审计已记）。
- **共享状态串味**：策略详情就地改写共享查询参数，影响后续列表；设备页两个弹窗共用一个 `ref`，策略保存依赖弹窗打开顺序。
- **数据健壮性**：设备状态列表列直接 `JSON.parse(runningStatus)`，非法 JSON 会让整表渲染抛错（详情处反而有 try/catch）。
- **口径问题**：报表统计卡取"历史列表第一条"而不是"最新日报/周报"，切日/周报卡片不变；首页大屏为静态假数据。

## 7. 智能体层（旁路增值能力）

### 7.1 四条不可违背的红线

1. **业务事实唯一所有者是 Java**：写操作只能回调 Java REST（`POST /agent/callback/task`），复用建单校验链；禁止直连写业务表。
2. **读走 MySQL 只读账号 + 表白名单**（`tb_*` 仅 SELECT）；`agent_*` 自有表可读写但无 DELETE/DDL。
3. **鉴权不裸奔**：前端只经 Java 网关 `/agent/**`；Python 不解析 JWT，只信任网关注入头；服务间密钥与用户 JWT 是两套体系。
4. **写操作 human-in-the-loop**：首期所有建单类写操作必须人工确认；LLM 输出视为不可信输入（结构解析 + 范围夹取）。

另有一条工程底线：`agent.enabled=false` 时 Python 不可用，主业务零影响（另有独立降级接口 `/manage/ai/**` 走单轮 LLM，**代码里没有自动切换**，需前端/调用方显式指定）。

### 7.2 三个 Agent 对照

| 维度 | 补货 Agent | 故障诊断 Agent | 运营分析 Copilot（对话 scene=4） |
| --- | --- | --- | --- |
| 目标 | 每天生成"哪台设备哪个货道补几件" | 单设备取证→诊断→派单提案→建维修单 | 分析问答 |
| 触发 | quartz 06:00；工作台页面 | 时间线页发起（默认 24h 窗口） | AI 助手抽屉 SSE |
| 流程 | analyze→calibrate→await_confirmation(interrupt)→apply_decisions→create_tasks | supervisor→diagnostician→supervisor→dispatcher→supervisor | focus→respond（工具轮次≤3/轮） |
| 写操作 | 补货工单（type=2） | 维修工单（type=3） | **无** |
| 确认方式 | 页面 API 状态机（非图 resume） | 两阶段 DB 状态机（waiting_confirm→running→done） | 不涉及 |
| 状态 | Phase 1 主体 ✅ | M3 ✅（M4 审核官未做） | **空能力**（3-1~3-5 已砍） |

### 7.3 补货 Agent：状态机与幂等

```
1 建议 ──调整──► 2 已调整 ──确认──► 4 已建单 ──► 5 已复盘（终态）
   │                 │
   └──跳过──► 3 已跳过 ◄┘            4 ──► 6 待指派（无匹配接单人）
   3 ──恢复建议（仅当天、原因必填）──► 1
   1/2/6 ──CAS 抢占──► 7 建单中 ──► 4
```

幂等四层：状态机 `already_ordered` 判定 → 唯一键 `(vm_id, plan_date)` → **CAS 抢占 7-建单中**（抢不到 409）→ Java 侧在途工单防重。建单失败计划状态不变、返回 502、原样再点即重试。

接单人分配：同区域 `role_code=1002` 启用人员，按当日负载最低，平手按 `emp_id` 升序；**没有候选就"待指派"，绝不跨区域凑人**。

### 7.4 故障诊断 Agent：证据纪律与两阶段确认

- 路由用**代码**（三个角色可枚举、零 token），LLM 只在角色内解释。
- **证据回溯硬校验**：每条证据必须能指回本轮某次工具调用的返回行（订单号/日志 id/工单集合命中且行数一致），指不回去的丢弃；全丢则 `cannotConclude=true`、置信度归零、**禁止派单**。
- 诊断结论**刻意不含病因**：平台没有结构化故障原因知识（维修单无字段），给"病因排序"等于编领域知识。
- 确认是跨进程 HTTP 动作：DB 状态机 + CAS + 建单前回查已建单结果 → 重复确认返回同一张工单；业务拒绝/传输失败回退 `waiting_confirm` 可重试，人工驳回需填原因且不建单。

### 7.5 对话助手：四个场景与"能力诚实"

- 场景 1 通用 / 4 运营分析：**不挂工具**，提示词要求如实说"本场景查不了"，引导去报表页或切场景。
- 场景 2 补货：4 个只读工具（补货清单/设备库存/在途工单/近期销量）。
- 场景 3 诊断：6 个工具（设备消歧/异常检测/历史维修单/结构化诊断/库存/在途）。
- 工具轮次上限 3，且**按本轮计**（曾因按会话累计导致第三句起静默失去查询能力）；工具异常转错误消息不回显原文。
- 数字保真：`done` 帧带本轮数据口径 + 数字出处核对，模型改写工具结果时前端单独展示工具事实（模型行为缺陷以 `KNOWN-DEFECT` 单独计数，不算通过也不算失败）。

### 7.6 与 Java 的契约与降级

| 项 | 事实 |
| --- | --- |
| 网关 | 显式路径白名单 + 路径形状正则 + 权限点；白名单外 404；SSE 逐块 flush 不缓冲 |
| 回调 | `/agent/callback/task`：服务间密钥（常量时间比较）+ 路径白名单 + 限流；4 类拒绝（未配密钥 503 / 密钥错 401 / 非白名单 404 / 业务校验拒绝 200+code500 原文回传） |
| 降级 | `agent.enabled=false`：非 SSE→503 信封，SSE→error+done 帧；上游 4xx 原样透传 |
| 鉴权 | 两套：用户 JWT（网关注入 `X-Agent-User/Roles/Region`，剥客户端同名头）与服务间 `X-Agent-Secret` |
| 定时 | quartz job 102：`agent.enabled=false` 算跳过不算失败、被暂停返回 skipped 不重试、4xx 不重试、5xx 重试、最终失败抛异常进 `sys_job_log` |

### 7.7 能力边界（诚实清单）

- 未做：M4 诊断审核官、M5 效果评估、Copilot/NL2SQL/分析模板（已砍）、知识库向量检索（维修单数据不达标，降级规则库）。
- 外部阻塞：真实数据导出（FIX-6）、容量权威源（FIX-5）、维修单结构化字段（FIX-22）、凭据轮换（FIX-7）。
- 内部风险：生产的人工确认**不走图 resume**（走 `RestockService._execute`），图内后半段主要被测试覆盖 → 决策执行逻辑存在两份，改语义要同时改；`agent_conversation` 有表无写入方；LLM 校准 token 未计入成本报表；角色/区域头不参与鉴权。

### 9.3 建议的下一步（按"影响 ÷ 成本"排序）

1. **先做结构复核**（0.5 天）：对 `tb_order`/`tb_inventory_log`/`tb_inventory` 跑 `SHOW COLUMNS`/`SHOW INDEX`，确认代码与库是否真的不一致——这决定好几个接口现在是不是坏的。
2. **定容量权威源并统一读写口径**（决策 1 天 + 改代码）：补货写回同时更新 `tb_inventory` 与流水，或明确废弃一侧；否则预警永远失真。

6. **权限收口**（1 天）：`/manage/ai/**` 加权限点、补货菜单与网关权限点对齐、决定是否引入区域数据权限。
7. **维修单结构化字段 + 运维端作业回执**（2~3 天）：这是诊断 Agent 从"证据助手"变成"经验助手"的前置。
