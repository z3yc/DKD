### 0.1 与梳理报告不一致处（代码/配置核实后修正）

1. **P0-3 比报告描述更严重**：报告称「三份锁共存、package-lock 早于 package.json」。实测：
   - `dkd-vue/.gitignore:22` **忽略了 `package-lock.json`**，仓库实际跟踪的是 `bun.lock` 与 `pnpm-lock.yaml`；
   - 因此 `dkd-vue/Dockerfile:13` 的 `COPY package.json package-lock.json` 在**干净 clone / CI / docker build**
     下直接失败（文件不存在）——这不只是"漂移"，而是构建链路断的；
   - 本地那份锁文件也真的过期：根依赖缺 `dompurify`、`marked`（`npm ci` 会以"不同步"拒绝）。
2. **P0-5 的缺项是明确的**：`dkd-app/src/main/resources/application-dev.yml:18` 为
   `${DKD_APP_JWT_SECRET}`（启动校验 ≥32 字节、fail-closed），而 `docker-compose.yml` 的 dkd-app 段
   原先只注入了 datasource/redis 两组变量；`.env.deploy.example` 也没有该项。
3. **P0-4 的边界**：`logback.xml:4` 写 `/home/ruoyi/logs`；compose 原挂 `admin_logs:/app/logs`；
   `dkd-parent/Dockerfile` 原 `mkdir -p /app/logs`。另：**dkd-app 没有任何文件日志配置**（只有
   MyBatis stdout），它的 `app_logs:/app/logs` 目前是空卷——本轮不动，登记为观察项（改了等于新增日志能力）。
4. **P0-1 复核结论**：`InventoryServiceImpl.updateInventoryQuantity(:357)` 全仓**零调用方**；
   `OrderController.add(:79)` → `OrderServiceImpl.insertOrder(:58)` 只做 `orderMapper.insertOrder`；
   库存变更入口 `applyInventoryChange` 仅被 `InventoryServiceImpl` 自己调用（后台编辑 :236、数量接口 :384）。
   即"下单不扣库存"成立，**但这是设计缺口还是待接线，需要负责人拍板**（§3.1）。
5. **P0-6 复核结论**：`dkd-app TaskServiceImpl.accept(:136)`/`cancel(:158)` 均无 `@Transactional`，
   且都是 `getById` → 判断 → `updateById` 的 check-then-act（同文件只有 `complete(:197)` 有事务）。
6. **P0-7 复核结论**：`dkd-agent/app/tools/read_tools.py` 每个查询都用 `tables=(...)` 字面量调用
   `assert_table_allowed`；SQL 文本本身不参与校验，漏传/写错表名即绕过（该文件头注释已自认此限制）。

4. P0-1/P0-6/P0-7 属业务语义或安全边界变更，**方案先行**，未经拍板不落代码。

## 3. 待决策 / 待设计（本轮不落代码）

### 3.1 P0-1 交易链路断链 —— 两个选项

| 选项 | 做法 | 代价/风险 | 适用前提 |
| --- | --- | --- | --- |
| **A. 接线** | 在 `OrderController.add` / 支付回调里，按货道扣减库存并写 `tb_inventory_log`（复用 `applyInventoryChange`），事务内完成；出货失败走回补 | 触碰主交易链路；需要幂等键（订单号）防重复扣减；并发下需行锁 | 业务确认"下单即锁库存" |
| **B. 确认废弃** | 删除/标注 `updateInventoryQuantity` 为废弃，并在 `OrderController` 注释显式写明"本平台下单不扣库存，库存事实由补货/出货回写" | 无运行时风险；但需确认没有其它系统（如外部支付）依赖该语义 | 业务确认库存只由补货/设备回传驱动 |

**建议**：先按 B 做"**显式声明**"（成本最低、消除误导），A 作为独立需求排期。无论选哪个，
都要在 `docs/DKD业务规范-清晰版.md` 的库存口径里写死，避免后续再被当成 bug。

### 3.2 P0-6 `accept`/`cancel` 并发

- 方案一（首选）：把 `getById` + 判断 + `updateById` 改为**条件 UPDATE**
  （`UPDATE tb_task SET task_status=? WHERE task_id=? AND task_status=? AND user_id=?`），
  以影响行数 0 判定"非预期状态/无权限"，避免读-改-写窗口。
- 方案二：`tb_task` 加 `version` 列 + MyBatis-Plus 乐观锁插件（需要 DDL，走 §7.4 评审）。
- 验收：并发两请求只有一条成功（需可重复的并发测试，不能用"看代码觉得对"代替）。

### 3.3 P0-7 表白名单强制校验

- 方案：新增 `extract_tables(sql)`（用 `sqlglot` 或轻量正则 + 关键字白名单），在 `_fetch_all` 内
  **从 SQL 解析表名**并与 `tables` 参数交叉校验；任一不在白名单 → 拒绝（fail-closed）。
- 与现有 `assert_table_allowed` 的关系：保留后者做"声明表"校验，新增解析做"实际表"校验，
  两者不一致即报错（**不一致本身就是 bug 信号**，不要静默取其一）。
- 验收：拒绝路径必测（子查询/别名/大小写/反引号/逗号分隔多表）；真实工具用例全过。

### 5.3 与计划的偏差

1. **P0-4 与 P0-5 合成了一个提交**：两处改动同处 `docker-compose.yml`，拆开会让任一个提交单独回滚时
   把另一项一起带走（且 compose 无法只索引半个文件）。已在提交正文分两段写清，属 §5.2 允许的
   「同一文件、同一问题域」合并（先例：P2 的 `8c32d57` 合并 P2-20+P2-21）。
2. **P0-3 的实际范围比计划大**：除了"重新生成锁文件"，还必须把 `package-lock.json` 从 `.gitignore`
   里移出并 `git add`——否则 CI/镜像里根本没有这份文件（§0.1 已记录）。
3. **执行方式偏差**：本机受 Windows 完整性级别限制（低完整性令牌写不了中等完整性的既有文件，
   `.git` 与 `package-lock.json` 都命中），因此文件改动走编辑工具、`npm` 与 `git` 走逐次审批命令；
   这是环境限制，不是流程变更。
