## 三、知识库：分三层，别用 RAG 查数字

**红线认知**：设备/库存/销量/工单这类**结构化事实一律走只读工具直查**（精确、可回归、有口径）；把取数塞进 RAG 是精度灾难。RAG 只负责回答"为什么、怎么办"。

| 层 | 内容 | 现状 | 建议 |
| --- | --- | --- | --- |
| **L1 结构化事实** | 设备/货道/库存/销量/工单 | 已有只读工具直查（`tools/read_tools.py`），**不要动** | 保持直查 |
| **L2 文档语料** | 厂商手册、故障码表、运营 SOP、口径说明 | **完全没有** | 先做这层：上传 → 切片 → 向量库 → 诊断/助手在结论中引用 → **引用强制校验**（断言必须带相似度 ≥ 阈值的片段，否则回退为"仅列证据"模板，防止知识库变成新的幻觉来源） |
| **L3 案例库** | 历史维修工单结构化案例 | 被 FIX-22 卡住（5 条、描述 4 个字、无结构化字段） | 等业务补字段 / 拿到厂商故障码表后再启；页面上如实显示"未启用 · 数据未达标" |

配套能力：语料管理（上传/切片/重建索引/启停）、**检索测试**（只读召回，调阈值用）、命中归因（近 7 日命中/采纳次数）。

## 四、MCP 工具接入：能接，但必须先过四道闸

当前 MCP 在仓库中**零基础**（全仓无 mcp 字样）。接入的收益是工具可插拔、不用改 Python 代码；风险是外部进程/网络会绕过 `sql_guard`、可能带写操作、可能出网泄数据。**必须先有工具中心（#6）**，MCP 与本地工具共用同一张注册表、同一开关、同一份调用日志。

接入校验（任一不过即拒绝登记）：
1. 工具 schema 可解析、与现有工具不重名；
2. **`read_only=1` 才允许接入**——写操作一律拒绝，写仍只能回调 Java（`create_work_order` 被拒是示例）；
3. 出网地址在白名单内；
4. 单次调用超时 ≤ 5s、返回 ≤ 200 行（对齐现有读护栏 `read_query_timeout_s=5` / `read_row_limit=2000`）；
5. 密钥只存环境变量名（`api_key_env`），永不入库、永不回显；
6. 返回内容进留痕前摘要化（复用 `params_digest`，不落原文）；
7. 启动探测：库里登记的工具必须能在 MCP 侧找到，找不到就拒绝启动（与现有"配置了不存在的工具就拒绝启动"同一原则）。

## 五、分期建议

| 阶段 | 内容 | 依赖 |
| --- | --- | --- |
| 第 1 期 | #1 配置台 + #3 降级可感知 + #4 执行日志 + #5 会话列表 | 已分别有方案/原型，可并行开工 |
| 第 2 期 | #2 效果度量 + #6 工具中心 + #10 成本看板 + #9 待办中心 | 依赖 #1 |
| 第 3 期 | #7 模型档案 + #8 Prompt 评测 + **MCP（本需求）** + **知识库 L2（本需求）** | MCP/知识库依赖 #6 工具注册表 |
| 第 4 期 | #11 知识库 L3（等数据）+ #12 反馈 + #14 移动端 | 依赖数据/业务输入 |

> MCP 与知识库都排在第 3 期不是它们不重要，而是**它们的安全边界依赖工具注册表与留痕先就位**——顺序反了会先埋雷。
