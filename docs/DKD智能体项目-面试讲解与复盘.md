## 一、分层话术（先练这个）

### 30 秒版（自我介绍里的一行）

> 我在帝可得售货机平台主导了一个「业务系统 + LLM 智能体」的旁路改造：把原来只能单轮问答的 AI，升级成能查库存/订单/工单、能生成补货计划、能建工单的智能体服务。核心难点不是调模型，而是**在不破坏 Java 单体事务与校验链的前提下做读写分离**，以及**让 AI 的写操作可审计、可降级、可回滚**。

### 3 分钟版（项目结构）

1. **业务背景**：RuoYi 3.8.7 改造的售货机运营平台。数据模型是四级结构：区域 → 点位 → 售货机 → 货道；核心闭环是「投放上架 → 库存 → 下单扣减 → 库存预警 → 补货建议 → 人工建工单 → 运维端接单 → 现场补货 → 库存回写」。
2. **问题**：现有 AI 是 `com.dkd.common.ai` 里的单轮 prompt 拼接——prompt 硬编码在 switch-case 里，只取设备 5 个静态字段，输出 100 字文本，没有上下文、没有工具调用、没有结构化输出、没有留痕。
3. **方案**：新增独立 Python 智能体服务（dkd-agent），旁路集成。**读走 MySQL 只读账号 + 表白名单；写一律回调 Java REST**，复用 `TaskServiceImpl.insertTaskDto` 的事务与校验链；前端统一经 Java 网关转发 JWT，Python 不解析 JWT。
4. **场景**：P0 智能补货（统计基线 + LLM 校准 + 人工确认 + 批量建单 + 7 日复盘）、P0 设备故障诊断（多轮问诊 + 实体消歧 + 维修工单卡片）、P1 运营分析 Copilot（预置模板 + 受控 NL2SQL）。
5. **工程化**（这块最能体现深度）：`agent.enabled` 一键降级、人机分级写操作、决策留痕表、敏感信息脱敏、token 成本计量与熔断、request_id 全链路、SSE 断点续传、幂等靠 DB 唯一键兜底。

### 10 分钟版（加架构决策与踩坑）

在 3 分钟版基础上补：**技术选型的否决理由**（为什么不用 LangChain4j、不用 MQ、不上 Milvus）+ **三个真实踩坑**（见 §五，挑 Redis 3.2 无模块、表名白名单错误、审计旁路打断对话这三个，故事性最强）。

## 二、业务背景与问题定义

### 2.1 系统现状（面试时要能画出来）

| 子系统 | 技术栈 | 角色 |
| --- | --- | --- |
| dkd-parent | Spring Boot 2.5.15 / **Java 8** / MyBatis / Druid / Redis / Maven 多模块 | 管理后台，**业务事实唯一所有者**，:8080 |
| dkd-app | Spring Boot / MyBatis-Plus / JWT | 运维移动端（补货/维修作业），与后台**共用 dkd 库** |
| dkd-vue | Vue 3.4 / Element Plus / Vite | 管理前端 |
| **dkd-agent（我新增）** | Python 3.11 / FastAPI / LangGraph / SQLAlchemy(async) | 智能体服务，:8090，旁路 |

业务表全部 `tb_` 前缀：`tb_inventory`（货道级库存：current_stock/min_stock/max_stock/last_supply_time）、`tb_inventory_log`、`tb_order`、`tb_task` + `tb_task_details`（工单主/明细）、`tb_channel`、`tb_sku`、`tb_vending_machine`、`tb_node`、`tb_region`、`tb_emp`、`tb_job` 等。

**规则版补货建议（现状基线）**：`InventoryServiceImpl` 里很朴素——现库存达容量 85% 不补；否则补到 85%，且不低于「最小预警值 ×2」；优先级 1~4 由「是否缺货 / 是否低于预警值 50%」决定。**这是智能体的对照基线**，也是我在面试里讲"为什么值得做"的抓手：规则版不看销量趋势、不看点位差异、不看节假日前置，纯阈值。

### 2.2 现有 AI 的六条局限（问题定义的依据）

| 局限 | 具体表现 | 智能体的解法 |
| --- | --- | --- |
| 无上下文 | 每次单轮直答 | LangGraph 多轮 + checkpointer |
| 无工具调用 | LLM 拿到什么算什么 | Function calling 工具层 |
| 数据维度单薄 | 只取设备 5 个静态字段 | 自主编排库存+订单+工单+故障历史 |
| 决策不可执行 | 只输出 100 字文本 | 结构化输出 → 一键建单 |
| 无结构化输出 | 前端无法渲染成可操作列表 | Pydantic 约束的补货清单 JSON |
| 无审计可观测 | 只有 HTTP 响应日志 | 决策留痕表 + trace + 成本计量 |

### 2.3 量化目标（面试官爱问"怎么衡量收益"）

缺货率 ↓30%+；补货排单人工耗时 ↓60%+；故障响应时长 ↓50%+；运营取数从小时级 → 分钟级；写操作留痕率 0 → 100%。
**口径要说清**：与规则版**并行双跑 3 周**做对照，而不是上线就看数字。

## 三、架构方案与决策链（面试重点）

### 3.1 一张图讲清

```
Vue3 ──同源 JWT──▶ dkd-parent:8080 【业务事实所有者】
                    ├─ AgentGatewayController  /agent/** 反代 + 注入 X-Agent-User 头
                    ├─ AgentCallbackController Python 回调（服务间密钥+白名单+限流）
                    └─ 复用 /manage/task 等现有 REST
                        ▲ HTTP 写回调          │ MySQL 只读直连（白名单）
                        │                      ▼
dkd-quartz 06:00 ──▶ dkd-agent:8090 【决策层/编排层】
                     FastAPI + LangGraph(Supervisor) + 工具层 + SQLite checkpointer
```

### 3.2 五个关键决策（每个都要能说出**否决了什么**）

| 决策 | 采纳 | 否决的备选与理由 |
| --- | --- | --- |
| 智能体放哪 | **独立 Python 进程旁路** | ❌ JVM 内嵌（Spring AI / LangChain4j）：项目锁死 **Java 8**，主流框架要 17+；升级 JDK 会牵动 RuoYi 全家桶，风险远大于收益 |
| 数据怎么读 | **读直连 MySQL 只读账号 + 表白名单** | ❌ 全走 REST：补货要聚合近 30 天 Order × Inventory × Task，REST 会导致 N 次调用 + Java 侧接口膨胀；✅ 单实体实时查询仍走 REST 以复用权限语义 |
| 数据怎么写 | **一律回调 Java REST** | ❌ Python 直连写库：绕过事务、工单防重、员工区域校验、操作日志 → 数据一致性风险，是**红线** |
| 怎么触发 | dkd-quartz 定时 HTTP 调 Python | ❌ MQ/Binlog CDC：当前无 MQ 基础设施，单体规模不需要；❌ Redis Stream：本机 Redis 3.2 不支持（见 §五坑 1） |
| 写操作要不要自动 | **首期全部人工确认**（human-in-the-loop） | ❌ 自动建单：`insertTaskDto` 有硬校验，补货涉及实物流转成本；放量需 Phase 3 复盘数据支撑 |

### 3.3 读写分离的落地细节（这是我最想被问的部分）

**两级授权账号**（这是本项目最容易被忽视、也最能体现工程判断的一点）：

| 对象 | 权限 | 为什么 |
| --- | --- | --- |
| 业务表 `tb_*`（白名单内） | 仅 `SELECT` | 业务事实只归 Java |
| 自有表 `agent_*`（会话/留痕/计划） | `SELECT/INSERT/UPDATE` | **它们不是业务事实**，是 Agent 自己的审计与状态数据；若强制也走 Java 回调，等于为了"纯洁"把审计链拉长一倍 |
| 其它 | 无 DELETE（软删除）、无 DDL、禁跨库 | 本机 MySQL 上还挂着 8 个其他项目库 |

> 这个边界我写进了 `AGENTS.md §7.3`：原规范只写"只读账号"，照做会导致留痕写不进去——**规范本身有缺口，实施时才暴露**。

**幂等设计**（补货建单）：
- DB 层：`agent_restock_plan` 上 `UNIQUE KEY (vm_id, plan_date)` —— 同设备同日只有一份计划；06:00 任务重跑走 `ON DUPLICATE KEY UPDATE` 且仅「建议/已调整」可覆盖。
- 应用层：状态机 `1-建议 → 2-已调整/3-已跳过/4-已建单/5-已复盘/6-待指派`，卡口合法迁移。
- 业务层：建单前先查同设备在途补货工单。

### 3.4 为什么必须做 human-in-the-loop（面试高频追问）

`TaskServiceImpl.insertTaskDto` 的真实校验链（我逐行读过）：
1. 售货机存在 → 2. 设备状态与工单类型一致 → 3. **同设备+同工单类型+进行中工单防重（设备级）** → 4. 员工存在 → 5. **`emp.regionId == vm.regionId`** → 6. 建单 + 补货明细。
第 3 条决定了**只能按设备整单创建、明细含多货道**，无法按货道拆单；第 5 条决定了 Agent 必须**按设备区域自动选接单人**，并处理"无可用接单人 → 待指派"。这两条是 M2 验收的隐形拦路虎，方案第一版完全没覆盖——这就是"读过代码"和"凭印象设计"的区别。

## 四、技术选型：为什么是这些栈

### 4.1 选型总表

| 组件 | 选择 | 关键理由 | 否决的备选 |
| --- | --- | --- | --- |
| 服务框架 | **FastAPI + Uvicorn** | 原生 async、SSE、Pydantic 一体化 | Flask（无 async/契约弱）、Django（重，无必要） |
| 编排框架 | **LangGraph（Supervisor）** | 有状态多 Agent、`interrupt()` 原生 HITL、checkpointer、`astream` | 纯 LangChain AgentExecutor（多轮中断恢复弱）、自研状态机（等于重写一遍）、Dify/Coze（见 §4.4） |
| LLM 接入 | **langchain-openai → DeepSeek** | 与现有 `ai.api-url` 同账号，零迁移；OpenAI 兼容 → 可切通义千问，只改配置 | 直接写 httpx（丢结构化/工具/流式封装）、各家原生 SDK（换供应商要改代码） |
| 结构化输出 | **Pydantic** | 补货清单/诊断结论强约束；字段对齐现有 `RestockSuggestionDto`，前端可复用渲染 | 让 LLM 直接吐自然语言（前端无法渲染为可操作列表） |
| 会话持久化 | **SQLite `AsyncSqliteSaver`** | 单机部署形态匹配、零新增基础设施、文件可备份 | Redis（本机 3.2 不可用）、Postgres（当期无 PG，留作演进） |
| 数据访问 | **SQLAlchemy 2.x async + aiomysql** | ORM/Core 双模式，能写带白名单校验的聚合查询 | 裸 pymysql（无类型/连接池）、同步驱动（阻塞 event loop） |
| 依赖管理 | **uv** | 一条命令装好 Python 3.11（方案要求 3.11+ 而本机只有 3.10）、`uv.lock` 精确锁定 | 系统 venv + requirements.txt（锁不住传递依赖；本机 PATH 有 4 个 Python，易踩错版本） |
| 观测 | 结构化 JSON 日志 + **决策留痕表** + LangSmith（可选） | 留痕是审计要求，不是可选项；LangSmith 只做开发期 trace | 只用 logging（无法回答"AI 为什么这么建单"） |
| 部署 | 独立 venv + uvicorn（systemd/Windows 服务） | 与现有运维形态一致 | Docker/K8s（当期 1 台服务器、2~3 人团队，只增加复杂度） |

### 4.2 会话持久化这条线要单独讲（演进思路）

```
Redis checkpointer（方案 V1.0 的初选）
   ↓ 实测不可用：本机 Redis 3.2.100 无 MODULE / 无 RedisJSON → 见 §五坑 1
SQLite AsyncSqliteSaver（当前）
   ↓ 触发条件：出现多实例部署 / 需跨机共享会话 / 需要 PG 做向量检索
Postgres saver（landing zone）
   ↓ 触发条件：千万级向量 + 高并发 + 多租户
专用向量库（Milvus/Qdrant）—— 见 §九
```

**这条演进线本身就是面试亮点**：不追求"一步到位的架构"，而是**给出迁移触发条件**，并接受"当前形态就是最优解"。

### 4.3 LangGraph 的两个反直觉点（值得主动讲）

1. **开放版本区间是陷阱**：方案原写 `langgraph >= 0.2`，实际解析到 **1.2.11**（配 `langgraph-checkpoint 4.2.0`）。`interrupt` 的字段在 0.6 被移除、1.0 又改过一轮；checkpointer 与主版本强绑定。→ 必须 `uv.lock` **锁精确三元组**。
2. **图代码变更即不可回滚的兼容性变更**：LangGraph 会把**最新图代码立即应用到所有历史 checkpoint**。所以 `state` 字段一旦上线就不能删改，只能"新增字段 + 默认值"。→ 我把这条写进了方案和代码 docstring，并在 Phase 0 就冻结 `ChatState`。

### 4.4 为什么不用 Dify / Coze / 百炼这类平台（大概率会问）

- 原型阶段它们更快；但本项目的核心是**写操作闭环**，必须复用 Java 的 `insertTaskDto` 事务与校验链、纳入现有 JWT 权限体系、满足留痕/脱敏/回调鉴权/降级开关这些**硬性要求**。
- 平台的写回路是"平台自己的工具/HTTP 节点"，很难嵌入**服务间密钥 + 路径白名单 + 限流 + 决策留痕**的完整链条；排障时也拿不到足够的内核控制（比如 checkpointer 语义、中断恢复）。
- 结论：平台适合做 PoC 与低耦合场景（比如纯问答 Copilot）；**与核心业务强耦合的写操作闭环，自研编排更可控**。

## 五、踩过的坑（真实复盘）

> 每条格式：**现象 → 定位过程 → 根因 → 修复 → 可迁移教训**。面试时挑 2~3 条讲，其余当"储备"。

### 坑 1（最有故事性）Redis 3.2 不支持模块，checkpointer 直接换方案

- **现象**：方案 V1.0 写的是 `langgraph-checkpoint-redis` 复用现有 Redis；准备开工时我先去核基础设施，发现项目根目录外有个 `E:\Redis-x64-3.2.100`。
- **定位**：`redis-server --version` → **3.2.100**（Microsoft 2016-07 移植版）；查配置 `appendonly no`、无 `maxmemory`；关键结论是 **3.2 没有 MODULE 系统** ⇒ 不可能有 RedisJSON/RediSearch，而 `langgraph-checkpoint-redis` 依赖它们（需 Redis 8.0+ 内置或 Redis Stack）。顺带发现内核 < 5.0 ⇒ **无 Streams**，方案里"预留 Redis Stream 升级路径"也不成立。
- **根因**：选型基于"项目有 Redis"这个**印象**，没有核版本与能力边界。
- **修复**：改 **SQLite `AsyncSqliteSaver`**（单机部署形态匹配、零新增基础设施），并写清迁移触发条件；同时把 Redis 版本登记为技术债。
- **教训**：**"有中间件"≠"这个中间件能满足这个用法"**。选型前先跑一条探测命令（版本 / MODULE LIST / 关键配置），成本 1 分钟，收益是整个方案不返工。

### 坑 2 表白名单全错：漏了 `tb_` 前缀、还漏了必需的 4 张表

- **现象**：方案与排期里的白名单写成了 `inventory/order/task/channel/sku/vending_machine/node/region`。
- **定位**：翻 `dkd-manage/src/main/resources/mapper/manage/*.xml`，实际表全部是 `tb_` 前缀（`tb_inventory`/`tb_order`/`tb_task`…），且白名单**漏了诊断与建单必需的** `tb_inventory_log`（库存变动异常检测）、`tb_task_details`（工单明细）、`tb_emp`（接单人区域匹配）、`tb_channel`（货道档案）。另外 `order` 是 **MySQL 保留字**——按原文档写白名单，SQL 还得加反引号。
- **根因**：文档作者（含我审阅前）"按 RuoYi 通用印象"猜表名，没核代码。
- **修复**：白名单改为真实表名并补齐；在 `db.assert_table_allowed()` 里加了"无 `tb_` 前缀一律拒绝"的护栏 + 8 条拒绝路径测试（写业务表/读非白名单/读系统表/跨库/DELETE/DDL）。
- **教训**：**表名、字段名、枚举码值这类事实，永远不要从文档/记忆里取**。我后来的做法是：所有事实性结论都必须带 `file:line` 证据，写进方案 §十"证据索引"。

### 坑 3 审计是"旁路"，但它一挂整个对话就断了

- **现象**：端到端联调时 `/agent/chat` 返回 **HTTP 200 但 SSE 体为空**。
- **定位**：看服务日志尾部，发现 `OperationalError: Unknown column 'agent_message.user_id'`；再往上看，异常是从限额检查里抛出来的，直接把 SSE 生成器打断了。
- **根因**（两个叠加）：
  1. 我在 `agent_message` 建表时**没设计 `user_id` 列** → 按用户聚合 token 的限额查询直接失败（写计量代码时才发现，属于典型的"需求驱动表结构")；
  2. 更本质的是**分层错误**：审计/计量是旁路能力，它的基础设施故障**不应该把用户对话打断**，但代码里 session 获取 + 查询写在了 try 外面。
- **修复**：① 补 `user_id` 列 + 索引 + 增量 ALTER 脚本；② 把限额与留痕整段包进 `except SQLAlchemyError` → **记录 WARN 后降级放行**；③ 但 `QuotaExceededError` 属于业务规则，必须明确返回 **429**，绝不静默放行；④ 补 3 个降级专项测试（审计库故障、写失败、限额命中）。
- **教训**：
  - 分清 **基础设施故障（降级放行）** 与 **业务规则命中（明确拒绝）**，两者的错误处理语义完全不同；
  - "旁路能力"必须在**调用点**做异常边界，不能指望被调函数自己吞干净；
  - 顺带得到一个判据：**编码错误（非 SQLAlchemyError）要让它暴露**，否则会被静默吞成隐性 bug。

### 坑 4 索引失效的现成写法：`date_format()` 包裹索引列

- **现象**：准备写"近 30 天销量聚合"工具时，参考现有 `OrderMapper.xml` 的时间过滤写法。
- **定位**：现有写法是 `AND date_format(create_time,'%y%m%d') >= date_format(#{params.beginTime},'%y%m%d')` —— **函数包裹列 ⇒ 索引失效**，30 天聚合会退化成全表扫描。
- **根因**：RuoYi 模板沿用的写法在"后台按日期筛选"小数据量下无感，但放到 Agent 的批量聚合格局就危险；而且项目**没有从库**（`slave.enabled: false`），聚合会和业务抢同一台 MySQL。
- **修复**：工具层强制**范围比较** `create_time >= ? AND create_time < ?`，并加"按 vm 分批 + 查询超时熔断"；把 `EXPLAIN` 结果留档；在 `AGENTS.md §10 CR 清单` 里加了"禁止 `date_format()` 包裹索引列"这条。
- **教训**：**"照抄现成写法"是性能事故的常见来源**。复用业务代码前要问一句：它的数据量前提和我一样吗？

### 坑 5 计划表排期算错：假期 + 兼职投入导致 Phase 0 超载 3.3 倍

- **现象**：评审排期计划时觉得"10 周有点紧"，一算发现不是紧，是**不可能**。
- **定位**：① 把法定假期按周对齐——2026 年中秋 9/25~27、国庆 10/1~7，Phase 0 声称 10 个工作日实际只有 **7 个**（且它把关键验收排在了 10/02，正好是国庆第 2 天）；② 按角色核算工作量——Phase 0 的 Java 侧 7 人日，而 Java 工程师只有 30% 投入，需要约 **23 个工作日**，排期只给 7 天，**超载 3.3 倍**。
- **根因**：排期按"自然周 × 5"估算，没有按「角色可用工时」折算，也没做假期扣减。
- **修复**：总量重排为 **14 周（64 个实际可用工日）**；Phase 0 拉长 + Java 侧 W1~W3 提投到 80% 以上 + 把 DDL/留痕/计量的主责移到 Python 侧；M1 拆成 G1（链路 echo）+ G2（全链路）两个验收门；每个里程碑加"是否具备进入下一阶段"的显式门禁。
- **教训**：**排期是算术题，不是意愿表达**。要用「任务人日 ÷ 角色可用工日」逐角色对账；同时"兼职 30%"这类前提必须写进排期文档，否则就是假账。

### 坑 6 密钥整改"看着做完了"，其实没有

- **现象**：文档写"application.yml 里有明文 OSS/DeepSeek Key 待轮换"。实际核对发现源码**已经改成 `${DKD_*}` 占位符了**，但改动未提交，且**初始提交的历史里仍含真实密钥**。
- **定位**：`git status` 看到 4 个 M 文件 + `.env.example` 未跟踪；`git log -p` 确认历史提交里有明文；再补一轮实测——**旧 DeepSeek Key 调用返回 401（已失效）**，说明轮换已经发生过（或供应商侧吊销）。
- **修复**：补齐 `.env`（8 个变量，含模板漏掉的 `DKD_DRUID_PASSWORD`），Git 历史由作者重写（`main`/`origin` 可达历史已无明文，旧提交对象以 dangling 形式残留 → 用 `git reflog expire && git gc` 清理）；文档同步纠正为真实状态。
- **教训**：
  - **"改代码"≠"密钥安全"**：还要覆盖提交状态、Git 历史、远端副本、环境注入；
  - 处理这类事要**先实测凭据是否有效**（我实测发现旧 Key 已废），再决定整改强度——避免为了不存在的风险做过度工程；
  - 顺手发现：`.env` **Spring Boot 不会自动读**，必须 `setx`/IDE 注入，否则本地起不来。

### 坑 9 同一个字段名，三处含义不一致（最值得讲的一条）

- **现象**：为补货建单写字段映射时，`TaskDetailsDto.expectCapacity` 的注释写的是「**货道容量**」，但直觉上"补货工单明细"应该装的是补货数量。
- **定位**：三处交叉验证 —— `dkd-parent` 的 `TaskDetails` 实体注释是「补货数量」；`dkd-app` 的 `VendingMachineServiceImpl:62` 直接 `setCurrentCapacity(currentCapacity + d.getExpectCapacity())`（**当作补货数量累加进库存**）；只有 `TaskDetailsDto` 的注释是「货道容量」。**结论：DTO 注释是错的**。
- **如果不查会怎样**（这是我把它单列一条的原因）：
  ```
  Agent 把容量 10 填进 expectCapacity（本意"这台机器该补到 10 件"）
    → 运维现场只补了几件 → app 执行 currentCapacity + 10
    → 库存虚增 → 下一轮预警/建议基于假数据 → 建议量继续偏离
    → 数据滚雪球，且每一步"看起来都成功"，极难归因
  ```
- **修复（三层，不靠人记）**：① `RestockItem` 范围夹取 `0 ≤ 建议量 ≤ 容量 - 现库存` → 填容量必然越界被拒；② `after_restock_quantity` 必须等于「现库存 + 建议量」→ 拦掉"补到某值"的语义混用；③ 映射函数有测试断言 `expectCapacity != max_capacity`。同时建议 Java 侧**只改注释**（零行为变更），不改字段名（跨 3 模块 + 前端，成本不匹配）。
- **教训**：
  - **字段名/注释不是契约，行为才是契约**——契约要从"谁消费它、怎么消费"反推；
  - 涉及"数据会被写回业务表"的映射，要做**范围夹取**而非信任上游；
  - 发现文档与行为不一致时，**改注释**往往比改代码更划算，但要留下书面结论（我们写进了评审稿 §4.2 的"语义陷阱"专节）。

### 坑 8 一个"看起来是坑、其实是发现"的点：配置的模型 ≠ 实际服务的模型

- **现象**：配置 `deepseek-chat`，但响应里 `model` 字段返回的是 `deepseek-flash`。
- **处理**：`ping_llm()` 改为记录**服务端实际返回的模型名**，不一致时打 WARN。
- **教训**：**成本计量与效果归因必须按实际值记**。如果按配置名统计，token 单价、模型版本对比、AB 实验全会失真。这是个很小但很"专业"的细节，面试时讲出来很加分。

### 坑 10 方案里写好的类，在目标模块里根本不存在（`spring-webmvc` 缺失）

- **现象**：方案 §3.3 明确要求 Java 网关用 `StreamingResponseBody`（或 `ResponseBodyEmitter`）逐块写 SSE，我把它写进了任务书；实现时编译直接报错：`org.springframework.web.servlet.*` 不可解析。
- **定位**：`mvn -pl dkd-common dependency:tree -Dincludes=org.springframework:spring-webmvc` → **空**。`dkd-common` 只依赖 `spring-web`（注解在这，所以 `@RestController` 能编译），而 `StreamingResponseBody`/`HandlerInterceptor`/`WebMvcConfigurer` 全在 **`spring-webmvc`** 里。
- **根因**：把方案的“意图”当成了“约束”。方案是跨模块设计文档，它不会知道你最终把类放哪个 Maven 模块；我自己在任务书里既锁定了“不新增依赖”又要求“用某个类”，两条约束互斥。
- **修复**：保持语义合同（**禁止先把响应体读完再返回、逐块 flush**）不变，改用 Servlet API 落地：控制器直接写 `HttpServletResponse.getOutputStream()`，读一块（1KB）写一块并 flush；回调鉴权改用 `OncePerRequestFilter`。附带好处：同步写不受 Tomcat 异步 `asyncTimeout`（默认 30s）掐流影响。代价记账：每个在途对话占一个 Tomcat 工作线程（`max=800`）。
- **教训**：**跨模块落地前先跑 `dependency:tree -Dincludes=<你要用的包>`**，一分钟的事；同时“不要新增依赖”这类约束要在任务书里写清**允许的例外与升级路径**（我后来补了一句“若改回原名 API，只需给 dkd-common 加 spring-webmvc 依赖”）。

### 坑 11 `HttpURLConnection` 的 `getErrorStream()` 必须“先读状态码”才有效——错误路径静默退化

- **现象**：单测里“上游返回 422/503 时透传原始信封”的用例全部失败，抛的是 `ResourceAccessException: I/O error on POST ... Server returned HTTP response code: 422`，网关把它当成“**服务不可达**”去降级。
- **定位**：Spring 的 `SimpleClientHttpResponse.getBody()` 会先取 `connection.getErrorStream()`，取不到才 `getInputStream()`；而 JDK 的实现里 **`getErrorStream()` 在响应码被读出之前恒为 null**，此时 `getInputStream()` 对 4xx/5xx 直接抛 `IOException`。我的 extractor 先读了 body、后读状态码，于是顺序反了。
- **根因**：JDK 这个“怪癖”不在直觉里；更本质的是**异常归因做错了层**——把“上游返回了业务错误”和“连不上上游”混成了同一个异常。
- **修复**：extractor 内强制**先 `getRawStatusCode()` 再读 body**，并在代码里写下“勿调换顺序”的注释；`forward()` 对 4xx **原样透传**（429 限额这种明确业务语义不能被换成 503），只对传输层失败/上游 5xx 降级。
- **教训**：① HTTP 客户端的**错误路径**最容易“看起来能跑”；② 错误要按**层次**归类（传输失败 / 上游业务错 / 网关照挂），归错层会把排查引向错误方向；③ 这类 bug 靠“跑一遍正常流程”发现不了，必须写**拒绝路径用例**。

### 坑 12 过滤器顺序决定“可达性”：白名单写了，但永远走不到

- **现象**：任务 0-7 的验收要求“非白名单回调路径 → 404”。单测全绿（直接 new 过滤器调 `doFilter`），但真机测 `/agent/callback/other` 返回的是 **401**。
- **定位**：我把 `AgentCallbackAuthFilter` 注册成 `order=0`，而 Spring Security 的 `springSecurityFilterChain` 是 **order=-100**（数值越小越先执行）⇒ 我的过滤器在**安全链内部**先经过安全链。`/agent/callback/other` 没被 `@Anonymous` 登记（只登记了 `/agent/callback/task`），于是被安全链以 401 拦掉，我的白名单分支**永远不可达**。
- **根因**：把“能执行到”当成了默认。**单元测试直接调过滤器方法，绕过了整个过滤器链，天然测不出顺序问题。**
- **修复**：改为 `order=-200`（先于安全链），让服务间密钥成为 `/agent/callback/**` 的唯一守门人：无密钥/伪造 → 401，密钥对但路径未登记 → 404，两种都不进业务；并在类注释里写清“为什么必须小于 -100”。
- **教训**：
  - **顺序类缺陷（过滤器/拦截器/AOP/中间件）只能靠集成或真端到端发现**，单元测试覆盖再高也给不出信号；
  - 设计鉴权时先问一句：“**谁能先拦到请求**”，而不是“我写了什么判断”——写了不等于会执行。

### 坑 13 `request_id` 被解析两次，全链路 trace 当场断掉 + 客户端可控字段未净化

- **现象**：网关回给前端一个 `X-Request-Id`，Python 日志里却是**另一个值**，用户报障时两边对不上号。
- **定位**：响应头处和转发头处各调了一次 `resolveRequestId()`，未传 header 时各自 `UUID.randomUUID()` → 两个 ID；单测里两个用例分别断言“生成了 ID”和“复用了客户端 ID”，**都通过**，所以没人发现。
- **修复**：① 统一为 `AgentRequestId.resolve()` 一个入口（顺带消掉 filter 与网关的重复实现）；② 同时加固：客户端可控的 `X-Request-Id` 会进入日志与响应头，只保留可见 ASCII、截断 64 字符、全非法则重新生成（防**日志注入**与非法响应头触发容器异常），并补 2 条净化用例。
- **教训**：**跨进程 trace id 只能有一个来源**（一次解析、层层传递）；“每个用例都过”不等于“这些用例拼起来是对的”——**同一概念的多次生成/重复实现，要有单点收敛的强制手段**。

### 坑 14 RuoYi 的“认证失败”是 HTTP 200 + `code:401`，把前端 SSE 客户端骗出了空白气泡

- **现象**：端到端验“未认证”时，`/agent/status` 返回 **HTTP 200**，我一度以为是网关漏了鉴权；对照既有 `/manage/inventory/list` 才发现行为**逐字一致**——这是 RuoYi 的约定（`AuthenticationEntryPointImpl` 渲染 `AjaxResult.error(401)`，而 `renderString` 固定写 200）。
- **更重要的发现**：我把同一约定带入 SSE 路径 → 前端 `openSseStream` 只看 `response.ok` ⇒ 200 通过 ⇒ 把这段 JSON 当 SSE 流解析 ⇒ **得到一个永不变化的空白气泡**（无报错、无提示）。
- **修复**：前端改为按 **`Content-Type` 判定是否为 SSE**（`text/event-stream`），不是就当 RuoYi 信封处理并按 `code` 分流（401 → “登录已过期”，503 → 降级横幅），`probeAgentStatus()` 同理。
- **教训**：
  - “**响应格式**”与“**状态码**”是两件事：判断“这是不是一个流”只能看 Content-Type；
  - 与既有框架约定对齐时，要连带检查**新老入口对该约定的处理是否一致**（一致性检查我用了 `curl` 对照 `/manage/**`，成本 10 秒）；
  - 静态检查帮不上忙，靠真机验“没有 token 会怎样”才暴露。

### 坑 15 观测性字段硬编码：真 LLM 调用被标成 `echo`

- **现象**：M1 验收跑真 LLM，`meta` 帧里 `"mode": "echo"`（回复内容确实是 LLM 生成的）。
- **根因**：SSE 生成函数叫 `_echo_stream`（Phase 0 骨架期命名），`mode` 直接写死 `"echo"`；后来接了 LLM 节点，这个标签没人跟着改。
- **修复**：`mode` 由**实际执行路径**决定（echo 节点写 `mode=echo`，LLM 节点写 `mode=llm` + **服务端实际返回的模型名**），续传路径从 checkpoint 读回模型；补 3 条测试（LLM 分支/续传/echo 分支）。
- **教训**：**可观测字段必须从执行路径推导，不能硬编码**——不然审计、成本归因、排障全部失真，而且**失真的方式恰好是“看起来正常”**。

### 坑 16 两个“静默”的工程坑：surefire 跳过 JUnit5、打桩丢了必填字段

| 坑 | 现象 | 根因 / 修复 | 教训 |
| --- | --- | --- | --- |
| surefire 静默跳过用例 | 加完 `spring-boot-starter-test` 后 `mvn test` **BUILD SUCCESS**，但一个新用例都没跑 | 父 POM 未继承 `spring-boot-starter-parent`，Maven 3.8 默认绑定 surefire **2.12.4**，不识别 JUnit5 → pin `2.22.2` | **“构建绿”不等于“断言跑了”**：必须核对 `Tests run` 数量；测试框架引入后的第一件事是验证它真的在跑 |
| 打桩与真实契约不一致 | 用 `AIMessage(usage_metadata={input_tokens, output_tokens})` 打桩 LLM，节点报 `ValidationError` | 本版 langchain 的 `usage_metadata` **要求 `total_tokens` 也必填** → 补上 | 打桩对象也要满足**真实契约的完整约束**，否则你测的是“桩能不能跑”，不是“代码能不能跑” |

## 五之二、知识点清单（可背诵，面试按需展开）

> 每条都来自本项目**实际写过的代码/踩过的图**，不是抄文档。括号里是“面试时怎么落地这两句”。

### A. SSE 与流式（问得最多）

| 知识点 | 要点 |
| --- | --- |
| 帧格式 | `event:` / `data:`（可多行，按 `\n` 拼接）/ `id:` / 注释行 `: keep-alive`；帧以**空行**分隔（`\n\n` / `\r\n\r\n` 都要兼容）；**注释行不是事件**，解析时要丢掉（本项目就踩过：被当成事件派发了一次空回调） |
| 为什么不用 `EventSource` | 它**不能自定义请求头** ⇒ 带不了 `Authorization: Bearer <jwt>`；所以用 `fetch` + `ReadableStream` 手工分帧 |
| 为什么不用现成 axios 实例 | 该实例 `timeout: 10000` 且响应拦截器按 `res.data.code` 解析 JSON，会把 `text/event-stream` 当 JSON → 另写 `utils/sse.js` |
| 断点续传 | 客户端把最后一个帧 `id` 放在 `Last-Event-ID` 头重连；服务端**不重跑**，从 checkpointer 读回本轮回复，只补发未收帧（`index <= offset` 跳过） |
| 不缓冲（服务端） | Tomcat 响应默认 8KB 缓冲 ⇒ 每块必须 `flush()`；响应头显式 `Cache-Control: no-cache, no-transform` + `X-Accel-Buffering: no` 对付 Nginx 缓冲/压缩 |
| 不缓冲（怎么**证明**） | 用 `curl -N ... \| while read line; do echo $(date +%s%3N) $line; done` 打时间戳：本次实测 **51 帧 / 3.2s，首 delta 距首行 70ms、末帧距首帧 3217ms**；若被整包缓冲，所有行会在毫秒级一起到达（这条比“我看能流式”有说服力得多） |
| 可取消 | `AbortController`；客户端断开 → 服务端写失败 → 归因为 `AgentClientAbortException`（正常操作，不打 WARN，否则监控噪声掩盖真故障） |
| 空闲超时 | 用“多久没收到**任何字节**”做心跳判据（不是帧数）：LLM 首包可能几秒，网关读超时 120s、前端空闲 60s |
| 帧级 vs token 级 | **本项目已实现 token 级（M1 发现后修光）**：LLM 节点 `streaming=True` + API 层 `astream(stream_mode=["messages","values"])`（messages 抽逐 token 分片、values 取最终 state）。实测真 LLM：13~14 帧 / 首 token 距 meta **545ms** / 末 token 距首 token **487ms**。两个坑：① messages 模式也会把节点返回的**完整 `AIMessage`** 吐出来（echo 节点），必须按 `AIMessageChunk` 类型过滤，否则重复发一遗；② 不显式开 `streaming=True` 时依赖 langchain 内部启发式，升级可能静默退化。**面试价值**：能区分“能流式”与“帧级 vs token 级”，并给出时间戳证据 |

### B. Servlet 过滤器链 / Spring Security（Java 侧最容易被追问）

| 知识点 | 要点 |
| --- | --- |
| 过滤器顺序 | `FilterRegistrationBean.setOrder()` 数值**越小越先执行**；Spring Security 的 `springSecurityFilterChain` 是 **-100** |
| 谁在谁里面 | 注册为 order > -100 的过滤器，其 `doFilter` 是在 Security 链的 `doFilter` **内部**被调用的 ⇒ 能读到 `SecurityContext`（`JwtAuthenticationTokenFilter` 已填充）；order < -100 则先于安全链 |
| `SecurityContext` 生命周期 | 安全链的 `SecurityContextPersistenceFilter/HolderFilter` 在 `finally` 里 `clearContext()` ⇒ 想在 Servlet 里拿身份，必须**在安全链内部**（本项目 `AgentTokenFilter` 用 order=0 就是这个原因） |
| `@Anonymous` 机制 | `PermitAllUrlProperties` 扫注解、把**方法级 URL** 加进 permitAll；类级注解会把该类所有映射都加进去（本项目回调 Controller 用它绕过 JWT，因为它是**服务间密钥**这套体系的） |
| 身份注入为何放 attribute 而不是改写请求头 | 头可被客户端伪造；attribute 由过滤器写、控制器读，**客户端没有任何路径能写进去**；转发时再按白名单**重建**头（绝不遍历客户端头） |
| 常量时间比较 | `MessageDigest.isEqual(a.getBytes(UTF_8), b.getBytes(UTF_8))`，避免 `equals` 按字符短路泄漏密钥长度/前缀 |

## 七、面试问答预演

**Q1：为什么不用 LangChain4j / Spring AI，非要多维护一个 Python 服务？**
Java 8 是硬约束（框架要 17+），升级 JDK 会牵动 RuoYi 全家桶；Python 侧生态（LangGraph、评测、向量库）成熟度明显更高。代价是多一个进程与运维面，我用「旁路 + 开关 + 兜底」把风险控制在"挂了也不影响主业务"。

**Q2：为什么不让 LLM 直接调 Java 接口、甚至直连数据库？**
直连库会绕过事务、工单防重、员工区域校验和操作日志，是红线。回调 Java REST 则天然复用这套校验链——**把"AI 的不确定性"关在业务校验之外**。LLM 输出一律视为不可信输入：结构化解析 + 范围夹取（数量 clamp 到 [0, 货道容量-现库存]）+ 写操作人工确认。

**Q3：LLM 给出的补货量不准怎么办？**
三层兜底：① **统计基线不依赖 LLM**（7/14/30 天分位销量 + 容量约束），LLM 只做"点位画像/节假日/异常波动"的校准与理由生成——最坏退化成"可解释的规则增强版"；② 首期全部人工确认；③ 7 日复盘（建议量 vs 实际消耗）回写并迭代参数。加上与规则版并行双跑 3 周做对照。

**Q4：多轮对话的状态存哪？为什么？**
LangGraph checkpointer，当前用 SQLite（单机形态匹配、零新增基础设施）。**为什么不是 Redis**：本机 Redis 3.2.100 无模块系统、装不了 RedisJSON/RediSearch，`langgraph-checkpoint-redis` 依赖它。迁移触发条件写清了：多实例部署或需跨机共享 → Postgres saver 或升级 Redis 8。

**Q5：怎么保证 AI 建的单不会重复？**
三道：`agent_restock_plan` 的 `UNIQUE(vm_id, plan_date)`（DB 层硬约束）；状态机卡口（只有"建议/已调整"能确认）；建单前查同设备在途补货工单。另外 `insertTaskDto` 自己有设备级防重，等于第四道。

**Q6：AI 服务挂了怎么办？**
`agent.enabled=false` 一键降级回原单轮 AI；多轮会话入口隐藏（不伪造能力）；定时任务失败有告警不静默。主业务完全不依赖 Python 进程。

**Q7：NL2SQL 不做防御不敢上生产吧？**
只读账号（白名单表）+ SQL 静态校验器（只读语句/表名白名单/强制注入 LIMIT/超时熔断）+ 预置模板兜底。且**先建评测集再定准确率目标**（50~100 条真实取数问题），不接受"感觉还行"。

**Q8：Prompt 注入怎么防？**
系统提示隔离 + 用户输入定界并声明"仅数据非指令" + 工具入参白名单化 + **写操作二次确认不受对话影响**（确认是前端结构化的，不是 LLM 能绕过的）。

**Q9：怎么评估效果？**
与规则版并行双跑 3 周，指标：缺货率、建议量偏差、人工调整率；补货质量用回测（建议量 vs 人工经验偏差 ≤±20%）；Copilot 用评测集抽样。**基线必须提前固定**，否则 3 个月后无法归因。

**Q10：这个项目的技术难点是什么？**
不是调模型，是**边界设计**：读写分离的粒度（哪些数据能直连、哪些必须走 Java）、写操作的幂等与人工确认、降级与审计的可用性权衡、以及"AI 代码要进生产"所需的留痕/脱敏/成本/权限一整套工程约束。

**Q11：为什么用 LangGraph 而不是自己写个 while 循环调工具？**
多轮 + 中断恢复 + 状态持久化这三件事自己写就是重新实现 checkpointer 与 HITL；LangGraph 的 `interrupt()` 正好对上"建议 → 人工确认 → 执行"的业务语义。**但要注意它的版本与 checkpoint 兼容性约束**（开放版本区间是陷阱，state schema 一旦上线只能加字段）。

**Q12：这套东西的 ROI 怎么算？**
客服/运营侧省的是人工排单时间（60%+），业务侧省的是缺货损失（30%+）；成本侧是 token 消耗（有计量与限额）。我会强调**先做对照实验再谈收益**，不拍脑袋。

**Q13：你说 SSE 不缓冲，怎么证明？**（能答好这题的人不多）
不是“我看能流式”，而是**打时间戳**：`curl -N | while read line; do echo $(date +%s%3N) $line; done`，本次实测 51 帧/3.2s，**首 delta 距首行 70ms、末帧距首帧 3217ms**；若被整包缓冲，所有行会在毫秒级一起到达。另一端也有约束：Tomcat 默认 8KB 响应缓冲 ⇒ 每块必须 `flush()`；Nginx 类中间层要 `X-Accel-Buffering: no` + `no-transform`。**我会主动补一句诚实的话**：当前是帧级流式（LLM 用 `ainvoke` 整段返回后分帧），不是 token 级，改法是用 `astream` + `stream_mode="messages"`。

**Q14：为什么滤波器/拦截器写了却没生效？**
先看**顺序**：`FilterRegistrationBean.setOrder` 数值越小越先执行，Spring Security 链是 **-100**。我把回调鉴权注册在 0，于是它在安全链**内部**执行——未登记的回调路径先被安全链 401 掉，我的“非白名单→404”分支**永远不可达**（单测全绿也发现不了，因为单测直接调方法、绕过了整条链）。修法是放到 -200 让服务间密钥先守门，并用真机验 401/404 两条分支。

**Q15：如果上游返回 4xx，你会怎么处理？**
**原样透传**，不换成 503。因为 4xx 携带明确业务语义（如 token 限额 429、参数校验 422），换成“服务不可达”会让前端丢失原因。**但这里有个 JDK 陷阱**：`HttpURLConnection.getErrorStream()` 必须在读出响应码**之后**才有效，先读 body 会把 4xx/5xx 抛成 IOException、被误判为“不可达”——错误归因分层错了，排查会被带偏。

## 八、简历写法（STAR + 量化，直接可抄改）
> **DKD 售货机运营平台 · 智能体旁路改造（Java 8 + Python/LangGraph）**
> - **背景**：RuoYi 改造的售货机平台，AI 能力停留于"switch-case 硬编码 prompt 的单轮问答"，无法调用业务数据、无法产出可执行动作。

| 方案 | 形态 | 优点 | 代价/风险 | 适配本项目 |
| --- | --- | --- | --- | --- |
| **sqlite-vec** | SQLite 扩展（纯 C） | 零运维、单文件、跨平台；**本机依赖树里已有**（随 `langgraph-checkpoint-sqlite` 一并装了 `sqlite-vec`）；可复用现有 checkpoint 文件思路 | 能力边界在万~十万级；无服务化/多实例；生态较新 | ⭐ 首期最省事（≤10 万条） |
| **pgvector** | PostgreSQL 扩展 | 与 MySQL 同级成熟度；**HNSW/IVFFlat 索引 + SQL 过滤 + 事务**；社区极大；还能**顺手当 LangGraph checkpointer（Postgres saver）** | 引入第二种数据库（备份/监控/权限/主从都要加一套）；本机与团队当前无 PG 经验 | ⭐⭐ 若愿意引入 PG，**一步到位**解决 checkpoint + 向量两件事 |
| **Milvus** | 分布式向量库 | 十亿级、多索引类型（HNSW/IVF/DiskANN）、GPU、标量过滤、生态成熟 | **运维最重**：完整部署需 etcd + 对象存储（MinIO）+ 消息队列（Pulsar/Kafka）；standalone 也需多容器；Windows 不友好（本项目开发机是 Windows） | ❌ 本阶段不合适（量级差 3~4 个数量级） |
| **Qdrant** | Rust 单二进制/容器 | 比 Milvus 轻得多；过滤强；支持稀疏向量做混合检索；量化省内存 | 仍需独立服务 + 持久化盘；<10 万条属杀鸡用牛刀 | 🔸 中期候选（若向量检索成为核心能力） |
| **Elasticsearch / OpenSearch** | 搜索平台 | **BM25 + kNN 混合检索**开箱即用，天然适合"关键词 + 语义"双路召回；若团队已有 ES 可直接复用 | 资源占用大（JVM 堆）；本项目当前**没有** ES | 🔸 若将来日志/搜索也要 ES，可合并考虑 |
| **MySQL 原生** | 8.0 无 VECTOR 类型（9.x 才加 `VECTOR` + `VECTOR_DISTANCE`） | 零新增组件 | 8.0 只能存 BLOB/JSON 自己算距离 + 全表暴力 → 万级以下可接受，再大就不行 | 🔸 「不引入任何新组件」时的保底 |
| **云托管**（百炼/向量检索服务、Zilliz Cloud 等） | SaaS | 人力成本最低、能力最全、免运维 | 数据出内网需合规评估；长期成本随量增长；锁定风险 | 🔸 若团队人手是硬约束，可作为试点 |

> 版本与能力细节请以选型时的官方文档为准（本文数字为量级判断，不作为承诺）。

### 9.3 分阶段建议（写死触发条件，避免"拍脑袋升级"）

| 阶段 | 规模 | 建议 | 迁移触发条件（满足任一即评估升级） |
| --- | --- | --- | --- |
| Phase 2 冷启动 | ≤1 千条案例 | **规则/关键词检索**，不做向量 | — |
| Phase 2~3 真做 RAG | 1 万~10 万条 | **sqlite-vec**（最小改动）或直接上 **pgvector** | 需要"元数据过滤 + 向量"混合查询且 SQL 里已有复杂条件 |
| Phase 4+ | >50 万条，或需多实例/多租户/高并发 | **pgvector 或 Qdrant** | 检索延迟 P95 > 300ms、或需要独立扩缩容 |
| 远期 | 千万级以上、持续高并发 | **Milvus / 云托管** | 单机索引内存成为瓶颈、需要水平分片 |

**我的倾向（可辩论）**：本项目**优先 pgvector**。理由：① 它同时解决"向量检索"和"会话 checkpoint 从 SQLite 演进"两件事，用一个新组件换两个能力，**净新增运维面最小**；② SQL 生态与团队 Java/MySQL 背景最接近，运维心智负担低；③ 万~百万级规模完全够用。Milvus 的能力对本项目是**过剩**的——"用最合适的，不用最强的"。

**反方观点也要记住**：如果向量检索变成核心能力（多路召回 + rerank + 多租户），或数据量进入千万级，pgvector 的运维优势会被性能劣势吃掉，那时 Milvus/Qdrant 才是正解。**面试时能说出这个 trade-off 比坚持某个结论更重要。**

### 9.4 RAG 工程要点清单（比选向量库更要紧）

| 环节 | 要点 | 本项目特有约束 |
| --- | --- | --- |
| 语料来源 | 历史维修工单（现象/原因/处置/复发间隔）、SOP、商品与点位档案 | **先做数据质量抽样**（0.5d），不达标就降级为规则库——不要拿脏数据喂 RAG |
| 切分 | 工单是天然结构化单元，**尽量不切**（一条案例=一个 chunk），长文档按语义段落切 | 元数据必须保留 `task_id`/设备型号/点位 |
| 元数据过滤 | 设备型号、点位、区域、时间窗 | 先过滤再召回，能大幅降低对向量库性能的要求（也是 pgvector 够用的原因） |
| 混合检索 | 关键词（故障码/型号，精确匹配强）+ 向量（现象描述，模糊匹配强）→ 融合 | 工单里的故障码是精确 token，纯向量会丢 |
| 重排 | 召回 top20 → rerank → 取 top3~5 给 LLM | 中文场景 rerank 收益明显 |
| 引用溯源 | 输出必须带案例 ID，前端可点回原工单 | **审计要求**：诊断结论要能解释来源，不能"模型说的" |
| 增量更新 | 工单结单即入索引 | 与 `agent_decision_log` 一样，尽量做成事件/定时增量，别全量重建 |
| 评测 | 建"问题 → 期望案例"的评测集，看 Recall@k / MRR | 与 Phase 3 的取数评测集同一套方法论 |

### 9.5 Embedding 模型选型（顺带记下）

| 候选 | 说明 |
| --- | --- |
| 通义 `text-embedding-v3/v4`（DashScope） | 中文强、与现有"可切通义千问"的规划一致、API 简单；**在中国大陆网络环境下更稳** |
| BGE 系列（bge-m3 / bge-large-zh） | 可**自托管**、支持多语言与稀疏+稠密混合；适合数据不能出内网时 |
| OpenAI `text-embedding-3-*` | 生态最广，但本项目主 LLM 走 DeepSeek，没必要为 embedding 单独引一条链路 |

**注意**：向量维度与索引参数要在选型时一起定（pgvector 的 HNSW 对维度有限制），换 embedding 模型通常意味着**重建索引**，所以要把"模型 + 维度 + 距离度量"当作一组配置冻结并记录。

## 十、复盘清单（每次迭代后回看）

1. **事实性结论必须有 `file:line` 证据**（表名、字段、校验链、索引写法）——本项目 3 个坑都源于"凭印象"。
2. **基础设施选型前先探测能力边界**（版本 / MODULE LIST / 关键配置），1 分钟省一次返工。
3. **区分基础设施故障与业务规则**：前者降级 + 告警，后者明确拒绝 + 可读错误。
4. **旁路能力在调用点做异常边界**，不要指望被调函数吞干净。
5. **排期按角色可用工时逐项对账**，并把投入比例写进文档。
6. **测"拒绝路径"比测"成功路径"更有价值**（白名单、鉴权、限额、降级）。
7. **成本与效果按实际值记**（服务端返回的模型名，不是配置名）。
8. **不引入新组件除非它的能力是当前量级必需的**——把迁移触发条件写下来，而不是提前上重装备。
9. **安全是流程而非代码**：提交状态 / Git 历史 / 远端 / 环境注入，四件事都要检查。
10. **每次评审后回写规范**（本项目已回写：表名前缀、Redis 能力边界、`agent_*` 两级授权、CR 禁止 `date_format` 包裹索引列）。
11. **顺序类缺陷只能靠端到端发现**（过滤器/拦截器/AOP/中间件顺序）：写了判断 ≠ 会执行到；设计鉴权先问“**谁能先拦到请求**”。
12. **用一个来源生成同一概念**（trace id、幂等键）：多处生成 = 多处不一致，且单测会各自“通过”。
13. **响应格式与状态码是两件事**：判断“是不是流”看 `Content-Type`，不看 `200`；跨入口对齐框架约定时，改完要拿旧入口做一次对照。
14. **可观测字段从执行路径推导，不硬编码**（`mode`/`model`/`upstream`）——失真的方式恰好是“看起来正常”。
15. **“构建/测试通过”要看数字**（`Tests run`、覆盖率、断言数）：surefire 2.12.4 会静默跳过 JUnit5；被跳过的“绿”比红灯危险。
16. **把一次性验证沉淀成资产**：本次把“16 项网关冒烟”入库为 `docs/scripts/g1-gateway-smoke.sh`，把真实 SSE 字节流做成分帧夹具——下次回归只跑一条命令。
