## 一、项目概览

### 1.1 四子系统与入口文件

| 子系统 | 技术栈 | 端口 | 主入口文件 | 职责边界 |
| --- | --- | --- | --- | --- |
| **dkd-parent** | Spring Boot 2.5.15 / **Java 8** / MyBatis / Druid / Redis，Maven 7 模块 | 8080 | `dkd-parent/dkd-admin/src/main/java/com/dkd/DkdApplication.java` | 管理后台。**业务事实唯一所有者**：事务 / 校验 / 权限 / 审计 |
| **dkd-app** | Spring Boot 2.7.3 / MyBatis-Plus / 自签 JWT | 9070 | `dkd-app/src/main/java/com/dkd/app/Application.java` | 运维移动端 API，**只含作业域**（接单/完成/取消） |

| **dkd-agent** | Python 3.11 / FastAPI / LangGraph / SQLAlchemy(async) | 8090 | `dkd-agent/app/main.py`（`create_app()`）+ `app/__main__.py`（`main()`） | 智能体旁路服务，**读 MySQL 只读账号、写回调 Java** |

> **关键事实：dkd-parent 与 dkd-app 是两套完全独立的工程**——独立 POM、独立身份体系（Spring Security `SysUser` vs `tb_emp` + 自签 JWT）、JWT 互不相认。仅共享同一个 MySQL 库 `dkd` 与 Redis db0。

### 1.2 Maven 模块职责（dkd-parent）

```
dkd-admin     启动入口 + 系统 Controller（唯一可启动模块）
  └─ dkd-framework    安全链路(JWT/Security/AOP/XSS/防重提交)
      └─ dkd-system    系统域（用户/角色/部门/字典/日志）
          └─ dkd-manage   ★ 核心业务域（21 个 Controller）
              └─ dkd-common    工具包 + com.dkd.common.ai（AI 兜底）+ common.agent（Java↔Python 网关）
├── dkd-quartz     定时任务
└── dkd-generator  代码生成
```

**dkd-manage 业务域**（`/manage/**`）：`Task`(工单) `TaskDetails` `TaskType` `Channel`(货道) `VendingMachine`(设备) `VmType` `Node`(点位) `Region`(区域) `Partner`(合作商) `Policy`(策略) `Sku`/`SkuClass`(商品) `Inventory`/`InventoryLog`(库存/流水) `Order`(订单) `Report`(报表) `Emp` `Role` `Job`，外加 Agent 三件套：`AgentRunController`、`AgentDecisionLogController`、`AgentCallbackController`。

### 1.3 核心数据模型

```
Region(区域) → Node(点位) → VendingMachine(设备) → Channel(货道)
Sku/SkuClass/Policy · Order(交易) · Inventory/InventoryLog(库存) · Task/TaskDetails(作业)
```

**业务表统一 `tb_` 前缀；智能体自有表统一 `agent_` 前缀。** 已确认存在的 agent 表由 README 所称的「四张」实际增长到 6+ 张（新增 `agent_run`/`agent_step`/`agent_tool_call` 观测三表）。

## 二、核心业务流程

### 2.1 全链路调用关系

```
【运营后台/Web】dkd-vue (:80)
    │ /dev-api → :8080（vite proxy；注 :9070 未配代理）
    ▼
【管理后台】dkd-parent (:8080)
    ├─ 过滤器链：XssFilter → RepeatableFilter → AgentTokenFilter(/agent/*) → Security(JwtAuthenticationTokenFilter) → RepeatSubmitInterceptor → @PreAuthorize
    ├─ dkd-manage Controller → Service → Mapper → MySQL(dkd) / Redis(db0)
    ├─ AgentGatewayController  /agent/**  ──转发──▶ dkd-agent (:8090)   [网关注入 X-Agent-User/Roles/Region]
    └─ AgentCallbackController /agent/callback/task ◀──回调── dkd-agent  [服务间密钥]
                                            │
【智能体】dkd-agent (:8090)                  ▼
    chat / restock / fault 三张 LangGraph 图 ──▶ MySQL 只读账号 + agent_* 可写
                                            └──▶ SQLite/Postgres checkpointer
【运维移动端】dkd-app (:9070)
    LogInterceptor → EmpHolder(ThreadLocal) → TaskServiceImpl.complete
        └─▶ tb_task(状态) + tb_vending_machine(状态) + tb_channel(读数)
            + tb_inventory(台账) + tb_inventory_log(流水)   ← 同一事务
```

### 2.2 主链路 A：补货作业闭环（最高频、唯一端到端打通的链路）

**① 建单（唯一入口）**
`TaskController.add()` / `AgentCallbackController.createTask()` → 均收敛到私有方法
**`TaskServiceImpl.insertTaskDtoInternal(TaskDto)`**（`dkd-manage/.../TaskServiceImpl.java:223`）

校验链（顺序 = 失败分支，异常文案被 Python 侧原样展示给用户）：

| 序 | 校验 | 实现方法 / 行 | 失败信息 |
| --- | --- | --- | --- |
| 1 | 设备存在性 | `selectVendingMachineByInnerCode()` :226 | 售货机不存在 |
| 2 | 工单类型白名单 + 设备状态匹配 | `checkCreateTask()` :383、`isTaskTypeAllowed()` :442、`isRepairAllowed()` :426 | 类型不合法 / 正在运行中勿重复投放 / 未投放已撤机 / 不在运行中 |
| 3 | **设备级工单防重** | `taskMapper.selectInflightTaskList(innerCode, typeId, [1,2])` :239 | 设备有未完成工单 |
| 4 | 员工存在 + 未停用 | :254 | 员工不存在 / 员工已停用 |
| 5 | 角色匹配（补货→1002/1001；维修/投放/撤机→1003/1001） | `isRoleAllowedForTaskType()` :467 | 该员工角色不能执行此类工单 |
| 6 | **员工区域 == 设备区域** | :264 | 员工区域与设备区域不一致 |
| 7 | 补货明细校验（货道归属 / `expectCapacity>0` / 不超容 / SKU 一致） | `checkSupplyDetails()` :500（一次 `loadChannels()` 建 Map 避免 N+1） | 必须包含明细 / 货道不存在 / 数量非法 |
| 8 | 落库 | `task_status=1(CREATE)`；`taskCode` 由 Redis `dkd.task.code:yyyyMMdd` 自增 :351 | — |
| 9 | 唯一键兜底 | catch `DuplicateKeyException` :312 | 请刷新重试 |

> ⚠️ **语义坑**：`TaskDetailsDto.expectCapacity` 注释写「货道容量」，但 dkd-app 侧**当作补货数量累加进库存**。建单必须传建议补货量，绝不能传容量。

**② 接单 → ③ 完成（在 dkd-app，不在 dkd-parent）**

`dkd-app/.../service/impl/TaskServiceImpl.complete(taskId, userId)`（`@Transactional(rollbackFor=Exception.class)`）
前置：必须 `taskStatus==2 进行中` 且 `userId.equals(task.getUserId())`，否则 `LogicException`。

同一事务内串联四个写入，任一步失败整体回滚：

```
complete() @Transactional
  ├─ this.updateById(task)                      → tb_task: 2→4(FINISH)
  ├─ VendingMachineServiceImpl.supply()          → tb_vending_machine.last_supply_time
  │     └─ tb_channel: current_capacity = min(current+expect, max_capacity)【夹取】
  │     └─ 异常明细进 failures 列表，非空则整体回滚（不静默跳过）
  └─ InventoryStockServiceImpl.applyRestock()    → tb_inventory(INSERT/UPDATE) + tb_inventory_log(流水)
        └─ 失败统一抛 LogicException("工单完成失败：设备状态或库存回写未生效")
```

> **非对称性**：`accept`（接单）与 `cancel`（取消）**没有** `@Transactional`，也无乐观锁（`task_version` 缺失），是典型 check-then-act，并发双击存在覆盖窗口。

### 2.3 主链路 B：交易下单 —— ⚠️ **事实上的断链**

这是本次梳理发现的**架构级缺口**，直接决定后续性能优化的判断：

- `InventoryServiceImpl.updateInventoryQuantity(vmId, skuId, channelId, changeQuantity, changeType, operator)`（`:270`，`@Transactional`，内含负库存拦截、超容夹取、写流水）——**全仓库零调用方**。Grep 确认只有接口 `IInventoryService.java:116` 与实现本身，无任何业务代码引用。
- `OrderController.add()`（`:78`）→ `OrderServiceImpl.insertOrder()`（`:56`）：**无库存扣减、无金额校验、无幂等、无事务**。
- 支付网关回调、出货指令下发代码在本仓库不存在。
- 结论：**Order 下单不扣库存、Task 完成才回写库存**（目前唯一库存增量来源是补货完成 + 后台 CRUD）。`InventoryServiceImpl` 精心实现的"库存唯一变更入口"实为空转。

### 2.4 主链路 C：智能体旁路（读写不对称设计）

```
前端 AgentAssistant/index.vue (SSE客户端)
  └─ src/utils/sse.js :: openSseStream()      ← fetch + ReadableStream（非 EventSource，需带 Authorization）
       └─ GET /agent/chat (Java 网关注入身份头 → 转发 Python)
            └─ dkd-agent app/api/chat.py :: chat / _chat_stream
                 └─ chat_graph.build_chat_graph()
                      START → resolve_focus → respond(LLM+bind_tools, MAX_TOOL_ROUNDS=3)
                              ⇄ ToolNode（条件边 _should_call_tools）
                 └─ 只读工具 app/tools/read_tools.py（白名单+超时+行数上限）
                 └─ ⚠️写操作唯一通道 app/tools/task_tools.py :: create_restock_task()
                      → POST /agent/callback/task → Java TaskServiceImpl.insertTaskDtoReturningTask
```

**写操作 human-in-the-loop 的三条保障**：
1. Python **不解析 JWT**，只信任网关注入头（`app/security.py :: require_agent_gateway()`，回环放行 + 非回环强制密钥，fail-closed）；
2. 补货图 `restock_graph.py` 在 `await_confirmation` 节点 `interrupt()` 暂停，**零副作用**，人工确认后才进 `apply_decisions` → `create_tasks`；
3. `app/db.py :: assert_table_allowed()` 硬卡两级白名单：`tb_*` 只读、`agent_*` 可写名单由 `AGENT_OWNED_TABLES` 限定且**账号无 DELETE 权限**。
降级开关 `agent.enabled=false` → 回退 `com.dkd.common.ai.AiServiceImpl`（DeepSeek 单轮），Python 不可用时主业务零影响。

### 2.5 状态机汇总

| 对象 | 状态码 | 常量位置 | 流转方法 |
| --- | --- | --- | --- |
| 工单状态 | 1创建/2进行中/3已取消/4已完成 | `dkd-common/.../DkdContants.java`（Long）**与** `dkd-app/.../VmSystemConstant.java`（Integer）**重复定义** | 创建→`insertTaskDtoInternal`；取消→`TaskServiceImpl.cancelTask`（dkd-parent）；接单/完成→dkd-app |
| 工单类型 | 1投放/2补货/3维修/4撤机 | 同上 | — |
| 设备状态 | 0未投放/1运行/2停机/3撤机 | 同上 | 新建→0（`insertVendingMachine`）；1/2/3 切换由 dkd-app 工单完成时改 |
| 订单状态 | 0待支付/1已支付/2出货成功/3失败/4取消 | **裸字面量**，见 §5-P1-③ | `cancelOrder`/`refundOrder` |
| 补货计划 | 1-7 | `app/graphs/restock_state.py :: PLAN_STATUS_*`、`ALLOWED_TRANSITIONS`、`can_transition()` | `apply_decision()` 状态机卡口 |

> ⚠️ **状态常量跨模块重复且类型不一致**（Long vs Integer），是后续最容易漂移的地方。

## 附录：给「性能优化与集成部署」的三条起手建议

1. **先定性再定量**：P0-1 的库存断链决定压测脚本怎么写——如果下单本就不扣库存，那么"下单链路性能"目前没有意义，真正的热点是**补货工单完成**（单次请求串 4 张表写入 + Redis 工单号自增）与**报表/库存预警**（无分页全表）。
2. **先补 CI 再优化**：没有自动门禁的优化会反复劣化。最低成本是先加一个跑四套 build/test 的 workflow（P0-2），把 README §七声称的 203/42/16 基线固化下来。
3. **部署顺序有硬依赖**：initdb → import 业务 dump → setup-agent-db（授权）→ healthcheck（含 SSE 逐帧）。其中「业务 dump」是唯一无法从仓库推导出来的外部输入，上线前必须确认 dump 来源与 `add_index_tb_order_and_tb_task.sql`（本机已执行、生产待低峰）、`add_task_active_dedup_unique.sql`（待评审）的执行状态。
