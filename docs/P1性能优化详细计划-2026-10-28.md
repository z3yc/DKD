## W1-2（P1-9）修复 OrderMapper 时间过滤的索引失效

**现状**（已核实 `OrderMapper.xml:43-48`）：
```sql
AND date_format(create_time,'%y%m%d') >= date_format(#{params.beginTime},'%y%m%d')
AND date_format(create_time,'%y%m%d') <= date_format(#{params.endTime},'%y%m%d')
```
函数包裹 `create_time` → 索引失效全表扫描。`ReportMapper.xml`、`AgentRunMapper.xml`、`AgentDecisionLogMapper.xml`、`InventoryLogMapper.xml` 已统一改为半开区间写法并在文件头注释禁用此写法，**此处是漏网之鱼**。

**改法**：
1. 改为半开区间（保持「按天、双端含当天」的原语义）：
   ```sql
   AND create_time >= #{params.beginTime}
   AND create_time < DATE_ADD(#{params.endTime}, INTERVAL 1 DAY)
   ```
2. 前置确认：前端 `order/index.vue` 的日期控件传的是 `yyyy-MM-dd`（RuoYi `addDateRange` 惯例）。若存在传完整时间戳的调用方，endTime 侧需改为 `< DATE_ADD(DATE(#{params.endTime}), INTERVAL 1 DAY)` 以免把传入时刻当天余下时间误包含。
3. 顺带在 `OrderMapper.xml` 文件头补一行与其它 Mapper 相同的「禁止函数包裹索引列」警示注释。

**涉及文件**：`OrderMapper.xml`（仅此一处 SQL）
**验收**：带时间范围的订单列表查询，EXPLAIN 显示走 `create_time` 索引（`docs/ddl/add_index_tb_order_and_tb_task.sql` 本机已执行过，索引可用）；结果集与旧 SQL 对拍一致（重点验证边界日当天的订单包含关系）。
**预估**：0.25 人日 ｜ **风险**：低；唯一语义风险就是上面第 2 点的传参格式。

## W1-3（P1-10）三处 N+1 查询整改

**现状**（均已核实）：
- ① `NodeServiceImpl.importNode()` :186 —— 循环内 `nodeMapper.selectNodeList(按名称)` 判重，导入 N 行 = N 次查询；
- ② `ChannelServiceImpl.setChannel()` :152 —— stream 内逐条 `getChannelInfo(innerCode, channelCode)`；
- ③ 同上 :170 —— for 循环逐条 `updateChannel`（此处注释说明了是刻意规避 JDBC 多语句限制，见下方改法注记）。

**改法**：
1. **①（必改）**：进入循环前一次性 `nodeMapper.selectNodeList(new Node())` 拉全部点位（或新增 `selectNodeNames()` 只查 id+node_name 两列），建 `Map<String, Long>`，循环内 O(1) 判重。点位量级远小于导入批次时这是净收益；点位表很大则改「按本批次名称集合 IN 查询」。
2. **②（必改）**：`setChannel` 改为按 innerCode 分组后每台设备一次查询（已有现成方法 `channelMapper.selectChannelVoListByInnerCode(innerCode)` 可参考其 SQL 写一个返回 `Channel` 的版本），建 `Map<String/*innerCode|channelCode*/, Channel>`，stream 里 O(1) 命中，未命中保持现有「过滤 null」行为。
3. **③（可选，低优先）**：逐条按主键 UPDATE 本身是索引写，N 通常 = 货道数（几十），收益有限。若要改，用 MyBatis foreach 拼单条 `UPDATE ... CASE WHEN` 语句（不依赖 `allowMultiQueries`）。**默认不改**，避免为小收益引入批量 SQL 风险——但要在代码注释里把「为什么逐条」写清楚（现有注释已有，保留）。

**涉及文件**：`NodeServiceImpl.java`、`ChannelServiceImpl.java`、`ChannelMapper.java` + XML
**验收**：导入 100 行点位 → SQL 日志确认判重查询从 100 次降为 1 次；货道配置保存 40 货道 → SELECT 从 40 次降为 1 次；导入功能成功/失败文案逐条对拍不变。
**预估**：1 人日 ｜ **风险**：①注意 `importNode` 的失败计数语义（`failureNum`/`failureMsg`）不能变；②注意「dto.innerCode 优先、回退外层」的回退逻辑要带进 Map 的 key。

## W1-4（P1-11）库存预警/补货建议：分页 + 去重逻辑合并（含 P1-15 顺手项）

**现状**（已核实 `InventoryController.java` + `InventoryServiceImpl.java`）：
- `/low`、`/outofstock` **有**分页（`startPage()`，:180/:192）；**无分页的是 `/alerts`(:220) 和 `/restock`(:231)**，直接 `success(list)` 全量返回；
- `generateInventoryAlerts()` :595 与 `generateRestockSuggestions()` :700 **各自**调 `selectLowInventoryList()` + `selectOutOfStockList()`（两次无条件全表查询）再做内存 `seenStockIds` 去重——**两段「加载+去重」逻辑几乎逐行重复**，且两方法均无 `@Transactional(readOnly=true)`；
- 若一个页面同时调 `/alerts` 和 `/restock`，一次加载 = 4 次全表扫描。

**改法**：
1. **SQL 合并**：`InventoryMapper` 新增一条带分类的查询替代「两次全表 + 内存去重」：
   ```sql
   SELECT ..., CASE WHEN current_stock = 0 THEN 2 ELSE 1 END AS alert_kind
   FROM tb_inventory WHERE current_stock <= min_stock（或 LEAST 口径按现有两条 SQL 对齐）
   ```
   单条 SQL 天然不重复（原来两列表在 `current_stock=0` 处重叠，靠内存 Set 去重——这是重复逻辑的根因）。
2. **Service 收敛**：抽一个私有 `loadAlertCandidates()` 返回带 `alert_kind` 的列表，`generateInventoryAlerts` / `generateRestockSuggestions` 各自只做「DTO 组装」那一层（`checkInventoryAlert` / `generateRestockSuggestion` 保持不动，两者产出物不同是合理的差异）。补 `@Transactional(readOnly = true)`。
3. **Controller 分页**：`/alerts`、`/restock` 加 `startPage()` + 返回 `getDataTable(list)`；前端 `api/manage/inventory.js` 与对应页面的表格加 `Pagination` 组件（项目已有全局组件，照 `list` 接口的用法抄）。
4. **P1-15 顺手项**：`InventoryController.add()` :96-148 的三段「显示字段→ID 反查」下沉为 `IInventoryService.insertInventoryByDisplay(Inventory)`（或 Service 内私有 `resolveDisplayIds`），Controller 恢复「参数校验 + 调 Service」的规范形态；三个 Mapper 注入从 Controller 移除。注意保持四段错误文案逐字不变（前端有依赖）。

**涉及文件**：`InventoryController.java`、`InventoryServiceImpl.java`、`IInventoryService.java`、`InventoryMapper.java` + XML、`dkd-vue/src/api/manage/inventory.js`、`dkd-vue/src/views/manage/inventory/index.vue`
**验收**：① `/alerts`、`/restock` 返回 `TableDataInfo` 结构且分页生效（total 正确）；② SQL 日志确认全表查询从 4 次（双接口同开）降为 2 次（各 1 次合并查询）；③ 预警分类对拍：`current_stock=0` 的货道只出一条「缺货（严重）」不出第二条「低库存」；④ `add()` 接口四个错误文案与改造前逐字一致。
**预估**：1.5 人日 ｜ **风险**：中低；接口返回结构从 `AjaxResult` 变 `TableDataInfo` 是**破坏性变更**，需确认前端是唯一消费方（grep `/manage/inventory/alerts|restock` 的调用点，Agent 的 Python 工具只读 `tb_*` 不走此 REST 接口，理论上无其它消费方）。

## W2-1（P1-12）dkd-agent 限额判断查询热点

**现状**（已核实 `app/audit.py`）：
- `enforce_daily_quota()` :270 每次请求触发 `summarize_usage()` 两次（per-user :283 + global :289）；
- 两次都是 `WHERE create_time >= now()-1d AND del_flag='0'` 的窗口聚合——`agent_message` 的 `create_time` 若无索引即**每次请求两次近全表扫描**，高频对话时熔断检查自己变成热点；
- 顺带发现一个**语义 bug**（本次一并修）：`summarize_usage(scene=...)` :258 过滤的是 `Message.msg_role == scene`——参数名叫「场景」实际按「消息角色」过滤，按场景统计的口径是错的。

**改法**（三层，按成本递增）：
1. **加索引（必做）**：`agent_message` 补 `(user_id, create_time)` 复合索引 + `create_time` 单列索引（global 查询用），DDL 归档到 `docs/ddl/`，注明执行环境与回滚（DROP INDEX）。
2. **进程内短 TTL 缓存（建议做）**：global 用量对熔断而言本来就是**近似前置检查**（docstring 自己写明「请求前判断」），用 `time.monotonic()` 做 30~60s 的进程级缓存即可，把两次查询降为「per-user 1 次索引查询 + global 每 30s 1 次」。注意缓存要可被测试强制失效（提供 `_reset_usage_cache()` 供 conftest 用）。
3. **修 scene bug（一并做）**：`summarize_usage` 的 `scene` 过滤改到正确的列（`Message.scene`，若无此列则删掉该参数及其调用点——先 grep 确认 `ops.py` 的 usage 报表怎么传的再定）。

**涉及文件**：`app/audit.py`、新增 `docs/ddl/agent_message_index.sql`、`tests/test_audit*.py`
**验收**：① `uv run pytest` 全绿且新增防回归测试：限额触发的 429 行为不变、缓存 TTL 内不重复查询（可用打桩 session 计数断言）；② `ops.py` 的 `/agents/usage/summary` 返回值与改造前对拍；③ EXPLAIN 确认走新索引。
**预估**：1 人日 ｜ **风险**：中；缓存引入「熔断最多滞后 30s」的语义偏移，需在代码注释与运维 runbook（`docs/agent-operations-runbook.md`）同步声明。

## W2-2（P1-13）补货建单串行回调 → 有界并发

**现状**（已核实 `app/graphs/restock_graph.py::create_tasks` :510-563）：
- `for plan in plans: await deps.create_task(...)` 串行，每次回调超时上限 `DKD_AGENT_CALLBACK_TIMEOUT_S=10s` → N 台设备最坏 **N×10s** 才能结束本轮图执行，SSE/HTTP 请求方（Java 网关 read-timeout 120s）在 N>12 时开始逼近上限；
- 失败语义已良好设计：单台失败进 `failures` 不抛穿图、不回退状态——**改造必须保住这个语义**。

**改法**（方案 A，推荐）：
1. 用 `asyncio.Semaphore(4)` + `asyncio.gather(..., return_exceptions=False)` 并发执行「回调 + 结果归类」，每台设备的 `CallbackError/OrderClaimConflictError` 捕获逻辑原样搬进各自的 coroutine 包装函数；
2. `created/failures/updated` 三个列表的**追加顺序**改为按 `plans` 原序（gather 完成后按输入序归并，而不是完成序），保证结果可复现、测试断言稳定；
3. `deps.save_decision` 保持串行（写审计库的顺序性比速度重要，且它走的是 agent 自有库、无 10s 超时问题）；
4. 并发度做成配置：`DKD_AGENT_CREATE_TASK_CONCURRENCY`，默认 4，加进 `app/config.py` 与根 `.env.example`（带注释：为何默认 4——Java 侧回调接口有 `@RateLimiter(60s/60次/IP)`，容器内固定出口 IP，4 并发远低于限流阈值）。

**方案 B（备选，不推荐本期做）**：Java 侧新增批量建单端点 `POST /agent/callback/task/batch`。收益更大但要动 Java Controller + 校验链的事务语义 + 密钥/白名单配置，建议等 A 落地后按实际耗时再评估。

**涉及文件**：`app/graphs/restock_graph.py`、`app/config.py`、`.env.example`、`tests/` 补「多台并发建单、部分失败不抛穿」的防回归用例
**验收**：① `uv run pytest` 全绿；② 用 mock 的慢回调（人为 sleep 2s × 8 台）验证总耗时从 ~16s 降至 ~4s（4 并发 × 2 批）；③ 部分失败场景 `failures` 内容与串行版完全一致。
**预估**：1.5 人日 ｜ **风险**：中；重点防「并发回调打爆 Java 限流器」——已通过 Semaphore 默认 4 + 配置化兜底。

## W3-1（P1-16）前端三套 HTTP 通道收敛

**现状**：`@/utils/request.js`（axios，全站默认）、`src/utils/sse.js`（fetch+ReadableStream，SSE 专用，**有充分理由独立**）、`src/api/manage/restock.js` 的私有 `call()`（fetch，绕开 axios）。第三套存在的根因：request.js 的响应拦截器把后端可行动文案改写成「系统接口xxx异常」，restock 工作台需要把 409 等业务码原文展示给用户。另 `Settings/index.vue` 直接 import axios。

**改法**：
1. **改拦截器（根因修复）**：`utils/request.js` 响应拦截器区分「传输层失败」（网络/超时 → 现有兜底文案）与「业务层失败」（`res.data.code` 非成功 → **原样透传 `res.data.msg`**）。这一步影响全站错误提示文案，上线前要过一遍高频页面的异常态。
2. **restock.js 迁移**：删私有 `call()`，全部函数改走 `@/utils/request`，确认 409/业务码文案经新拦截器能原样到达组件。
3. **sse.js 保留不动**（注释已说明为何不能用 axios/EventSource，理由成立）。
4. **Settings/index.vue** 改回 `@/utils/request`。

**涉及文件**：`src/utils/request.js`、`src/api/manage/restock.js`、`src/layout/components/Settings/index.vue`
**验收**：① `npm run build:prod` exit 0；② 补货工作台手工回归：正常/409 冲突/停机降级三态文案与改造前一致；③ 任一老页面接口报错时错误提示仍可读（抽 3 个页面回归）。
**预估**：1 人日 ｜ **风险**：中——拦截器是全站命脉，建议单独一个 commit 便于回滚。

## W4-1（P1-14）状态/角色常量收敛到单一事实源

**现状**：
- Java 侧同一套工单状态码写了两份且类型不一致：`dkd-common/.../DkdContants.java`（Long）vs `dkd-app/.../common/constant/VmSystemConstant.java`（Integer）；
- Python 侧 `read_tools.DEFAULT_CASE_WINDOW_DAYS=1095` vs `assistant_tools.DEFAULT_CASE_WINDOW_DAYS=2000`（同义不同值，含义漂移的实锤）；
- 角色码 `1001/1002/1003` 在 Java 两模块 + Python `read_tools.py` 至少三处硬编码。

**改法**（务实版，不做过度工程）：
1. **先建契约文档**：`docs/CONTRACTS/status-codes.md` 一张总表（工单状态/类型、设备状态、订单状态、员工状态、角色码、变更类型），标注每个取值在三个子系统里的消费方——这是唯一事实源，评审用。
2. Java：`dkd-app` 的 `VmSystemConstant` 逐项改为引用/对齐 `DkdContants`（受限于独立 POM 无法直接依赖，退而求其次：两边常量名与取值强制对齐 + 在两处文件头互相引用契约文档路径与「改这里必须同步那里」警示）；
3. Python：`DEFAULT_CASE_WINDOW_DAYS` 统一为一个值（先查清 1095 与 2000 谁是故意的——grep 两处的注释与 git blame，若无故意的差异证据则以 `read_tools` 的 1095 为准），并在 `app/config.py` 配置化（带默认值），两个工具模块都读配置；
4. Python 角色码抽到 `app/config.py` 或独立 `app/constants.py`。

**验收**：契约文档评审通过；grep 全仓角色码/状态码字面量，除常量定义处外零散硬编码清零（允许 Mapper XML 的 SQL 字面量，但需在契约表登记）。
**预估**：1 人日 ｜ **风险**：低；**注意**：这不是纯机械替换——`dkd-app` 是生产子系统，改常量定义要过它自己的测试（`mvn -pl dkd-app test`，注意该工程目前**没有测试**，所以只做「引用对齐」不做「行为重构」）。
