## 1. 为什么要先把口径写死

排期 1-14 是「规则版与基线引擎双跑 3 周」，3-8 是「据此输出缺货率 / 建议偏差 / 人工调整率，
决定是否下线规则版入口」。三件事如果口径不统一，数字会“看起来有结论、实际不可比”：

- 规则版建议量取自 `tb_inventory.max_stock`，基线引擎取自 `tb_channel.max_capacity`
  ——**本库实测两边不一致**（FIX-5），于是偏差里混进了容量口径差（§6 有实测证据）；
- 缺货率的分母是「全部货道」还是「有库存记录的货道」，差别是本机 **272 : 3**；
- 人工调整率的分子来自审计留痕（`agent_decision_log`），按计划去重还是按动作计数，值差一倍。

所以本文件把每个指标的**分子/分母/数据源/SQL/边界**逐条写死；脚本与将来的报表都按它实现。

## 2. 两条链路的口径对照

| 维度 | 规则版（Java） | 基线引擎（Python） |
| --- | --- | --- |
| 入口 | `GET /manage/inventory/restock` → `InventoryServiceImpl.generateRestockSuggestions()`（`InventoryServiceImpl.java:414`） | `POST /agents/restock/analyze` → 落 `agent_restock_plan`；读侧 `GET /agent/restock/plans` |
| 取候选 | `selectLowInventoryList()` + `selectOutOfStockList()`（低库存/缺货才出建议） | 运行中设备逐货道算，缺口 > 0 才出计划行 |
| **容量来源** | **`tb_inventory.max_stock`** | **`tb_channel.max_capacity`**（FIX-5 实测两侧不一致） |
| 现库存来源 | `tb_inventory.current_stock` | 同 |
| 需求依据 | **不看销量**：目标 = 容量 × 85% | 逐日销量分位（0.75）× 覆盖率天数 × 服务水平系数，多窗口加权 |
| 下限 | `min_stock × 2 - 现库存`（取大） | 同（刻意对齐，避免运营习惯突变） |
| 上限 | `容量 - 现库存` | 同 |
| 兜底 | 无（不依赖样本） | 无样本/缺货自锁 → 容量 × 85% + `degraded=true` |
| 优先级 | 0 → 4；≤ min×0.5 → 3；≤ min → 2；否则 1 | 由需求紧迫度推导，最终夹取同上 |
| 单位与字段 | `suggestedQuantity`（件） | `items[].suggestedQuantity`（件） |

> **两处刻意一致**：`85%` 兜底与 `min_stock × 2` 下限。原因写在
> `app/graphs/restock_baseline.py` 模块 docstring：双跑要对照的是“看不看销量”，
> 不是“下限算不算得一样”，把无关变量对齐才能让偏差可解释。

## 3. 配对口径（怎么算「一对」）

**同一天 + 同一台设备 + 同一个货道**才算一对。键 = `(innerCode, channelCode)`。

- **不按设备汇总后再比**：设备内多货道会互相掩盖（A 货道多补 8 件、B 货道少补 8 件，
  汇总后偏差为 0，看着“完全一致”，实际两条建议都错了）。
- **不跨天比**：规则版接口是“当前库存的即时建议”，基线计划是“当日 06:00 的快照”，
  跨天比等于拿两个不同时点的库存做差。
- **只有一边有建议的单独计数，不进百分比**：规则版只在低库存/缺货时出建议，基线在“有缺口”时出。
  混进百分比就会出现“除以 0”或“凭空 +∞”，统计数字会骗人。脚本输出
  `ruleOnly` / `baselineOnly` 两个计数正是为此。

## 4. 三项指标定义（3-8 的报表口径）

### 4.1 缺货率

| 项 | 定义 |
| --- | --- |
| 分子 | `tb_inventory.current_stock = 0` 的货道数 |
| 分母 | **有 `tb_inventory` 记录的货道数**（不是 `tb_channel` 行数） |
| 为什么分母这么取 | `tb_channel` 里**没有库存列**，货道库存只存在于 `tb_inventory`；用 272 行当分母会把“没采集到库存”算成“不缺货”，得出一个虚假的低缺货率 |
| 必附指标 | **库存覆盖率** = `count(tb_inventory) / count(tb_channel)`。本机 = **3 / 272 ≈ 1.1%**——这个数字必须与缺货率同时出现，否则读者会把 3 个货道的比例当全网 |
| 已知阻断 | 覆盖率要提上去依赖数据采集完整性（属 Java/现场侧），不是 Agent 能补的 |

复跑 SQL（脚本已实现）：

```sql
select count(*) as total,
       sum(case when current_stock = 0 then 1 else 0 end) as out_of_stock
  from tb_inventory;                       -- 注意：该表**没有 del_flag 列**
select count(*) from tb_channel;            -- 覆盖率分母
```

### 4.2 建议偏差

| 项 | 定义 |
| --- | --- |
| 单货道偏差（绝对值） | `baseline - rule`（件）。**负值 = 基线更保守** |
| 单货道偏差（相对值） | `(baseline - rule) / rule × 100%`，**仅当 `rule > 0`**；`rule = 0` 时不计算相对值（避免除零/无穷） |
| 汇总 | 配对样本的**均值与中位数同时给**：样本极小时（本机 n=2）均值会被单条极端值带走，中位数更能说明“多数情况” |
| 总量对照 | 两侧建议量合计（`ruleTotal` / `baselineTotal`），用于看方向 |
| 解读边界 | **在 FIX-5（容量权威源）拍板前，偏差不可解释为“算法差异”**——见 §6 实测 |

### 4.3 人工调整率

| 项 | 定义 |
| --- | --- |
| 分子 | 当日有 `adjust` 或 `skip` 动作的**计划数**（按 `target_id` 去重） |
| 分母 | 当日计划数（`agent_restock_plan.plan_date = 当日`） |
| 数据源 | `agent_decision_log`：`action in ('restock.adjust','restock.skip')`，`target_type = 'plan'`，`create_time` 落在当日 |
| 为什么按计划去重而不是按动作计数 | 同一计划当天可能被调整多次（改完又改），按动作计数会把“一个人反复改”当成“很多计划需要人工干预”，指标就失去管理含义 |
| 实测坑（写错会静默得 0） | `target_type` 的值是 **`plan`**，不是 `restock_plan`；表里也确有 `restock_pause` / `restock_run` / `conversation` 等其它值，硬编码前必须先 `select distinct` 核 |

## 6. 本机实测（2026-10-01，n=2）——以及最关键的发现

```
规则版（Java 按容量 85%）货道数 : 2，合计建议 6 件
基线引擎（agent_restock_plan）: 3，合计建议 22 件

  设备         货道      规则版    基线     偏差     偏差%
  A1000001   5-6         4        9       +5    +125.0%
  aim5xu4I   1-1         2        8       +6    +300.0%
  偏差均值=212.5%  中位数=212.5%
  只有基线有建议（规则版未提）: 1 条
```

**这个 +212% 不是算法差异，是容量口径差异。** 原始证据（同一次运行查的两侧容量）：

| 设备 | 货道 | `tb_inventory.max_stock`（规则版用） | `tb_channel.max_capacity`（基线用） |
| --- | --- | --- | --- |
| A1000001 | 5-6 | **6** | **10** |
| aim5xu4I | 1-1 | **2** | **10** |
| tCeiyxLx | 3-6 | 4 | 10 |

验算：`aim5xu4I/1-1` 现库存 0 ——

- 规则版：`0.85 × 2 = 1.7 → 1`，再与 `min_stock(1) × 2 - 0 = 2` 取大 → **2**（与接口返回一致）；
- 基线引擎：目标是 `10`（货道容量）→ 建议 **8~10**（实际 8，含需求侧夹取）。

两侧算的都不是“错”，但**分子分母用的是两个不同的容量**。所以：

> **在 FIX-5（货道容量权威源）拍板之前，「建议偏差」这个指标量的是容量口径差，
> 不能用来评价基线引擎的算法优劣，也不能据此决定是否下线规则版入口。**

这与 §八 FIX-5 的结论互相印证：FIX-5 从“数据质量问题”升级为 **1-12 对账与 1-14 双跑的共同前置**。

> 附一条口径演进的留痕：早先（1-4 回测补记）记录的偏差是 **-33.3%**（基线更保守），
> 与本次 +212.5% 方向相反。原因**不是算错**，而是两次比对覆盖的货道/容量取值不同、
> 样本都只有个位数——这正好说明**小样本偏差率不能当结论**，必须按 §7 的数据量门槛执行。

## 7. 前置、门槛与执行方式

| 项 | 要求 | 当前状态 |
| --- | --- | --- |
| **FIX-6** 生产/测试库导出（`tb_inventory` 历史快照、`tb_order` 近 90 天、历史人工补货量） | 双跑与回测的**硬前置** | ⛔ 未拿到 |
| **FIX-5** 容量权威源拍板 | 偏差可解释的前置 | ⛔ 未拍板 |
| **FIX-21** 29% 订单无 `channel_code` | 按货道聚合的完整性问题（已按“不可归因”单列，对账守恒） | ⛔ 待业务决定是否修数 |
| 库存覆盖率 | 缺货率可用的前置（建议 ≥80%，当前 1.1%） | ⛔ 差距大 |
| 样本量 | 建议：配对货道 ≥ 30 条 / 累计 ≥ 3 周再出结论 | ⛔ 本机 2 条 |

**执行频率**：双跑期（3 周）每日 06:00 分析后各跑一次
`compare-1-14-rule-vs-baseline.py --json >> 当日报表`；3 周后按 §4/§5 字段汇总出 3-8 报告。
脚本**只读**，可随时重跑；不写任何业务表（`agent_*` 也不写）。
