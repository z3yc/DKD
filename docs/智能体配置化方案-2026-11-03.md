> 日期：2026-11-03 · 状态：**待确认，确认后才动工**

> 原则：**先给内置三智能体（补货 / 诊断 / 助手）的配置「可视、可调、可回滚」，再开放自定义智能体；任何一步都不改变未配置时的行为。**

## 0. 现状梳理（勘察结论，全文均有代码依据）

### 0.1 三个智能体的配置结构、存储与调用链路

| 智能体 | 入口（前端 → 网关 → Python） | 配置现在在哪 | 存储 |
| --- | --- | --- | --- |
| **补货 restock** | 补货工作台 → `AgentGatewayController` → `/agent/restock/**` → `restock_graph`（analyze→calibrate→await_confirmation→create_tasks）；定时 06:00 由 `AgentTask.restockAnalyze()` → `POST /agents/restock/analyze` | ① `app/config.py` 的 `restock_*` 环境变量（分位 0.75、周期 2.0、系数 0.7~1.5、批量 20…）；② `app/prompts/restock_calibration.py` 的 `SYSTEM_PROMPT` + `FACTOR_MIN/MAX` 源码常量；③ `temperature`/`max_tokens` **不存在** | `agent_restock_plan` / `agent_restock_pause`（MySQL，业务状态不是配置） |
| **诊断 fault** | 设备页/运行页 → 网关 → `POST /agent/fault/runs` → `fault_graph`（diagnostician→dispatcher，**不调 LLM**，结论由 `diagnosis.py` 纯规则合成）→ 人工确认回调建维修单 | 硬编码散在 `fault_graph.py`（窗口 24h、优先级、动作关键词）、`diagnosis.py:217`（置信度阈值 ≥2/==1）、`diagnosis_checklist.py`（5 步清单） | `agent_run` / `agent_step` / `agent_tool_call` / `agent_decision_log` |
| **助手 chat** | AI 抽屉 → 网关 → `POST /agent/chat`（SSE）→ `chat_graph`（focus→respond→tools），场景 1-4 共用一张图，**场景只决定 system prompt 与工具子集**（`build_chat_graph(tools_by_scene=…)` 签名已支持） | ① `app/prompts/assistant_chat.py` 的 `_BASE_PROMPT`/`_SCENE_FOCUS`/`_SCENE_WRITE_GUIDANCE`/`TOOL_NAMES_BY_SCENE` 源码常量；② `app/llm.py:57` 模型参数（无 temperature/max_tokens，`max_retries=2` 字面量）；③ 前端 `AgentAssistant/index.vue` 硬编码场景列表/快捷问题/欢迎语 | `agent_conversation` / `agent_message` / checkpoint（SQLite 或 PG） |

**调用链路总图**：`dkd-vue → /prod-api → Java AgentGatewayController（JWT+权限点+路径白名单，fail-closed）→ Python /agent/*（回环放行/服务间密钥）→ 图 → 工具（MySQL 只读白名单）→ 写操作回调 Java /agent/callback/task（密钥+白名单+限流）`。菜单：`sys_menu` 9000「AI 智能体」下已有 9001 工作台 / 9007 决策审计 / 9010 运行时间线。

**关键事实**：
- 全仓**没有** `agent_config` / `ai_config` 表；但 `agent_run.config_version` 列注释已预留「`agent_config.version`，用于回放」——目前无写入方，是空钩子；
- Python 配置只有 `.env` 一个来源，`get_settings()` 是进程单例，改配置必须重启；无任何热更新；
- prompt 全部是源码常量，改一个字 = 改代码 + 发版（Java 兜底链路 `AiServiceImpl` 的 switch-case prompt 同理，且其 `maxRetries` 字段配了不生效）；
- `ChatRequest.scene` 校验写死 `ge=1, le=4`（`app/api/chat.py`）。

### 0.2 由此得出的核心设计决策

**决策 1：自定义智能体 = 配置驱动的「场景」，不是用户可编排的新图。**
新增智能体必须选择运行载体（`chat_graph` / `restock_graph` / `fault_graph`），可配的是：角色设定（system prompt）、工具子集（受载体白名单约束）、模型参数、业务参数覆写、启用状态。理由：动态编排会与「LLM 不可信 + 人工确认 + 审计」红线冲突；而 `chat_graph` 天生支持「按场景切工具子集」，新增自定义助手 = 注册一个新场景码（≥101）+ 一条工具子集配置，改动最小且可被现有测试覆盖。

**决策 2：配置放 MySQL 的 `agent_config` 表（对上预留语义），版本化。**
CRUD 归 Java（业务事实唯一所有者 + RuoYi 权限/审计），Python 只读消费；每次保存 `version+1` 并整行快照进 `agent_config_history`，同时把 `agent_run.config_version` 真正写起来（补上空钩子）。

**决策 3：默认即现状，三重回落，永不因配置失败 500。**
内置三智能体的 seed 初始值 = 从现有代码常量导出的原文；DB 无记录 / 解析失败 / 超范围 → 一律回落代码内置默认并 WARN；`DKD_AGENT_CONFIG_FROM_DB=false` 可一键回到纯代码路径。

## 3. 表单校验规则与错误提示方式

| 字段 | 规则 | 提示 |
| --- | --- | --- |
| 名称 | 必填，2~30 字，全局不重名（后端唯一校验） | 「名称已存在」 |
| 编码 | 必填，`^[a-z][a-z0-9_]{2,31}$`，新增可填/编辑只读 | 「小写字母开头，2~32 位，保存后不可修改」 |
| 描述 | 必填，≤200 字 | |
| system_prompt | 必填 100~8000 字；**只允许白名单占位符**（chat: `{focus} {tool_list} {window_days}`；restock: `{fmin} {fmax} {data}`） | 出现未知 `{xxx}`：「不支持的占位符 {xxx}」 |
| tools | ≥1 个；必须是载体白名单子集（前端禁选 + 后端再校验） | 「xxx 不在该载体的工具白名单内」 |
| temperature | 0~2；>1.2 黄字预警「输出不稳定，建议 ≤0.7」 | |
| max_tokens | 256~8192；>4096 提示成本 | |
| timeout_s / max_retries | 5~300 / 0~5 | <10 提示「过短会导致正常请求超时」 |
| 系数上/下界 | 0.5~2.0 且 min < max | 「上界必须大于下界（当前下界 x.xx）」（原型 S3 已演示） |
| 停用 | `enabled=0` 时原因必填 5~100 字 | 「停用内置智能体时，原因必填（5~100 字）」 |

**错误提示方式**（沿用 Element Plus）：字段级 = `el-form-item` 红字 + `scrollToField` 滚动定位首个错误；全局 = `ElMessage.error(res.msg)`；冲突 = `409` → `ElMessageBox`「配置已被他人更新，请刷新后重试」（表单携带 `version` 做乐观锁）。后端三重校验：前端 rules → Controller 入参校验 → Service 唯一性/白名单/乐观锁，错误以 `{code, msg, data:{field->msg}}` 返回。

## 4. 保存与结果反馈交互

- **保存即生效**：只有「保存并生效」一个主动作（配置不是业务事实，回滚成本低），生成新版本、对该智能体**下一次调用**生效，进行中的运行不受影响；按钮 `loading` + `finally` 复位（AGENTS §2.2 铁律）。
- **改内置的保护区字段**（模型、工具集、业务阈值、停用）→ `ElMessageBox.confirm` 说明影响范围 + 要求填 `change_note`（写入 history）。
- **成功**：`ElMessage.success('已保存，版本 v13 已生效')` + 抽屉关闭 + 列表刷新 + 该行高亮一次。
- **新增自定义**：创建后 `v1`，启用状态默认开；启用后立即出现在助手抽屉场景列表（见 §5.6）。

## 5. 配置持久化与生效接入点

### 5.1 Java 侧（新增，业务域 `dkd-manage`）

`AgentConfigController`（`/manage/agent/config/**`，list/get/add/edit/setEnabled/history/rollback）+ `IAgentConfigService`/`AgentConfigServiceImpl` + `AgentConfigMapper`(.xml) + `AgentLogController`（`/manage/agent/log/list`，只读）。写操作加 `@Log` 进 `sys_oper_log`。**不经 `/agent` 网关**（不动 fail-closed 白名单）。

### 5.2 配置生效与失效通知

- Python 新增 `app/config_store.py`：进程内 TTL 缓存（30s）+ 版本比对；`load_agent_config(code) -> snapshot | None`，**任何异常一律返回 None**；
- `AGENT_OWNED_TABLES` 增加 `agent_config`（只读）；
- Java 保存成功后异步调 `POST /agents/config/reload`（走 ops.py 服务间密钥）清 Python 缓存；失败只 WARN，靠 TTL 兜底；
- 总开关 `DKD_AGENT_CONFIG_FROM_DB`（默认 true，可一键回落纯代码）。

### 5.3 三个载体的接入点（最小改动清单）

| 载体 | 改动点 | 现状文件 |
| --- | --- | --- |
| chat | `ChatRequest.scene` 校验放宽为「1-4 内置 或 已启用配置存在」；`build_chat_graph(tools_by_scene=…)` 传入配置工具集；`system_prompt(scene, …)` 增加 overrides；`build_chat_model()` 支持注入 temperature/max_tokens/retries | `app/api/chat.py` / `app/graphs/chat_graph.py:299` / `app/prompts/assistant_chat.py` |
| restock | `system_prompt(factor_min,max)` 与 `restock_baseline.py` 阈值改从 config 取；`config.py` 的 `restock_*` 作为「env 兜底」 | `app/prompts/restock_calibration.py` / `app/graphs/restock_baseline.py` |
| fault | `DEFAULT_WINDOW_HOURS`、置信度阈值、排查清单改为配置驱动 | `app/graphs/fault_graph.py:64` / `app/services/diagnosis.py:217` / `diagnosis_checklist.py` |
| 公共 | `app/llm.py:57` 支持 `temperature/max_tokens/max_retries` 入参（默认不传 = 现状） | `app/llm.py` |

### 5.4 运行侧埋点

每次运行把实际生效的 `version` 写入 `agent_run.config_version`（补上现有空钩子），审计页即可按版本回放。

### 5.5 保证原有三个智能体不被破坏

1. **seed 初始值 = 代码常量原文**（含 prompt 逐字一致），未修改前行为与现状完全相同；
2. **三重回落**：DB 无记录 / 解析失败 / 超范围 → 代码内置默认 + WARN；LLM 参数缺失 → 不传参（现状）；
3. **数值强制夹取**到 §2.3 区间，杜绝手滑导致成本失控；
4. 内置 `builtin=1`：**不可删除、不可改 code/runtime**；保护区字段变更二次确认；
5. `app/prompts/*.py` 常量**保留**作为默认值来源，不删；
6. 测试门槛：现有 **pytest 538 全绿** + 新增 `test_config_store.py` 断言「DB 关闭/为空/损坏 → 行为与现状一致」「配置值=默认常量时 prompt 与硬编码逐字相同」；
7. 前端助手抽屉 `SCENES` 改为「优先取 `/agent/status` 下发的 agents 列表，失败回落现有硬编码 3 项」——新智能体自动出现，老行为兜底。

### 5.6 新配置在列表与调用流程中生效的接入点（汇总）

- 智能体列表页：新菜单 9011，数据来自 `agent_config`；
- 助手抽屉场景列表：`GET /agent/status` 扩展返回 `agents[]`；
- 调用流程：`/agent/chat` 的 scene 校验 + `chat_graph` 工具子集 + `llm.py` 参数注入；
- 审计：配置变更进 `agent_config_history` + `sys_oper_log`；运行留痕进 `agent_run.config_version`。

## 6. 智能体执行日志页（本次新增页面）

**页面**：菜单 9017，路由 `manage/agentLog/index`，权限点 `manage:agentLog:list`（只读，无写权限——与审计页一致的纪律）。

**数据来源（二选一，推荐 A）**：
- **A（推荐）新增 `agent_log` 表**：Python 侧加一个自定义 `logging.Handler`，把 `dkd.agent.*` 日志器（级别≥INFO，含 `request_id/run_id/conversation_id` 上下文）异步批量写入。字段：`id` / `create_time`(datetime(3) 毫秒) / `level` / `run_id` / `conversation_id` / `task_id` / `scene` / `node` / `status` / `message`(varchar1000) / `error_msg`(varchar1000) / `request_id` / `duration_ms` / 审计列。只增不改、保留 30 天（定时清理）。读写纪律与 `agent_*` 一致（Agent 可写不 DELETE，Java 只读）。
- **B 复用 `agent_run/step/tool_call`**：不新增表，把「日志」定义为 step+tool_call 的平铺视图。省一张表但语义被强行压平，错误信息（如 LLM 超时原因）没有自然落点。
- 落 A 时前端三个状态：空 = `el-empty` + 「调整筛选条件」；加载中 = 骨架屏；失败 = 错误图标 + 原因 + 重试（均见原型 S6）。

**读链路**：前端 `agentLog.js` → Java `GET /manage/agent/log/list`（时间范围必填、默认近 24h、时间倒序、分页 20/页；关键词匹配 `message/error_msg`；级别/状态/关联对象精确匹配；**强制 LIMIT 与索引**——`idx(create_time)`、`idx(request_id)`、`idx(level, create_time)`，符合单主库护栏）→ MySQL 直查（不经 Python）。「关联运行」跳到 `agentRun` 页带 `requestId` 参数。

**查询性能护栏**：默认时间窗 24h、最大 30 天；关键词搜索强制带时间范围；`list` 上限 2000 行；详情行内展开（不再发请求）。

## 7. 分期建议与待确认问题

**分期**：P1 = `agent_config` 表 + 内置三智能体的「可视化 + 参数微调 + 版本/回滚」+ 日志页（风险最低）；P2 = 自定义智能体（chat 载体）；P3 = 自定义 restock/fault 载体 + 版本 diff UI。

**待确认**：
1. 自定义智能体是否**只放开 chat 载体**起步（推荐）？restock/fault 的自定义要后置到 P3 吗？
2. 日志页数据走 **新增 `agent_log` 表**（推荐 A）还是复用 `agent_run/step`（B）？
3. `agent_config` 里 temperature/max_tokens 是否接受「NULL = 未设置（模型默认）」语义（推荐，与现状一致），还是强制给默认数值？
4. 停用内置智能体是否允许（推荐：允许但必须填原因 + 二次确认），还是只让「改参数、不让停用」？
5. 助手抽屉场景列表改后端下发（推荐，可灰度），还是 P1 阶段保持前端硬编码？
