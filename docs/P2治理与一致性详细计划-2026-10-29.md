## 2. 前端（执行单元：vue-p2）

### 2.1（P2-19）loading 未复位

**现状**：RuoYi 模板写法 `loading.value = true; listXxx(params).then(res => {...; loading.value = false})` —— 请求 reject 时 `loading` 永久为 `true`，表格一直转圈。审计结果（`views/manage/**`，`loading.value = true` 且无 `finally`）：

`emp`、`inventory`、`node`、`order`、`partner`、`policy`、`region`、`sku`、`skuClass`、`task/business`、`task/operation`、`vm/index`、`vm/components/ChannelDialog`、`vmStatus`、`vmType`（15 个）；`agentAudit`/`agentRun`/`report`/`restock` 已合规（P1 期间新增/整改的页面）。

**改法**：把 `.then()` 内的 `loading.value = false` 移到 `.finally(() => { loading.value = false; })`；`async/await` 形式用 `try { ... } finally { ... }`。**不改**成功路径的赋值顺序与错误提示（错误提示由 `request.js` 拦截器统一 toast）。

**验收**：`npm run build:prod` exit 0；人工抽查 3 个页面（region/node/sku）在接口失败时 loading 复位（可用 DevTools 断网模拟）。

### 2.2（P2-20）`getAiDiagnosis` 重复

**现状**：`api/manage/vm.js:46` 与 `api/manage/ai.js:4` 两个函数体逐字相同（`GET /manage/ai/diagnose`，`params: { innerCode }`）；消费方 `views/manage/vm/index.vue:289` 从 `vm.js` 导入。

**改法**：保留 `ai.js` 为唯一实现；删除 `vm.js` 中的副本；`vm/index.vue` 改从 `@/api/manage/ai` 导入。grep 确认无其他消费方。

**验收**：`grep -rn "getAiDiagnosis" dkd-vue/src` 只剩 `ai.js` 定义 + `vm/index.vue` 导入与调用；build 通过。

### 2.3（P2-21）CRUD 五件套收敛

**现状**：`api/manage/*.js` 中 region/partner/policy/node/vmType/sku/skuClass 等文件是同一份「list/get/add/update/del」样板，只是 baseUrl 不同（`/manage/region`、`/manage/partner`…），改一个接口要改 N 处。

**改法**：新增 `src/api/manage/crudFactory.js`：

```js
export function createCrud(baseUrl) {
  return {
    list: (query) => request({ url: baseUrl + '/list', method: 'get', params: query }),
    get:  (id)    => request({ url: baseUrl + '/' + id, method: 'get' }),
    add:  (data)  => request({ url: baseUrl, method: 'post', data }),
    update:(data) => request({ url: baseUrl, method: 'put', data }),
    del:  (id)    => request({ url: baseUrl + '/' + id, method: 'delete' })
  }
}
```

迁移纪律（**本轮最容易被"顺手改错"的地方**）：
1. 只迁移「五个函数的 URL/method/参数名与工厂完全一致」的文件；有自定义方法的文件（`partner.resetPartnerPwd`、`emp` 的导入导出、`task` 的业务方法等）要么保留自定义方法、五件套走工厂，要么整体不迁移 —— 以「不改变任何请求定义」为准；
2. 迁移后**保持原命名导出**（`export const listRegion = regionCrud.list` 之类），调用方 `import { listRegion }` 一行都不用改；
3. 不同构的文件不迁移，报告中列出理由（不做"为了统一而改 URL"）。

**验收**：build 通过 + `git diff` 逐文件对照（迁移前后 URL/method/params 完全一致）+ 报告中「迁移 / 未迁移」清单。

### 2.4（P2-22）路由权限旁路

**现状**：`router/index.js:87-112` 把 `/manage/inventory`、`/manage/report` 直接放进 `constantRoutes`。`store/modules/permission.js` 对 `constantRoutes` 不做权限过滤（`filterDynamicRoutes` 只作用于 `dynamicRoutes`），因此**任何已登录用户都能通过 URL 直达这两页**，与 `sys_menu` 配置的角色权限无关（页面内按钮的 `v-hasPermi` 只挡操作，不挡进入）。

**改法**：两条路由从 `constantRoutes` 迁到 `dynamicRoutes`，加 `permissions: ['manage:inventory:list']` / `['manage:report:list']`（与页面内 `v-hasPermi` 的前缀一致；超管 `*:*:*` 命中原有 `hasPermiOr` 逻辑）；保留 `component: Layout` 与子路由 path/name/meta。注释写明「为什么不能留在 constantRoutes」。
顺带修复 home 小部件中可确证为错的跳转（`partner-node-collect-chart.vue:34` 的 `/node/partner`、`abnormal-equipment-table.vue:163` 的相对路径 `vm/machine`）；RuoYi 模板标准跳转（`tool/gen`、`monitor/job`、`system/*`）不动，报告中列为范围外。

**验收**：build 通过；报告中说明「哪些角色仍能进 / 哪些不能」以及 `sys_menu` 侧的后续动作（若后端菜单已登记则无需动作，未登记则侧边栏本来就没有入口）。

### 2.5（P2-27）`store/index.js` 隐式依赖 auto-import

**现状**：`store/index.js` 只有 `const store = createPinia()`，`createPinia` 靠 `vite/plugins/auto-import.js` 的 `pinia` preset 注入。Vite 构建/开发上下文正常，但该文件一旦被非 Vite 工具（脚本、单测、SSR/Node 侧导入）直接引用就会 `ReferenceError`。

**改法**：加 `import { createPinia } from 'pinia'` + 一行注释说明为什么不能省。

**验收**：build 通过；`node -e "require('fs')..."` 不适用（ESM），以代码审阅为准。

## 3. Java（执行单元：java-p2）

### 3.1（P2-24）订单/支付状态裸字面量 + 异常类型

**现状**：`OrderServiceImpl` 用 `4L`（取消）、`2L`（退款中 / 可退款判断）、`0L`（可取消判断）裸字面量；`getStatusDesc` 用 `switch (status.intValue())` + `case 0..4`；`getOrderDetail` 抛裸 `RuntimeException`。`ReportServiceImpl` 又有私有 `ORDER_STATUS_SUCCESS = 2`（与 P1-14 常量收敛的精神不一致——报表口径常量仍散落）。契约表 `docs/CONTRACTS/status-codes.md` 已定义订单/支付状态，但 dkd-parent 侧没有对应常量。

**改法**：
1. `DkdContants` 增补 `ORDER_STATUS_CREATE/PAYED/VENDOUT_SUCCESS/VENDOUT_FAIL/INVALID`（Long）与 `PAY_STATUS_*`（按契约表取值），Javadoc 指向契约表；
2. `OrderServiceImpl` 全部替换为常量；`getStatusDesc` 改 if/else 链（Java 8 的 `switch` 不能用 Long 常量做 case，除非强转，可读性差）；**修正 cancelOrder 的注释口径**（契约表 4 = 失效 INVALID；业务上「取消」落到的正是该状态，注释要写清"取消订单写入失效状态"，不能再写"4-已取消"这种与契约表冲突的表述）；
3. `RuntimeException` → `ServiceException`（RuoYi 全局异常处理器会转成用户可见文案），**文案逐字不变**（前端可能依赖）；
4. `ReportServiceImpl.ORDER_STATUS_SUCCESS` 改为从 `DkdContants` 派生，消灭第二个 2；
5. 契约表登记 dkd-parent 常量名，与 dkd-app `VmSystemConstant` 对齐；
6. 单测：`getOrderDetail(null)` / 订单不存在抛 `ServiceException`；`cancelOrder` 状态 0 → status=4 + cancelDesc；`refundOrder` 状态 2 → payStatus=2；**拒绝路径**（状态 1 不可取消、状态 0 不可退款）必须有覆盖（AGENTS §8：该拒绝的没拒绝比该通过的没通过更严重）。

**验收**：`mvn -pl dkd-admin -am test` 全绿（基线 141 + 新增用例）；`grep -n "4L\|2L\|0L\|RuntimeException" OrderServiceImpl.java` 中业务字面量清零（`0L` 作为 id 判断等非状态语义可保留，需逐个说明）。

### 3.2（P2-26）`rank()` 假数据

**现状**：`dkd-app/.../TaskController.java:54-60` 的 `GET /task/rank/{userId}` 直接返回 `{total: 3, rank: 3}`，移动端首页排名是假的。

**改法**：`TaskMapper` 增两条 `@Select`（dkd-app 无 XML mapper）：① `COUNT(*) FROM tb_task WHERE user_id=? AND task_status=4`；② 领先人数（`GROUP BY user_id HAVING COUNT(*) > 我的完成数` 的子查询计数）。`TaskService.getRank(userId)` 返回 `Map{total, rank}`，`rank = 领先人数 + 1`，`userId` 非法抛 `LogicException`；Controller 只委托。

**口径（自主决策，需产品确认）**：total = 该员工**历史累计已完成**工单数；rank = 按已完成数降序、并列取最小名次（1-based）。若产品要「本月/本季」口径，只需改 SQL 的时间条件，不动接口结构。

**验收**：`mvn -f dkd-app/pom.xml test` 全绿（新增 4 个用例：非法入参 / rank=1 / rank=3 / total 透传）；接口返回结构 `{total, rank}` 不变（移动端不感知）。

### 3.3（P2-29）`batchInsertChannels` 无分批

**现状**：`VendingMachineServiceImpl:102-120` 按 `vmRow × vmCol` 内存生成货道后调用 `channelService.batchInsertChannels(channelList)`，`ChannelMapper.xml` 是一条 `INSERT ... VALUES <foreach>`。机型维度大（如 100×100）时单条 SQL 的包体可能超 `max_allowed_packet`，表现为插入失败/连接被重置。双层循环本身是内存对象构造（**不是** N+1 查询），不重构。

**改法**：`ChannelServiceImpl.batchInsertChannels` 按 500 行分片循环调用 mapper、累加返回行数（顺序不变）；常量 `CHANNEL_INSERT_BATCH_SIZE = 500` 加注释说明依据（单行约 8 列 → 500 行远低于默认 4MB/64MB 包上限，留足余量）；XML 不动；`VendingMachineServiceImpl` 循环处补一行「为什么这里是内存构造」的注释。

**验收**：`mvn -pl dkd-admin -am test` 全绿；新增单测覆盖 1200 行 → 3 次调用（500/500/200）且返回合计 1200、小列表 1 次、空列表行为与现状一致。
