### ② 详细版（STAR，适合项目经历栏展开）

**S｜背景与问题**
RuoYi-Vue 3.8.7 改造的售货机运营平台，核心闭环是「投放 → 下单扣减 → 库存预警 → 补货建议 → 建工单 → 运维端接单 → 库存回写」。既有 AI 能力是 `com.dkd.common.ai` 里的单轮 prompt 拼接：prompt 硬编码在 switch-case、只取设备 5 个静态字段、输出 100 字文本，**无上下文、无工具调用、无结构化输出、无审计留痕**，无法产出任何可执行动作。

**T｜目标**
在**不改动 Java 单体事务与校验链、不影响主业务可用性**的前提下，接入有状态多轮智能体，让 AI 的建议能被人工确认后直接变成业务工单，且全过程可审计、可降级、可回滚。

**A｜做法（4 个关键决策）**

1. **落地形态：独立 Python 进程旁路**，而非 JVM 内嵌（Spring AI / LangChain4j 需 JDK 17+，而项目锁死 Java 8，升级会牵动 RuoYi 全家桶）。
2. **数据通道：读直连 / 写回调**。MySQL 两级授权账号 —— 业务表 `tb_*` 仅 `SELECT`（表白名单校验器 + 无 `tb_` 前缀直接拒绝），Agent 自有表 `agent_*` 可 `INSERT/UPDATE` 但**无 DELETE（软删除）、无 DDL、禁跨库**；所有业务写操作回调 Java REST，复用 `TaskServiceImpl.insertTaskDto` 的校验链。
3. **鉴权：前端统一经 Java 网关**（`/agent/**` 反代 + 身份头白名单重建），Python 不解析 JWT，只信任网关注入的 `X-Agent-User/Roles/Region`；服务间回调另用密钥 + 路径白名单 + 限流（两套体系不混用）。
4. **可控性：human-in-the-loop + 幂等 + 降级**。首期所有建单类写操作必须人工确认；幂等靠 DB 唯一键（`UNIQUE(vm_id, plan_date)`）+ CAS 状态机 + Java 侧设备级在途工单防重；`agent.enabled=false` 一键回退到原单轮链路。

## 三、面试深挖预演（Q&A）

**Q1｜为什么独立 Python 服务，不在 Java 里做？**
Java 8 是硬约束（主流 LLM 框架要 17+），升级 JDK 牵动 RuoYi 全家桶，风险远大于收益；Python 侧 LangGraph、评测、向量生态成熟度更高。代价是多一个进程，我用「旁路 + 开关 + 兜底」把风险控制在"挂了也不影响主业务"。

**Q2｜为什么不让 LLM 直接调 Java 接口甚至直连数据库？**
直连库会绕过事务、工单防重、员工区域校验和操作日志 —— 这是红线。回调 Java REST 天然复用这套校验链，等于**把 AI 的不确定性关在业务校验之外**。LLM 输出一律视为不可信：结构化解析 + 范围夹取（补货量 clamp 到 `[0, 货道容量−现库存]`）+ 写操作人工确认。

**Q3｜AI 给的补货量不准怎么办？**
三层兜底：① **统计基线不依赖 LLM**（7/14/30 天分位销量 + 容量约束），LLM 只做点位画像/节假日/异常波动的校准与理由生成 —— 最坏退化成"可解释的规则增强版"；② 首期全人工确认；③ 7 日复盘（建议量 vs 实际消耗）回写迭代。并计划与规则版**并行双跑**做对照，而不是上线就看数字。

**Q4｜多轮对话状态存哪？**
LangGraph checkpointer。最初方案用 Redis，开工前核基础设施发现本机 Redis 是 **3.2.100**（2016 微软移植版，无 MODULE 系统 ⇒ 装不了 RedisJSON/RediSearch，内核 <5.0 ⇒ 无 Streams），`langgraph-checkpoint-redis` 根本跑不起来 → 改 SQLite（单机形态匹配、零新增基础设施），并预留 PG saver 的可切换实现与迁移触发条件。

**Q5｜怎么保证 AI 建的单不重复？**
四道：`agent_restock_plan` 的 `UNIQUE(vm_id, plan_date)`（DB 硬约束）、CAS 状态机抢占（只有"建议/已调整/待指派"能认领）、建单前查同设备在途工单、以及 `insertTaskDto` 自带的设备级防重。

**Q6｜跨进程建单崩了怎么办？（这是本项目最硬的一题）**
CAS 抢占成功（status=7）后回调 Java，若 Java 已提交但 Python 在回写状态前崩溃，会出现"库里已建单、Agent 状态仍占位"的窗口。我**没有**做成自动释放 —— 因为自动释放会允许再次建单、产生重复工单。当前是**风险缓解**：占位不动 + 值班按设备/计划日与 Java 工单查询人工对账 + 受控释放并留操作人/时间/证据。要真正闭环得加租约超时回收协议 + Java 侧幂等键，这条我在文档里明确写成"未完成"，没标成功。

**Q7｜AI 服务挂了怎么办？**
`agent.enabled=false` 一键降级回原单轮 AI 链路；多轮会话入口直接隐藏（**不伪造能力**，因为多轮没有等价的单轮兜底）；定时任务失败抛异常让 Quartz 落 `sys_job_log`，不静默。另外把"开关关闭/运营主动暂停"记为 WARN/INFO 正常返回 —— 否则告警会被脱敏，真故障没人看。

**Q8｜SSE 怎么保证真的流式、没被缓冲？**
不是"我看能流式"，而是打时间戳：`curl -N | while read line; do echo $(date +%s%3N) $line; done`，实测 51 帧 / 3.2s，首 delta 距首行 70ms、末帧距首帧 3217ms（若被整包缓冲，所有行会在毫秒级一起到达）。服务端每块 `flush()`（Tomcat 默认 8KB 缓冲），响应头带 `X-Accel-Buffering: no` + `no-transform` 对付 Nginx。另外区分**帧级 vs token 级**流式，本项目是 token 级（`astream(stream_mode=["messages","values"])`）。

**Q9｜断点续传怎么做的？**
客户端把最后一帧 `id` 放进 `Last-Event-ID` 重连；服务端**不重跑图**，从 checkpointer 读回本轮回复、只补发未收帧（`index <= offset` 跳过）——不重复计费、不重复追加上下文。踩过一个坑：前端把 `Last-Event-ID` 当普通参数传给了**每一轮**请求，服务端误判为续传去读 checkpoint，新会话直接 404；修法是把"新一轮"与"续传"两个语义彻底拆开，并顺手补了断线自动续接。

**Q10｜这个项目最难的地方是什么？**
不是调模型，是**边界设计**：读写分离的粒度（哪些能直连、哪些必须走 Java）、写操作的幂等与人工确认、降级与审计的可用性权衡、以及"AI 代码要进生产"所需的留痕/脱敏/成本/权限一整套工程约束。

## 四、面试时最能讲的 6 个"坑"（故事性排序）

| # | 坑 | 一句话讲法 |
| --- | --- | --- |
| 1 | **Redis 3.2 装不了 checkpointer** | "有中间件"≠"这个中间件能满足这个用法"。选型前跑一条 `MODULE LIST` 省整个方案返工。 |
| 2 | **字段语义陷阱：`expectCapacity`** | DTO 注释写"货道容量"，但运维端实际把它当**补货数量**累加进库存。若按注释填容量 → 库存虚增 → 后续建议全部基于假数据滚雪球。修法三层：范围夹取 + `after = 现库存 + 建议量` 校验 + 映射测试断言。**字段名不是契约，消费行为才是契约。** |
| 3 | **过滤器顺序决定"可达性"** | 回调鉴权注册在 `order=0`，而 Spring Security 链是 `-100` ⇒ 我的过滤器在安全链**内部**，未登记路径先被 401 掉，"非白名单→404"分支**永远不可达**。单测全绿也发现不了（直接调方法绕过了整条链）。改为 `-200` 让服务间密钥先守门。**顺序类缺陷只能靠端到端发现。** |
| 4 | **`HttpURLConnection.getErrorStream()` 必须"先读状态码"** | 先读 body 会把 4xx/5xx 抛成 IOException，被误判成"服务不可达"去降级 —— 于是**限额 429 和链路故障被归成同一类**。修法：强制先 `getRawStatusCode()` 再读 body，4xx 原样透传。**错误要按层次归类**，归错层会把排查引向错误方向。 |
| 5 | **校准结果从不落库** | 工作台显示 20 件、实际按 21 件建单。根因是校准后没回写。**没有任何断言比对"库里的值"与"状态里的值"**，所以脚本全绿。教训：**"验收脚本全绿"≠"功能对"** —— 后来我把断言扩到控制台 warning、计算样式、以及库值 vs 状态值对照。 |
| 6 | **审计是旁路，但一挂整个对话就断了** | `/agent/chat` 返回 HTTP 200 但 SSE 体为空，根因是限额查询用了 `agent_message.user_id` 这个**当时根本不存在的列**，异常把 SSE 生成器打断了。修法：区分**基础设施故障（降级放行 + WARN）** 与 **业务规则命中（明确 429 拒绝）** —— 两者错误语义完全不同；旁路能力必须在**调用点**做异常边界。 |
