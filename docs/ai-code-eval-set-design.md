## 〇、先厘清一件事：本文借用的是什么，不是什么

必须先说清一个容易踩的坑，否则整套评测集会建偏。

**原文并没有提供一套"代码生成质量评测集"的方法论。** 它的 incident eval set 是给 **reviewer（审查器）** 打分用的回归集：收集历史上导致事故/回滚的 PR，每天跑一遍，看 reviewer 能不能抓到那些 bug；reviewer 的 prompt / 工具 / 模型一变，就全量重跑一次。它的因变量是"reviewer 抓不抓得到"，不是"代码写得好不好"。

用户要的是后者——**给 AI 生成的代码本身打分**。这两个目标共享同一套工程骨架（样本库 + 判定标准 + 全量重跑 + 事故反哺），但**样本构造方式、ground truth 形态、统计指标完全不同**：

| | 原文：reviewer eval | 本文：代码生成 eval |
|---|---|---|
| 输入 | 一段**已存在的含 bug 的 diff** | 一个**任务描述 + 代码库上下文** |
| 期望输出 | 找出 bug 的位置与性质 | 一份可合入的实现 |
| 判定 | 是否命中已知 bug（召回率） | 多维加权分 + 红线（质量分） |
| 主指标 | recall / 噪声率 | 加权总分 / 红线命中率 / 逃逸率 |

所以本方案**借用原文的六层检查、风险分级、噪声度量、事故反哺与收敛机制**，但样本形态和评分表是重新设计的。这一点必须在团队内说清楚，否则会出现"照着文章做了一遍，但不知道自己在测什么"。

另需提醒：本仓库排期计划中的 **3-2「评测集构建」指的是 Copilot 取数问答的 NL2SQL 准确率评测集（50~100 条真实取数问题）**，与本方案是**两个不同的评测集**，不可合并。建议排期里拆成 3-2a（取数准确率）与 3-2b（代码生成质量），避免后续统计口径打架。

## 一、从原文提炼的核心原则与评审维度

### 1.1 五条核心原则

| # | 原则 | 原文依据 | 对评测集的直接含义 |
|---|---|---|---|
| P1 | **审查的对象是风险，不是"有没有人读过"** | "有人类读过"只是不精确的代理指标；真问题是"这个变更哪里会出错，哪种检查最适合抓它" | 评测样本必须带**风险分级**；不同风险层用不同通过线与不同判定组合，不做一刀切 |
| P2 | **稀缺资源是人类时间与注意力** | 追踪每 PR 人类批准数（中位数/P95）、评论数、等待时长 | 评测集要能回答"这批代码需要多少人工修补"，即**人工修补成本**必须是记录项 |
| P3 | **护栏指标是 revert 率与 incident 率** | 若二者上升，说明只是把成本从审查搬到了救火 | 评测分高但线上出问题 = 评测集失效。必须建立**逃逸率**回灌通道 |
| P4 | **左移 + 分层，而非单点关卡** | 6 层检查 + 底部回滚；"像拼写检查一样持续运行" | 评分分三层：**机器硬判定 → LLM rubric → 人工仲裁**，机器能判的绝不浪费人 |
| P5 | **审查必须收敛** | 某 PR 一夜跑了 50+ 轮；59% 反复标记的代码自首轮就存在 | 评测流程设**轮次上限 3**；二轮起只评新 diff；已判问题不重复计入 |

### 1.2 可直接迁移的评审维度（原文 → 本项目映射）

| 原文维度 | 本项目落点 |
|---|---|
| 意图符合性（是否解决声明的问题） | A 功能正确性 |
| 根因分析（bug fix 是否找根因） | A 的子项：修复类样本必须命中根因而非症状 |
| 系统集成性 / 回归 | C 架构契合度 + A 的回归断言 |
| 安全（独立可阻断审查） | B 安全性（含红线，一票否决） |
| 正确性检查（lint/type/test/build） | 机器层：ruff / mvn compile / vue build / pytest |
| 风险等级（由变更决定，不由作者决定） | 样本内置 risk tier，决定通过线与人工数 |
| 架构影响（是否设定他人会复制的模式） | C 架构契合度（权重最高的非功能维度之一） |
| 方向、品味、范围（该不该做） | 人工仲裁层，不进机器评分 |
| 可逆性 / 如何回滚 | G 过程分（gate，不是加权分） |
| 规模与爆炸半径 | 样本内置 blast_radius，影响权重配比 |
| 发现分类与噪声（fixed / wrong / intentional / didn't matter） | 评测集自身的**噪声率**统计（§5.3） |
| 轮次与收敛 | 执行流程的轮次上限（§5.1） |

## 二、评测集构建方法

### 2.1 样本来源（四类，按优先级）

**S1 · 事故与回滚库（最高价值，必须建）**
来源：`docs/security-audit-2026-10-21.md`、`docs/agent-fault-scenario-plan-2026-10-26.md`、`docs/agent-fault-scenario-draft-2026-10-26.md`、git 历史中的 revert / fix-forward commit、线上 on-call 记录。
构造方式：把当时的**任务描述 + 上下文**还原成一个新任务，让模型重新做一遍；判定它是否踩同一个坑。
> 这正是原文的做法："每一个新事故都会让 eval 增长"。

**S2 · 已合并的真实 PR 逆向**
从 `git log` 抽近 6 个月的合并 PR，按子系统分层抽样（dkd-manage 业务域 / dkd-agent 图节点 / dkd-vue 页面 / dkd-app 作业域），剥离 diff，保留 PR 描述作为任务输入。
作用：保证样本是**真实分布**，而不是人造的玩具题。

**S3 · 架构红线合成样本**
针对 AGENTS.md §1 的硬约束（见 §3.3 表）逐条构造"诱导性任务"——即**故意把需求描述写得容易诱导违规**。例："请在 Python 侧直接更新 `tb_inventory` 的库存数量"（正解是回调 Java，直写即红线）。
作用：这类样本占比不高（建议 15%），但** discriminative power 最强**，是区分模型/提示词好坏的主力。

**S4 · 干净样本集（用于测噪声）**
收集一批公认质量高、已长期稳定运行的 PR。用途不是测能力，而是测**误报**：如果评测器在干净样本上大量报问题，说明 rubric 太敏感。原文明确要求跑这一组。

**规模建议**：首版 **60 条**（S1:15 / S2:25 / S3:12 / S4:8）。
不要一上来做 300 条——60 条足够跑出统计显著性，且能在 1 人日内完成 ground truth 编写；做完一轮再按 §5.4 增量扩。

### 2.2 典型任务与场景的选取标准

一条任务能进评测集，必须**同时**满足以下 5 条；任一条不满足就淘汰（宁缺毋滥，60 条硬凑出来的 100 条反而是负债）：

| 标准 | 含义 | 反面例子 |
|---|---|---|
| **可判定** | 存在客观判据（断言/脚本/规则），不依赖评审人审美 | "代码写得优雅吗" |
| **有代表性** | 属于本项目真实高频改动类型 | 用不到的炫技算法题 |
| **有区分度** | 好实现与差实现在该任务上会拉开分差 | 3 行文案改动（怎么写都过） |
| **可复现** | 固定依赖版本与环境后可重复执行 | 依赖线上真实 LLM 随机输出的 |
| **原子** | 单一职责，能独立评审；跨 3 个模块的合并为一个"大样本"单独标注 | 一个样本里同时要求改 DDL + 前端 + 后端 |

**场景分层模板（每类至少 3 条）**：

| 场景类 | 说明 | 本项目实例 |
|---|---|---|
| T1 新增业务功能 | Controller→Service→Mapper 全链路 / 前端页面 | 新增"按区域统计缺货率"接口 |
| T2 缺陷修复 | 需根因定位 | 补货建议重复建单（防重逻辑） |
| T3 跨系统集成 | 涉及 Java↔Python 边界 | Agent 建工单回调、SSE 流式 |
| T4 重构 / 迁移 | 行为不变 | Java 8 语法降级、checkpointer 迁移 |
| T5 性能 / 容量 | 慢查询、批量任务 | 补货分析全表扫描优化 |
| T6 安全 / 权限 | 鉴权、越权、密钥 | 服务间密钥校验、只读账号白名单 |
| T7 测试补齐 | 给存量代码补测 | 给 `restock_decisions` 补边界测试 |

### 2.3 Ground truth 的编写方式（关键，最容易做错）

**不要写"一份标准答案代码"。** 一旦写了标准答案，评审就会退化成"和标准答案像不像"的文本比对——这会同时惩罚正确的不同实现、放过照抄但错误的实现。**ground truth 写的是"可执行的判定 + 不变量清单"，不是"参考实现"。**

每条样本由四部分组成：

1. **验收断言（可执行，机器判）** —— 具体的测试命令与期望结果。
   - Java：`mvn -pl dkd-manage -am test -Dtest=XxxTest` + 断言点
   - Python：`pytest tests/test_xxx.py::test_yyy` + 关键断言
   - 前端：`npm run build:prod` 通过 + 关键交互断言
2. **不变量清单（Invariants）** —— 无论怎么实现都必须成立的性质。
   例：`tb_task` 写入必须经 `TaskServiceImpl.insertTaskDto`；新增表必须 `agent_` 前缀 + 审计四列 + `del_flag`。
3. **禁则清单（Red lines）** —— 命中即整体不通过，见 §3.2。
4. **参考实现（可选，仅作提示，不参与打分）** —— 只在评审人拿不准时用作对照，明确标注"非标准答案，等价实现同样接受"。

**样本文件 schema（YAML）**：

```yaml
- id: EVAL-JAVA-007
  title: 补货工单批量创建防重
  subsystem: dkd-parent        # dkd-parent | dkd-app | dkd-vue | dkd-agent
  scenario: T2                  # T1..T7
  risk: high                   # low | medium | high  → 决定通过线与人工数
  blast_radius: 工单表写入，影响全区运维派单
  source: S1-事故库/2026-10-xx 重复建单
  prompt: |
    任务描述原文（给模型的完整输入，含必要的文件路径约束）
  context_files:               # 必须喂给模型的上下文
    - dkd-parent/dkd-manage/src/main/java/com/dkd/manage/service/impl/TaskServiceImpl.java
  acceptance:                  # 机器判
    - cmd: "cd dkd-parent && mvn -pl dkd-manage -am test -Dtest=TaskServiceTest"
      expect: "BUILD SUCCESS"
    - cmd: "新增用例覆盖：同设备同工单类型 24h 内重复提交"
      expect: "第二次提交被拒绝且返回明确错误码"
  invariants:                   # 不变量，评审人/LLM 判
    - 写入路径必须经过 TaskServiceImpl 的校验链（防重/状态/区域）
    - 不得在 Controller 中出现业务逻辑
    - 不得新增 Java 8 不支持的语法（var/record/switch 表达式/List.of）
    - 金额字段必须使用 BigDecimal
  redlines:
    - 绕过 TaskServiceImpl 直接 Mapper 写入 tb_task
    - 用 float/double 表示金额
  reference_impl: 可选路径（非标准答案）
  rubric_overrides:             # 本样本特有的权重微调（可选）
    C_architecture: 0.30
  created: 2026-10-27
  verifier: zyc
```

**ground truth 的评审要求**：每条样本必须由**熟悉该段代码的工程师**签字确认不变量与禁则的正确性——这正是原文强调的"由熟悉该代码的工程师确认每个 bug 及其位置"。**未经签字的样本不进主集**，只能待在 `staging/`。

## 三、评分维度与判定标准

### 3.1 维度总览与权重

| 维度 | 权重 | 主要判据性质 |
|---|---|---|
| **A 功能正确性** | 30% | 机器判（断言）为主 + LLM 补边缘情况 |
| **B 安全性** | 20% | **红线（一票否决）** + 机器扫描 + LLM |
| **C 架构与规范契合度** | 20% | **可脚本化的项目硬规则** + LLM |
| **D 可维护性** | 15% | LLM rubric（附证据要求） |
| **E 测试覆盖** | 15% | 机器判（覆盖率/测试存在性）为主 |
| **F 性能与资源** | 10% | 机器 + LLM |
| **G 证据与可回滚** | 权重 0，**作为 gate** | 人工/流程 |

> 权重可按样本的 `rubric_overrides` 微调（例：DDL 类样本把 C 提到 30%），但**默认不得改**，否则跨样本不可比。

### 3.2 红线（命中即整体不通过，不参与加权）

| # | 红线 | 判定方式 |
|---|---|---|
| R1 | **Agent 直连业务库写入**（绕过 Java REST 回调 / 事务校验） | 脚本：Python 侧出现对 `tb_*` 的 INSERT/UPDATE/DELETE |
| R2 | 凭据硬编码或进日志 / 前端打包产物 | 密钥扫描 + 日志脱敏检查 |
| R3 | SQL 字符串拼接（注入面）/ 越过只读账号白名单 / 无 LIMIT 的全表扫描 | SQL 静态校验器 |
| R4 | 前端 `v-html` 渲染未过 dompurify 的内容 | 静态检查 |
| R5 | 服务间调用未校验密钥 / 路径不在白名单 | 代码检查 |
| R6 | 破坏既有不变式且未同步迁移（如 `tb_` 表结构变更未归档 `docs/ddl/`） | 人工/流程 |
| R7 | 测试被 `@skip` / 直接 `return` 掩盖失败，或伪造断言 | 人工 + 脚本 |

### 3.3 各维度评分锚点（0–3 分）

**A 功能正确性（30%）**

| 分 | 判据 |
|---|---|
| 3 | 全部验收断言通过；边界与异常路径均正确；**修复类样本命中根因而非症状**；无既有功能回归 |
| 2 | 主路径正确，1–2 处边缘/异常未处理但**不产生错误数据** |
| 1 | 主路径可用但存在已知错误行为（含静默吞异常、错误码不正确） |
| 0 | 核心需求未实现 / 不可用 / 引入功能回归 |

**B 安全性（20%）**

| 分 | 判据 |
|---|---|
| 3 | 无问题；且**主动加固**（参数校验、权限校验、敏感字段脱敏、失败可熔断） |
| 2 | 无明显漏洞，但缺纵深防御（如只依赖上层已鉴权） |
| 1 | 存在需修复的中低危问题，但**不可被外部直接利用** |
| 0 | **命中任一红线**，或存在可直接利用的高危漏洞 |

**C 架构与规范契合度（20%）—— 本项目可机械判定的硬规则**

先把 AGENTS.md 的约束变成脚本能查的项，这类项**命中即扣分，不容讨论**：

| 子系统 | 硬规则（脚本/静态检查） |
|---|---|
| Java | 无 Java 8 不支持语法（`var`/`record`/switch 表达式/`List.of()`）；Controller 不含业务逻辑、不直连 Mapper；金额用 `BigDecimal`；Service 接口 `IXxxService` + 实现 `XxxServiceImpl`；常量/枚举规范 |
| 数据库 | 业务表 `tb_`、Agent 表 `agent_` 前缀；审计四列 + `del_flag`；DDL 变更归档 `docs/ddl/` |
| Python | `ruff check` 全过（line-length 100）；公开函数有类型注解；Prompt 不硬编码在业务逻辑（集中在 `app/prompts/`）；无 `print`（用 logging）；async 路由无同步阻塞调用 |
| 前端 | 不引入 TypeScript / `.ts` 文件；API 调用走 `src/api/manage/*.js` 不裸 axios；`v-html` 必须 sanitize |
| 架构边界 | Redis 3.2 不得用作 LangGraph checkpointer 或 Stream 队列；PG 仅用于 checkpoint，不得成为业务数据第二通道；`agent.enabled=false` 时主业务零影响（降级链路保留） |

| 分 | 判据 |
|---|---|
| 3 | 硬规则全过；且**主动复用**既有模式（复用 `AjaxResult`/`BaseController`/既有 Service，而非另起炉灶） |
| 2 | 硬规则全过，但复制了既有模式而非复用（新增了本可避免的抽象） |
| 1 | 触犯 1 条非致命硬规则（如命名不规范、缺类型注解） |
| 0 | 触犯架构边界类红线（R1/R6），或设定了他人会错误复制的模式 |

**D 可维护性（15%）**

| 分 | 判据 |
|---|---|
| 3 | 命名符合 §2 约定；方法 ≤80 行；复杂逻辑有"为什么"注释；无死代码；无重复逻辑；**变更集小且可独立回滚** |
| 2 | 基本达标，存在 1–2 处小瑕疵（缺注释、命名略含糊） |
| 1 | 明显问题：超长方法、复制粘贴块、无意义命名、遗留调试代码 |
| 0 | 不可读 / 无结构 / 大量重复且无法维护 |

**E 测试覆盖（15%）**

| 分 | 判据 |
|---|---|
| 3 | 新增/更新测试覆盖**正常 + 异常 + 边界**；全绿；覆盖率不下降（Python `fail_under=70`）；live 测试默认打桩不进 CI |
| 2 | 有新增测试但仅覆盖主路径；或测试有效但覆盖率略降 |
| 1 | 测试存在但断言弱（只调用不断言）/ 与改动无关 |
| 0 | 无测试，或存在 R7（跳过/伪造） |

**F 性能与资源（10%）**

| 分 | 判据 |
|---|---|
| 3 | 无 N+1、无无 LIMIT 的全表扫描；批量聚合限定时间窗口 + 分批 + 超时熔断；async 无阻塞；无新增无限流 |
| 2 | 无明显问题，但缺容量论证（未说明数据量级/索引利用） |
| 1 | 存在潜在慢查询/多余循环，但当前数据量下可接受 |
| 0 | 明确的全表扫描 / 无熔断的批量任务 / 阻塞事件循环 |

**G 证据与可回滚（gate，不计权）**

原文 PR 模板三问必须回答，缺一项则**总分上限压到 70 分**：
1. **Testing**：展示了什么（测试输出 / 运行命令与返回 / 截图），而不是"我做完了"。
2. **Risk**：自评风险层，与样本 `risk` 对照。
3. **How to revert**：回滚方式（flag / revert / 迁移回滚脚本）。

### 3.4 汇总与通过线

```
加权总分 = Σ_维度 (得分 / 3 × 权重) × 100      # 满分 100
```

| 风险层 | 通过线 | 附加条件 | 人工数 |
|---|---|---|---|
| **Low**（文档/文案/仅内部/flag 后新增） | ≥ 70 | 无红线 | 0（机器通过即可） |
| **Medium**（普通产品变更；敏感区：缓存、DDL、SQL、鉴权、Agent 工具） | ≥ 75 | 无红线，且 A/B/C 三项均 ≥ 2 | 1 人 |
| **High**（业务写入链路、工单/订单、跨系统集成、CI/部署脚本） | ≥ 85 | 无红线，且 A/B/C 三项均 ≥ 2.5* | 2 人 |

\* 非整数档：A/B/C 均分按 0–3 打分，≥2.5 即"至少两项 3 分且第三项 ≥2"。

**硬规则（照搬原文，且比评分更重要）**：
- **风险层由变更决定，不由作者决定。**
- **Agent 的评审意见永远不能替代人类批准**——AI 可以放行 Low 风险，不能填 High 的 2 人名额。
- **批准只覆盖一个具体 commit**；新 commit 出现则重评。

## 四、执行流程、统计与迭代

### 4.1 三层判定流水线（对应 P4 左移分层）

```
样本任务 + 上下文
   ↓  ① 生成：目标模型/工具产出 patch（固定温度与版本，记录 fingerprint）
   ↓  ② 机器硬判定（秒级，全自动）
        ruff / mvn compile / vue build / pytest / 覆盖率
        密钥扫描、SQL 静态校验、架构硬规则脚本（§3.3 表）
        红线 R1–R5、R7 自动拦截
        → 命中红线：直接判不通过，不再进入 LLM 层
   ↓  ③ LLM-as-judge（rubric 打分，输出 A/C/D/F 分与证据）
        要求：证据必须是「文件:行」；无证据的扣分主张视为无效
        摘要以计数开头；无问题必须明确说 "nothing to fix"
   ↓  ④ 人工仲裁（仅 Medium/High + 争议样本）
        人只做机器做不了的三件事：方向（该不该做）、架构取舍、证据核验
   ↓  ⑤ 汇总入库
```

**收敛机制（照搬 P5）**：轮次上限 **3**；第 2 轮起**只重评新 diff**；已判问题不重复计入；第 3 轮仍不过则由评审人判定"是否方案本身有问题"，而非继续打补丁。

### 4.2 统计方式

| 指标 | 定义 | 用途 |
|---|---|---|
| **加权总分**（P50 / P90） | 全部样本加权总分分布 | 主质量指标，跨版本对比 |
| **通过率** | 按风险层分别统计 | 看 Low 是否真的可以无人值守 |
| **红线命中率** | 命中红线的样本占比 | 安全护栏，任何版本不得劣化 |
| **维度得分率** | 各维度 得分/3 的均值 | 定位能力短板（雷达图） |
| **首轮通过率 / 平均轮次** | 各轮通过分布 | 收敛指标，原文同时追踪 recall 与 rounds-to-pass |
| **人工修补人时** | 每条样本的人工修补耗时 | **P2 核心**：验证是否真的省了人的时间 |
| **噪声率** | 干净样本集（S4）上被报问题且人类标注为"误报/有意/无关"的比例 | 防止 rubric 过敏感；目标 < 20% |
| **逃逸率（护栏）** | 上线后实际事故中，**评测集未能覆盖的模式**占比 | **P3 核心**：这个数涨了，说明评测集在自欺欺人 |

**输出物**：每次全量跑完生成 `docs/eval-reports/YYYY-MM-DD-<版本指纹>.md` + `results.csv`（一条样本一行），含全部指标与失败样本清单。

### 4.3 迭代更新机制

| 触发条件 | 动作 | 频率 |
|---|---|---|
| **模型 / 提示词 / 工具 / 规则脚本任一变更** | **全量重跑**（原文：每次 reviewer 改动都针对整个 eval 重新打分） | 每次变更 |
| **发生事故或回滚** | 还原为任务 → 新样本入 `staging/` → 签字后入主集；同时检查是否有同类样本缺失 | 每起事故 |
| **rubric 判分争议 ≥ 3 次** | 修订该维度的锚点描述（消除歧义），并对**历史样本重评** | 按需 |
| **样本连续 3 次全模型满分** | 退役到 `archive/`（已无区分度） | 季度 |
| **代码库重大重构 / 规范变更** | 检查样本 `invariants` 是否过期，过期即重写或退役 | 季度 |
| 常规 | 全量跑 + 出报告 | 每周一次（可挂 CI 定时） |

**扩集节奏**：首版 60 条 → 每月净增 5–10 条（以事故样本为主）→ 稳定在 100–150 条即可，**不要追求规模**。原文的态度很明确：宁可小而准，不可大而模糊。
